# REQ

Everything OneDrop has to be, in one place: the requirements (the stories in `SPEC.md`, summed up by area) and the decisions made along the way, with the reasons for them. `SPEC.md` says _what_ users can do; this file also says _why it is that way_ and what was ruled out, so a later change doesn't undo a choice by accident. See `AGENTS.md` for when and how to update it.

## Product

- OneDrop is a self-hostable, Replit-style app builder: a person describes an app in chat, a coding agent builds it in a sandbox, and the running app is live at a URL while they work.
- Target users are trusted staff, not anonymous strangers. Real-time multi-user editing of one app is out of scope.
- Any stack, but Laravel's React starter kit by default (AGT-008).
- Bring your own AI: each user connects their own Claude, Codex/ChatGPT, OpenRouter or Gemini account. No markup on AI.
- Runs on a laptop (Docker), a single server, AWS, or Laravel Cloud from the same codebase.

### Decisions

- **2026-09-30: One codebase for self-hosting and for our multi-tenant hosted OneDrop.** Anyone can self-host one install; we also run one hosted install that serves many companies, so organizations must be a real boundary, not a kind of group. Groups stay as teams inside an organization (see Organizations).

- **2026-09-30: Name is OneDrop, never "zap".** `zap` is only the local checkout folder. Use `onedrop` in code, paths, images, headers; `APP_*` env vars on the platform server, `ONEDROP_*` inside sandboxes (where `APP_*` belongs to the user's app). Everything was renamed as a clean break, no migration for old sandboxes.
- **2026-09-28: Source available under the Elastic License 2.0.** Say "source available", never "open source".
- **2026-09-27: Inertia + React throughout; no Livewire,** in the platform and in the default app template.
- **2026-09-28: Postgres unless `DB_CONNECTION` says otherwise.** Local, tests, servers and the Docker install set `sqlite` explicitly; hosts like Laravel Cloud that only inject Postgres settings just work. Avoid SQL that only one of them supports.
- **2026-09-29: Dark theme by default.**
- **2026-10-03: Layers show depth by getting lighter, not by shadow alone.** Users said menus blended into the page in dark mode: popovers and cards were the same color as the background, with only a faint border, and dark shadows don't show on near-black. Each level is now a step lighter in dark mode: page, raised (`bg-card`, `bg-raised`), floating (`surface-floating`: menus, selects, popovers) and modal (`surface-modal`: dialogs, sheets). Floating and modal layers also get a brighter edge and a lit top. Dialogs dim and slightly blur what's behind them, so a dialog opened over a menu still stands out. Content inside a layer (a selected option, a deploy row) is a step lighter than the layer, not just outlined. New floating UI uses these utilities, not `bg-popover shadow-md`.
- **2026-10-04: Dark mode is charcoal, not black, with regions told apart by shade.** Users found the chat, workspace and files all one near-black (`#0a0a0a`), split only by thin lines. The page is now `oklch(0.23)` (about `#1c1d1f`), the frame around it (sidebar) darker, and tab bars and pane headers a lighter `bg-toolbar` strip; code, terminals and logs stay `neutral-950` so they read as wells. Greys carry a faint cool tint (chroma 0.004, hue 265) so they don't look dead.
- **2026-10-04: The preview bar looks like a browser's toolbar, without fake window chrome.** The address was an editable field that looked like plain text, so people didn't know they could type in it: it's now a rounded field with the path standing out over a dimmed host, copy and open-in-a-new-tab inside, and a thin line while the page loads. No traffic lights, tab strip or window frame: they cost height in a small pane and would clash with the workspace's own tabs. No stop button: the preview is on another origin, so the page can't stop its load.
- **2026-10-03: Major features get a manual test checklist in `docs/testing/`, hidden from the public docs.** The Pest suite runs on a fake sandbox, publisher and agents, so it can't prove that real agents (OpenCode, Claude Code, Codex), the Shell, Tools panels, sandbox updates or publishing still work. One page per area, steps plus checkboxes, tagged with spec IDs. They live in the Mintlify docs (a `hidden` tab, `public: false` group, `noindex` pages) rather than a separate tool, so they're versioned with the code and edited in the same change as the feature.
- **Build plan:** Laravel never holds a long-lived connection or supervises a process. Long-running work happens in the sandbox (agent, forwarder) or a queue job; Laravel coordinates, stores and broadcasts.

## Accounts, people and settings

AUTH-001..003, GRP-001..003, USR-001..003, INV-001, SET-001, BRAND-001.
Email/password (Fortify) plus Google, Microsoft, GitHub, GitLab and OIDC sign-in; two-factor and passkeys; groups with owners; admin user management; invite links; an account menu with settings in a modal.

### Decisions

- **Sign-up stays open to everyone;** invites are a convenience, not a gate (INV-001).
- **2026-09-29: The first account on a server install can only be made from the installer's one-time setup link** (`SETUP_TOKEN`), so a stranger who finds a new server first can't make themselves admin. On a local Docker install the first person to sign up is admin.
- **2026-09-30: Email verification is off by default when `APP_ENV=local`** (mail only goes to the log); on everywhere else. `AUTH_VERIFY_EMAIL` still wins.
- **Provider emails count as verified only when the provider says so;** Microsoft's never do. An unverified email is never auto-linked to an existing account.
- **2026-09-29: One GitHub App covers Tools → Git and "Continue with GitHub"** (`GITHUB_APP_CLIENT_ID/SECRET`); `GITHUB_CLIENT_*` override it for a separate OAuth app.
- **2026-09-28: Trust Laravel Cloud's load balancer** so OAuth callbacks come out as `https://` (the loopback-only `trustProxies()` had turned Cloud's handling off).
- **2026-09-28: Groups, Invite people and Users live in the settings modal,** not as top-level pages.
- **2026-09-30: An admin's user page (USR-002) shows what the install holds about the person, never their secrets.** AI connections show only their hint, GitHub only the login. Changing admin access stays on the list. Projects link only when the admin could open them anyway, so a platform admin still can't open another organization's projects (ORG-006). Recent sessions show only when sessions are kept in the database.
- **2026-09-30: Its usage section reuses the Usage page's report (`UsageReport`), fixed at 30 days,** plus all-time totals, so the two pages can't disagree about the numbers.
- **2026-09-30: Sign-ins are recorded on the user (`last_login_at`, `last_login_method`), not in a log table.** Admins needed "when did they last sign in" for support; a full history wasn't asked for. The method comes from the route that signed them in; a remember-me cookie resuming a session isn't recorded, and a provider sign-in that goes through the two-factor challenge still records the provider.
- **2026-09-30: The first admin actions on a user are Sign out everywhere and Reset two-factor,** the two support requests that come up most. Both ask for confirmation, not the admin's password, and neither works on the admin themselves (they have Settings → Security for that, and resetting your own two-factor there needs your password). Sign out everywhere deletes their database sessions and rotates the remember-me token. Suspending and deleting users were left for later: each needs its own decisions (what happens to their projects).
- **2026-09-30: Admins can impersonate users (USR-003), with an audit trail and guardrails.** It's a session swap (`Auth::login` as the user, the `impersonations` row's id kept in the session), not a package, so stopping signs the admin back in without a password. Other admins can't be impersonated, so one admin can't act as another and hide behind their name; the target already being a non-admin also keeps admin pages out of reach while impersonating. The user's profile, password, two-factor, passkeys, sign-in providers and account deletion are blocked by route name (`BlockWhileImpersonating`), so the admin can see and act as them but not take the account over. Everything else works as the user, including running agents on their AI connection. Every impersonation is a row (admin, user, IP, start, end) listed on the user's page; signing out ends it, and a session that just expires leaves it "not stopped". The banner is a fixed pill at the bottom, above the settings modal, because the sidebar is fixed full-height. Stopping only needs `auth`, since the user may not have verified their email. Confirming is enough; no password re-entry, like the other admin actions.

## Organizations

ORG-001..007 (see `docs/plans/organizations.md`; all built: the boundary, the switcher, members, settings, usage, logos, and the platform admin's list). Billing comes next, separately. Organizations are the boundary between companies: projects, groups, invites and skills belong to one, and nothing crosses it.

### Decisions

- **2026-09-30: Organizations always exist, on every install.** A self-hosted install has one, made by a migration that moves everything into it; the hosted install has many. One code path, not an "org mode", so self-hosted can't drift from hosted. No making "organization" a kind of group: groups have no settings, admins or data of their own, and it would mix a company boundary with a team inside it.
- **2026-09-30: A person can belong to several organizations and switch between them.** Adding this later would mean re-keying every membership, and consultants and agencies need it.
- **2026-09-30: The current organization comes from the URL, not the session.** Two tabs can be in two organizations, and a link always opens in the right one. Organization pages live under `/o/{slug}/` (new project, groups, invites; search and creating projects too). `/o/` rather than a bare `/{slug}` so a slug can never clash with a top-level route (`login`, `s`, `invite`, …). Project pages keep `/projects/{id}`: the project already names its organization, and putting the slug in every project route would have changed about 150 routes, every link to them and ~700 test lines for no gain in isolation. Opening an organization page or a project makes that organization the user's current one, and `/dashboard` (where signing in lands) redirects to it.
- **2026-09-30: Things that belong to a person stay with the person, outside any organization:** profile, password and 2FA, passkeys, social logins, SSH keys, AI connections (bring your own AI, REQ Product), and for now the GitHub accounts they connected. Projects, groups, invites and skills belong to an organization. A person's own skills stay in the organization they made them in. AI usage belongs to both: the person's Usage page shows what their connections paid for, and the organization's shows every run in its projects.
- **2026-09-30: Two kinds of admin.** Platform admin (`users.is_admin`) runs the install: sandbox providers, server, monitoring, backups, and on hosted, the list of organizations. Organization owners and admins run their organization: members, groups, invites, name and logo, usage. Being a platform admin gives no access to an organization's projects on the hosted install. On a self-hosted install platform admins also run its one organization, so making someone admin on the Users page still works as before, and the first account owns it.
- **2026-09-30: "Everyone" means everyone in the organization,** never everyone on the server: sharing a skill, Sign in with OneDrop set to everyone, its group picker and `groups` claim, and privately published apps. On the hosted install the old meaning would reach other customers. The Users list stays a platform-admin tool for the whole install; an organization's own members are in Settings → Organization (ORG-004).
- **2026-09-30: Sign-up depends on the install.** Self-hosted: new sign-ups join the one organization, as today (sign-up stays open). Hosted (`APP_MULTI_TENANT=true`, an `APP_` variable because it's the platform's own setting): signing up without an invite creates "<first name>'s organization", owned by that person; an invite joins the inviter's instead. New self-hosted accounts join as members.
- **2026-09-30: Something in another organization is a 404, not a 403,** so nobody can learn that another company's project, skill, group or invite exists. That includes a group or invite opened under the address of a different organization the person is also in.
- **2026-09-30: Leaving an organization takes away its projects, even your own.** Projects stay with the organization, where its owners and admins can still open them.
- **2026-09-30: Groups only take people from their organization,** and adding someone from outside gets the same message as an unknown email, so it doesn't reveal who is on the install.
- **2026-09-30: The migration names the install's organization after the install (ADMIN-001's name) and makes its admins its owners** (the first account when there's no admin). A fresh install gets its organization when its first account signs up.
- **2026-10-01: Each usage row records its project's organization** (`agent_usages.organization_id`), rather than finding an organization's runs through its projects, so a deleted project's runs still count in the organization's usage, as they already do in the person's. Its usage page is the person's Usage page with a breakdown by person added, opened from the account menu (it's a full page, not a settings tab).
- **2026-10-01: Members and the organization's details share one settings tab, Organization.** Everyone in it sees the list; owners and admins change it. Admins switch people between member and admin; making, changing or removing an owner is for owners only, so an admin can't take over or lock out the owners. On a self-hosted install a platform admin counts as an owner.
- **2026-10-01: On a self-hosted install nobody leaves or is removed from its one organization.** Everyone on the install is in it by design, and a removed person would just join again on their next page; an admin deletes the account instead. On the hosted install removing someone also takes them out of the organization's groups.
- **2026-10-01: Changing an organization's address breaks links to the old one.** No redirects from old slugs for now: a slug is chosen once, rarely changed, and keeping old ones would reserve them forever.
- **2026-10-01: The organization switcher is a submenu of the account menu at the bottom of the sidebar, and the app's logo and name are the sidebar's header again, on every install.** Switching organizations is rare, so it shouldn't take the whole top left. The organization's name shows under the user's name in the footer so they still see where they are. Stacking the app's header above a full-width switcher was ruled out earlier because it looked silly. A self-hosted install shows its one organization (named after the install), so the submenu still opens Organization settings. The install's own name and logo (ADMIN-001) stay on sign-in pages, the browser tab and emails.
- **2026-10-01: An organization without a logo shows the install's logo on a self-hosted install, and its initial on the hosted one.** Self-hosted then looks as it did; on the hosted install the droplet for every organization would make them look alike. Organization logos are only served to its members, unlike the install's, which the sign-in page needs.
- **2026-10-01: The Organization submenu lists the user's organizations, opens the organization's settings, and (hosted only) creates one;** switching goes to that organization's new-project page.
- **2026-10-01: The shared props are `currentOrganization` and `userOrganizations`, not `organization`/`organizations`.** A page's own prop with the same name replaces a shared one, and the admin user page's list of that user's organizations did, which crashed the switcher into a blank page.
- **2026-10-02: Anyone on the hosted install can create organizations, with only a name, but while AI credits are on (CREDIT-001) each person can own only one.** The address is made from the name and can be changed in settings. Every organization gets free credits, so unlimited organizations would mean unlimited credits; joining others by invite is unlimited. The limit lifts with paid plans.
- **2026-10-01: Platform admins get Admin → Organizations on the hosted install,** a list with owners and counts that links to the owners' user pages but never into an organization's projects. Searching happens in the browser, like the Users list, until there are too many to send.
- **2026-09-30: Tenancy first, billing later.** Plans and billing attach to the organization, but are a separate piece of work once the boundary is in place.
- **2026-10-01: Tests always run as a single-organization install (`APP_MULTI_TENANT=false` in `phpunit.xml`); tests for the hosted install turn it on themselves.** A local `.env` with `APP_MULTI_TENANT=true` made 83 tests fail with 404s, since their users weren't in the install's organization.

## AI connections and agents

AI-001..007, AGT-001..015, USAGE-001.
Users connect an AI before building; each project picks its agent (OpenCode, Claude Code or Codex), model and reasoning level; runs can be stopped, queued or sent now; prompts can be recalled; attachments work; usage and estimated cost are tracked per agent, model and project.

### Decisions

- **The platform never pools subscriptions.** Every run uses the project owner's own connection. Keys are encrypted and never sent back to the browser.
- **2026-09-29: Claude subscriptions use Claude Code's own sign-in** (`claude auth login` in the Shell tab). No token is stored; pasted setup tokens are refused and saved ones deleted. One sign-in covers all of a user's Docker sandboxes (per-user `CLAUDE_CONFIG_DIR`).
- **2026-09-30: A Docker sandbox with a dead host folder mends itself on its next wake:** the folder is made again and the container restarted, since a bind mount whose source was deleted can't be fixed from inside the container. Only folders under `storage_path` are recreated, never any other path a container mounts. A restart is the cheapest fix (files and home kept); recreating the sandbox would take minutes. Checked in `wake()` because it already runs on project open and the workspace's activity pings, at most every 30 seconds.
- **2026-09-30: Signing out of Claude empties the user's shared login folder; it never deletes it.** Running Docker sandboxes bind-mount that folder, and deleting it left them a dead mount: the next `claude auth login` said "Login successful" but couldn't save, so Claude Code stayed signed out until the sandbox was recreated.
- **2026-10-01: Tests point Docker's `storage_path` at a throwaway temp folder (`Tests\TestCase`), never `storage/app/sandboxes`.** Test users start at id 1, so tests that sign a user out of Claude (`SignOutOfClaude`) emptied the dev user's real shared login: running the suite locally signed every sandbox out of Claude.
- **2026-09-30: A Claude sign-in that succeeds switches the workspace back to the Preview tab.** Once the Shell says "Login successful" there's nothing left to do there; the app is what the user came to see. It only fires when the chat saw Claude Code signed out first, so opening an already-signed-in project doesn't move tabs. The Shell tab stays open, not closed, in case they want its output.
- **2026-09-30: The chat carries on after a Claude sign-in whenever it sees Claude Code signed in while a message waits for one** (the server says so: `waiting_for_sign_in`). It used to need to see "signed out" then "signed in" in the same page load, so switching tabs or reloading during the sign-in left the chat stuck until something else woke it.
- **2026-10-01: The chat keeps trying to pick up a message after a Claude sign-in until it runs or stops waiting.** The resume request once failed (SQLite "database is locked" in the rate limiter) and the chat, already seeing "signed in", stopped checking, so the message never ran. The resume answer now says whether a message still `waiting`; while one is, a failed or unsuccessful try is retried every 5s.
- **2026-09-30: A rejected Claude sign-in is retried once,** because Claude Code refreshing a shared login elsewhere revokes the token a run started with. Rejected twice, Claude Code is signed out in that sandbox so the chat offers to sign in.
- **2026-09-30: "Sign in to Claude" shows whenever a message waits for a sign-in, and each chat's sign-in check has its own rate limit (60 a minute).** The failed message tells the user to click that button, so it can't depend on the check answering. The check used `throttle:30,1`, which Laravel counts in one bucket per user across every route with the same limit: two signed-out chats polling every 5s ran out, the 429 was taken as "don't know", and the button disappeared. A failed check now keeps the last known answer.
- **2026-09-29: A run that failed because Claude Code wasn't signed in is remembered** and re-run once the user signs in.
- **2026-09-30: Codex is a third agent** next to OpenCode and Claude Code. Codex gets the ChatGPT tokens without the refresh token; the platform keeps refreshing it.
- **2026-09-30: AI onboarding is a picker, not a wall of forms.** The user picks one AI from a row of icons, then sees only that provider's setup. Subscriptions come first (Claude subscription, ChatGPT sign-in, OpenRouter sign-in); an API key is the small "instead" link. Gemini is key-only, since Google forbids subscription use. Settings → AI keeps the full list of cards, with Claude also subscription-first there, so both pages agree.
- **2026-09-30: Ollama connects with an Ollama Cloud key, or the user's own server by URL plus an optional Bearer key.** Cloud is the main option; it's models.dev's `ollama-cloud` provider, so OpenCode runs it as-is. The key is checked with `POST ollama.com/api/me`, because Ollama's model list answers without a key.
- **2026-09-30: A user's own Ollama server reuses OpenCode's `ollama-cloud` provider,** with its `baseURL` and the server's models (at zero cost) passed in `OPENCODE_CONFIG_CONTENT`. That keeps model ids, usage and the picker the same as Cloud, and the zero costs stop OpenCode pricing self-hosted runs at Cloud prices. The model list comes from the server's `/api/tags`, cached for an hour.
- **2026-09-30: The platform won't call private, loopback or internal Ollama addresses** (e.g. the cloud metadata address): the URL is user-typed, so this blocks server-side request forgery. The checked address is pinned for the request, and redirects aren't followed. `SANDBOX_OLLAMA_PRIVATE_SERVERS` allows them, and it's on by default when `APP_ENV=local`. There, Docker sandboxes reach a `localhost` server as `host.docker.internal`.
- **2026-09-30: A narrow chat composer shrinks its controls instead of wrapping them.** The model name truncates first, then Autofix (below 32rem) and the agent (below 24rem) drop to icons; the send buttons never shrink. Sizes follow the composer (a container query), not the window, since the chat pane is resizable.
- **2026-09-30: Annotate (AGT-013) takes its picture inside the preview's page** (modern-screenshot, pinned in `docker/sandbox/Dockerfile` and served by `host-proxy.mjs`), so it shows what the user sees: open menus, typed input, scroll position, their signed-in session. Rejected: the sandbox's headless Chromium (a fresh visit loses all of that) and the browser's tab sharing by default (a permission prompt every time). The library loads only when Annotate is clicked. It comes from the sandbox, never from a URL the workspace sends, since any page framing the preview could then run its own script there.
- **2026-09-30: The page only answers its own parent frame, at that frame's origin,** because the picture can show private data.
- **2026-09-30: The picture is the visible viewport, not the whole page.** That's what the user is pointing at, and a long page would be hard to draw on. Fixed headers and scrolled boxes (a dashboard's main column) are moved so the copy matches the screen.
- **2026-09-30: Marks are numbered on the picture, and the agent gets a line per mark naming the element under it,** like a CSS selector (tag, id, first 3 classes, `data-test`) with its text in brackets: `1. Note "too big" on div.card ("Counter")`. The agent can search the code for those instead of guessing from pixels. A box gets the element that fits it best; an arrow or note gets the element at its tip, skipping icons and formatting inside it.
- **2026-09-30: Those lines go to the agent only, never into the chat box or the chat** (`agent_context` on the request, kept in the message's `meta` and added to the agent's prompt). In the chat they read as stray HTML (`<div.card>`), and even as `div.card ("…")` the user saw them as noise they hadn't typed. They belong to the picture in the composer, so removing the picture before sending drops them.
- **2026-09-30: Annotate opens with the Text tool picked,** because a note saying what to change is what users reach for first.
- **2026-09-30: The marked-up picture goes into the chat box as a normal attachment (AGT-006), not sent automatically.** The user still says what to change, and vision-model fallback works as for any image. PNG, or JPEG if the PNG would be over the 10 MB attachment limit.
- **2026-09-30: Pressing an existing mark drags it, whatever tool is picked; pressing anywhere else draws.** Users need to nudge a mark onto the right element, and switching to a separate move tool would be one more step. A mark is hit by its line (within 8px), a note's text, or its number. Undo keeps a history of changes, so it reverses a whole drag or a Clear, not just the last mark added.
- **2026-09-30: Tab sharing is the fallback, offered only after the page fails to answer,** behind its own click, since the browser only lets a click start tab sharing.
- **2026-10-01: Inspect (AGT-014) works on the live page, not a picture:** hover highlights, click picks, drag moves, and Add to chat takes the picture at the end. The agent gets exact elements instead of guesses from where a mark was drawn, and moves show the result before anyone writes code.
- **2026-10-01: No libraries for Inspect; `docker/sandbox/inspector.js` does it in about 600 lines.** Rejected: bippy (it must load before React to hook it, but the inspector loads only when turned on), react-grab (its own UI and clipboard flow, not ours), @medv/finder (our short selector is enough: id, `data-testid`/`data-test`/`name`/`aria-label`, else a path of up to 5 steps using class names that aren't utilities), Moveable/interact.js (only drag is needed, not resize or rotate handles), and Stagewise or Onlook (whole editors). The proxy serves the file from the sandbox, loaded the first time the workspace asks, like the capture library.
- **2026-10-01: Components are read from the page's own DOM:** React's fiber on the element (`__reactFiber$…`): `_debugOwner` for the component, `_debugSource` for file and line (React 18), or the first app file in `_debugStack` (React 19, file only, because the stack isn't source-mapped). Vue's `__vueParentComponent` gives `__name` and `__file`. Production builds have none of these, so the agent gets the selector and text only.
- **2026-10-01: Moves are shown with copies, and the originals are hidden, never moved.** Moving an element React or Vue manages breaks the framework's next update ("removeChild" errors). A copy isn't the framework's, so it can't break it, and stopping removes the copies and shows the originals again. Removing a move from the list puts the page back the same way. The app's code and files never change; the agent makes the move.
- **2026-10-01: Dropping on the outer 30% of an element at either end moves before or after it; the middle 40% swaps.** Along the row for flex rows, inline elements and grid cells, otherwise down the column. Swapping is the common ask ("swap these buttons"), so it gets the biggest area.
- **2026-10-01: The file open in the editor goes with every message automatically, as a chip the user can remove (AGT-015).** Users say "this file" while looking at it; making them attach it each time is a step they'd skip. Only the path is sent, as an `agent_context` note (not in the chat), never the contents: the agent reads the file in the sandbox itself, and a big file would bloat every prompt. Unsaved changes are mentioned, since the agent can't see them.
- **2026-10-01: Removing the chip lasts until another file is opened, not just for one message.** Bringing it back after every send would make the user remove it again and again for the same file.
- **2026-10-01: While inspecting, the page's clicks, presses, drags and form submits are swallowed** (capture-phase listeners on the window), so picking a link or button doesn't use it. Esc in the page stops inspecting, and the inspector stops when the preview reloads, since a reloaded page has lost its picks.
- **2026-09-30: A user's own Ollama server with Nimble pulled answers the platform's checks in Jev's place (AI-007).** Nimble (Bespoke Labs, 9B, Apache 2.0) speaks Jev's API at `/v1/systemone`, so the questions and thresholds are unchanged; only where they're sent differs. It's free for the user, and keeps their prompts and code on the server they chose instead of sending them to OpenRouter. Self-hosted only: Nimble isn't on Ollama Cloud.
- **2026-09-30: Nimble on the server comes before the owner's OpenRouter key.** Someone who points the platform at their own server wants it used. It's found by name (`nimble` or `nimble:*`) in the server's cached model list (an hour), so pulling it takes effect within the hour, and nothing new to set up.
- **2026-09-30: A Nimble failure isn't retried on OpenRouter.** Falling back would quietly send the user's prompts somewhere else, and a down server would make a 3 s message check take two timeouts. It fails open like any Jev failure. Nimble's 8K-token context is smaller than Jev's, so the largest states (a long REQ.md, eight failing tests) can fail there; left as is until it shows up.
- **2026-09-30: Nimble is called through the same pinned, no-redirect, private-address-guarded request as the server's model list,** because the URL is user-typed (AI-006).
- **2026-09-30: The abuse check (PUB-003) never uses Nimble,** for the same reason it never uses the owner's OpenRouter key: an abuser's own server could answer whatever it liked.
- **Agent CLIs are pinned in `docker/sandbox/Dockerfile`.** Bumping one means re-checking its events parser (`OpenCodeEvents`, `ClaudeCodeEvents`, `CodexEvents`) against the CLI's real output.

## Sandboxes

SBX-001..012, TOOL-001, and every workspace tool (DB-001, SECRET-001..002, STORE-001, FLAG-001, MON-001, APPAUTH-001..002, GROW-001..003, RT-001).
One sandbox per project, on Docker locally and Runtime Cloud (or Blaxel) in production, kept up to date, checkpointed after every turn, backed up outside the provider, and suspended when idle.

### Decisions

- **One image definition** (`docker/sandbox/Dockerfile`) for every provider; nothing provider-specific in it except Blaxel's extra steps in `docker/sandbox/blaxel`.
- **No secrets in images or repos.** The user's AI credential is injected per run.
- **2026-09-28: Each sandbox is driven by the provider it was created on** (`RoutingSandboxProvider`); `SANDBOX_PROVIDER` only picks where new ones go. A project on another provider counts as outdated, so the normal update moves it.
- **2026-09-28: Updates keep all of `/home/sandbox`,** not just the agent's history, because agents install things there (a project's Postgres lived in `/home/sandbox/pgsql`).
- **2026-09-28: The old sandbox is deleted only after the new one has every kept file.** Any failure before that deletes the new one and puts the project back on the old one, unfrozen. (A queue timeout redelivering a long update job once lost a project's database.)
- **2026-10-01: Docker sandboxes copy kept files through tar, not plain `docker cp`.** Docker refuses to unpack a relative symlink that climbs out of the folder it copies into, both ways (`corepack enable` leaves `~/.local/bin/pnpm -> ../../../../usr/lib/...`), so every update of that sandbox failed and the preview sat on "Updating sandbox…". Out: `docker cp … -` unpacked by the host's tar (works on a stopped container). In: the host's tar unpacked by the new container's tar.
- **2026-09-28: Freezing for a copy always has a watchdog** that thaws the app after the longest an update may run, so a deploy that cuts an update off never leaves an app frozen.
- **2026-09-30: Build steps that run as the sandbox user set `HOME=/home/sandbox` on the step itself,** because Runtime's builder keeps `HOME=/root` after `USER` (Docker doesn't), and npx then can't write its cache. Not an image-wide `ENV HOME`, which would change the `HOME` Runtime gives sandboxes.
- **2026-10-01: Old Runtime image versions are deleted hourly and right before each `sandbox:build-image` on Runtime (`sandbox:prune-images`),** because Runtime charges $0.08/GB-month for every stored image (~4.8 GB each), caps how many an account holds (a build failed with "Image quota exceeded" at 20), and every build leaves one behind. Daily was too slow, and the prune only looked at the current name, so the 14 images from before the rename (`zap-sandbox`, plus a `zap-probe` from trying Runtime out) were never deleted, 5 of them failed builds. The GitHub `runtime image` workflow doesn't prune first, since it has no PHP app; the hourly run covers it. Kept: the current version (deleting it would also drop its build checkpoints), newer builds (a failed one holds the checkpoints its fix starts from), and any version a running, paused or stopped-persistent sandbox came from (read from its image label, `zap.image` for sandboxes made before the rename), since we don't know that a paused sandbox wakes without its image. Only the configured image's name and its former names (`RuntimeSandboxProvider::FORMER_IMAGE_NAMES`) are touched, never other images on the account; the current version is never deleted, whatever the listing says. It runs whenever `RUNTIME_API_KEY` is set, not only with `SANDBOX_PROVIDER=runtime`, because Runtime sandboxes outlive a provider switch.
- **2026-09-29: `sandbox:update` suspends each sandbox it updated,** to stay within Runtime's trial limit of 8 running sandboxes.
- **2026-10-01: While a new sandbox is made for an update, the preview shows the "Updating sandbox…" placeholder, not the app; only then, not while the update waits in the queue.** The sandbox row keeps its old preview address until the new one is up, and the old sandbox is frozen for the copy, so on servers the iframe showed the browser's "unable to connect" page. The iframe comes back (a fresh load) once the update is done. The placeholder used to show from the moment the job was queued: a 12-second swap showed it for minutes behind agent runs on the one queue, and for 15 minutes after a job that failed before it started.
- **2026-10-01: Sandboxes update once their project has gone unused for 10 minutes (`UpdateSandbox`), never when it's opened or before an agent run.** Updating on open put it on the user's time, exactly when they wanted the project. Not every sandbox after each image build, because that wakes and rebuilds dormant ones for nothing (cost, and Runtime's trial cap of 8 running); a sandbox nobody uses is updated after its next use. Not on a schedule: Laravel Cloud wakes a sleeping app for every scheduled task. Deploying to the user's own cloud is left for later; the leading option is a Publish target run by a platform queue job with credentials stored per organization, starting with Cloudflare Workers for Platforms behind the existing gateway Worker so Private/Public and the abuse check still apply.
- **2026-10-02: AWS services Lambda functions use run as free single-service stand-ins (DynamoDB Local, S3Mock, ElasticMQ), reached through the AWS SDK's standard `AWS_ENDPOINT_URL_*` settings.** LocalStack covers more but has needed an account token since March 2026 and its free plan is non-commercial, so it's only used when the user adds `LOCALSTACK_AUTH_TOKEN`. Standard endpoint settings keep the code free of local-only branches. MinIO was ruled out for S3 because it stopped publishing community images in 2025.
- **2026-10-03: The shell has the common cloud, hosting, database and infrastructure CLIs (SBX-011), installed on first use, not built into the image.** The user asked for every such tool in the shell, kept current. All 32 installed take about 5 GB (az 450 MB, gcloud 380 MB, vercel and netlify 350 MB each), and Runtime charges per stored GB for each image version and starts sandboxes from it, so only small general tools are in the image (yq, xh, uv, shellcheck, the Postgres/MySQL/Redis clients, Python, corepack's pnpm and yarn). A first use takes seconds to about a minute.
- **2026-10-03: First use is caught by a two-line stand-in per command in `/opt/onedrop/lazy`, at the end of PATH, not bash's `command_not_found_handle`.** The handler only runs in interactive bash, so the agent, scripts and Makefiles would never get the tool. Last on PATH so the app's own copy (`node_modules/.bin`, `~/.local/bin`) wins. `bashrc` adds the folder too, because SSH sessions start with sshd's PATH and sandboxes on an older image get the stand-ins (tool files) before a new image.
- **2026-10-03: Versions are pinned in `onedrop-tool`, a tool file, so a bump reaches running sandboxes without a new image or a new sandbox** (SBX-002) and installs on the tool's next use, removing the old version. Not "latest at install time": that would never update once installed, and a broken release would reach users before CI saw it.
- **2026-10-03: First-use tools install into `~/.cache/onedrop/tools`, as the sandbox user.** No root needed, and snapshots and updates skip caches, so a 5 GB toolbox isn't packed and moved with each project; a new sandbox installs them again on first use. Each install is under a lock (two Shells, or the agent and the user) and marked done only at the end, so a cut-off install is started again, not used half-finished. Downloads come over HTTPS from each project's own releases, without checksums (as for the image's tools), since Renovate can't keep a checksum per architecture current for every tool.
- **2026-10-03: Renovate keeps the sandbox's tools current: one grouped pull request a week (Monday), releases at least 3 days old.** Every version in the Dockerfile and `onedrop-tool` sits under a `# renovate:` comment. Weekly and grouped because each merged Dockerfile change moves every sandbox to a new one once it's idle; a few days' wait keeps a pulled or broken release out. Renovate, not Dependabot (which stays for GitHub Actions), because Dependabot can't read versions from `ARG` lines or a script. Renovate only reads the sandbox's two files, not the app's Composer or npm packages. It needs the Renovate GitHub app installed on the repository.
- **2026-10-03: The base images are pinned by digest, and PHP stays on 8.4.** A new digest of `php:8.4-cli-bookworm` (rebuilt for Debian security fixes) is a Renovate update like any other, which is how existing sandboxes get those fixes; a scheduled rebuild with the same Dockerfile wouldn't move them. A newer PHP minor isn't proposed, since users' apps run on it.
- **2026-10-03: The agent CLIs get their own Renovate pull request,** because the platform parses their JSON events, and each bump needs `OpenCodeEvents`, `ClaudeCodeEvents` or `CodexEvents` re-checked first. Playwright (1.63.0) isn't bumped by Renovate: `guides/tests.md` and `tests.mjs` name the same version.
- **2026-10-03: A pull request that changes the sandbox's tools builds the image and installs and runs every tool, on amd64 and arm64 (`sandbox tools` workflow),** so a release that renamed its download or no longer starts fails there, not in a user's Shell.
- **2026-10-07: The image's apt retries a stalled download (5 tries, 30-second timeout), set before its first `apt-get`.** From Oct 5 every Runtime build hung on `apt-get update`: Runtime's build proxy (`127.0.0.1:10800`) dropped Debian's package list mid-download and apt waited on the open connection until Runtime stopped the build at 30 minutes. Retrying turns a hang into a few quick tries. Not worked around by switching Debian mirrors, since the proxy sits in front of every mirror.
- **2026-10-03: `psql` and `pg_dump` come from Postgres's own apt repository (the newest major), not Debian's 15,** since `pg_dump` refuses servers newer than itself.
- **2026-10-03: App Storage's type icons come from the shared `FileIcon`, extended with media and document types** (video, audio, PDF, Word, spreadsheets, slides, AVIF/HEIC), not a separate set for App Storage, so the Files panel shows the same ones. Icons, not image thumbnails: a thumbnail is a fetch from the sandbox per row, and images already preview on click.
- **2026-10-03: App Storage has batch actions (STORE-001): select with checkboxes (Shift for a range), then download as a zip, move, copy paths or delete.** Each is one call to the sandbox's tool with a list of paths (up to 1,000), not one request per item from the browser. A move checks everything before moving anything, so a name clash or a folder moving into itself leaves the bucket as it was; it never overwrites. A batch delete skips paths that are already gone, so a folder and something inside it can be deleted together. The zip is made in the sandbox and capped at 25 MB of files, like single downloads, because it comes back through exec output; larger downloads would need signed links. Move takes a typed folder path (created if missing), not a folder-tree picker, to keep it small.
- **2026-10-03: `ask` in the shell gets the project's AI from the platform for each question (SBX-012), not from keys kept in the sandbox.** The user wanted `ask blah blah` (their own habit) and keys set up for every agent, "whatever is best, safe, and allowed". Keys written into the shell's environment were ruled out: the user's app and its dependencies, the agent, and the organization's admins (who can open any project's Shell) could all read them, and they would outlive a disconnect. Per question, the credentials exist only while it runs, and follow the project's current AI. `ask` runs OpenCode (or Claude Code on a Claude subscription) read-only, so it can look at the project but never change it.
- **2026-10-05: AI credits and subscriptions only reach `ask`, never pi, fx or the Gemini CLI.** Credits are charged around the platform's own runs (after each, and again before the next), and those agents would spend from the organization's key outside them, with no run, usage row or picker to show it (credits now allow any OpenRouter model, so that was the earlier reason, not this one); a Claude subscription may only be used by Claude Code (Anthropic's terms), and a ChatGPT sign-in is OpenCode's. Those agents use their own logins instead (`fx login`, pi's `/login`, `gemini`), which is the person's own explicit choice. They install on first use (SBX-011), since most projects never run them.

### Decisions

- **2026-10-02: Credits are kept in Autumn, in cents of AI usage at provider rates, with no markup.** The catalog is code (`autumn/autumn.config.ts`, pushed with `npm run atmn push`): a credit system `ai_credits` (1 credit = 1 cent) fed by the metered `ai_usage`, and a Free plan every new customer gets: 500 credits once, plus 100 a month that reset and are used first. OpenCode only: Claude Code and Codex need their own providers' accounts.

It first showed only while a project ran on credits, and the user, whose projects start on their own Claude, couldn't find it; credits are also a choice there, so the balance belongs beside it either way. The Usage card (both the user's page and the organization's) loads deferred, so a slow Autumn never holds up the page.

## Previews, publishing and sharing

PUB-001..003, GW-001..002, REM-001, SHARE-001..002, HOME-002.
Every app is reachable while it's built; publish to Tailscale or to the server's own domain, Private or Public; share a project on a public page with a preview card and Remix.

### Decisions

- **Every path to a sandbox goes through the platform's auth check** (`SandboxGatewayController`). Never hand out a provider's own preview URL.
- **2026-09-29: On Laravel Cloud, previews and shells go through a Cloudflare Worker** on `*.<domain>`, because Blaxel's and Runtime's preview cookies don't work inside OneDrop's frame (Runtime didn't load at all; Blaxel lost CSS/JS in Safari). The browser only ever sees OneDrop addresses and cookies.
- **2026-10-02: The Cloudflare Worker tells the sandbox's proxy which address the browser used (`X-OneDrop-Host`, always set by the Worker, stripped by Caddy), and the proxy uses it instead of Host to localize Origin/Referer and as the app's `X-Forwarded-Host`.** The Worker fetches the provider's address, so Host there is the provider's: the proxy didn't see the page's own Origin as same-site and passed `https://preview-25.onedrop.io` on unchanged, and Plausible's LiveView (Phoenix `check_origin`, against `BASE_URL=http://localhost:8000`) refused every WebSocket. A custom header, not `X-Forwarded-Host`, because providers' proxies may set that themselves; `X-OneDrop-Geo-*` already proved custom headers get through. Rejected: setting each app's base URL to the preview address, since templates are set up for localhost on purpose (the proxy maps it) and the address changes when the app is published.
- **2026-10-05: Locally (Docker), the preview's host defaults to `APP_URL`'s host when that's `localhost` or `127.0.0.1`, else `127.0.0.1`; `SANDBOX_DOCKER_HOST` overrides it.** Browsers treat `localhost` and `127.0.0.1` as different sites, so with OneDrop on `localhost:8000` and the preview on `127.0.0.1:<port>` the framed app lost its cookies: a Pixwel app found no login token and showed `no-token` only in the Preview. Rejected: switching the fixed default to `localhost`, which breaks anyone browsing on `127.0.0.1` instead (and may try `::1` first while Docker publishes on IPv4 only); and following any `APP_URL` host such as `zap.test`, usually https there, where an http preview is blocked as mixed content (loopback addresses are exempt).
- **2026-09-30: Publish targets: Your domain or Tailscale,** remembered per project. Private on your domain means anyone in the project's organization (ORG-007), not only the project's people. A project named like a preview address gets an `app-` prefix so it can't take one over.
- **2026-09-30: Tailscale publishing checks the node's capabilities (`https`, and `funnel` for Public) before running `tailscale serve`/`funnel`, and waits for them.** With Funnel off, `tailscale funnel` prints an enable link and blocks until someone turns it on; our timeout killed the job and left the project "Publishing…" forever while the command kept waiting in the container (so the URL later worked but the panel never updated). Now the panel links to the setting and publishing carries on once it's on. Both publishing jobs also mark the project Failed if they crash.
- **2026-10-03: A ConfirmPublication job that crashes checks again (next attempt) while attempts are left; only the last one marks the project Failed.** The endpoint carries on without the job: a SQLite lock stopped the worker picking up one check, which marked a Fly deploy Failed while it went on to build and start the app. Locally, SQLite also waits up to 10 s for a lock (`DB_BUSY_TIMEOUT`) in WAL mode (`DB_JOURNAL_MODE`) instead of erroring at once, since `composer run dev` runs several queue workers against one file.
- **2026-10-03: While publishing, the header's Publish button spins and says Publishing….** The user lost track of a long Hosting deploy with the panel closed: the button looked idle.
- **2026-09-29: Share cards are rendered in the sandbox** with headless Chromium (1200×630, prompt beside the app).
- **2026-09-30: On the hosted install, Jev checks an app for abuse before it's published as Public or after it's shared (PUB-003).** Anyone can sign up there and put an app on a public address or a OneDrop share page, so phishing pages, scams and malware are the platform's problem. Private publishing isn't checked (only the organization or the tailnet can open it), and self-hosted installs aren't (the owner runs the server).
- **2026-09-30: The abuse check uses the platform's OpenRouter key (`Jev::platformKey()`), never the owner's; without one there's no check.** It's the platform's protection, so the owner shouldn't pay for it, and an abuser could otherwise skip it by connecting a key that fails.
- **2026-09-30: Jev never blocks anything by itself: above 0.8 on any question (phishing, scam or malware, otherwise harmful) the publish or share is held for a platform admin, who approves it or takes it down.** One probabilistic answer isn't enough to refuse someone; a person decides. 0.8 was tuned live: a PayPal copy (0.99), a "Chase" login (0.92), an ETH giveaway (0.99), a cracked-download page (0.97) and a doxxing page (0.98) were over it; a todo app, a SaaS's own sign-in, an Instagram clone (0.35), a Netflix clone (0.30), a bakery with checkout and a crypto tracker were well under it.
- **2026-09-30: The abuse check fails open: if Jev errors or times out (15 s), the app publishes as normal and the exception is reported.** Jev being down shouldn't stop every publish on the hosted install; the daily re-check catches it later. Rejected: failing closed, which would turn every Jev outage into a publishing outage for everyone.
- **2026-09-30: The publish check runs inside the queued PublishProject job, before the endpoint starts; the share check is its own queued job (CheckForAbuse) after the share is saved.** Publishing is already asynchronous, so the check adds no request latency (the panel just says Publishing… a few seconds longer). The share page is visible for those few seconds; its slug is unguessable and only the owner has the link yet, so hiding it until the check ends wasn't worth the extra state.
- **2026-09-30: Jev sees the project's name, its first 2 and latest 8 prompts (500 characters each), and the home page as headless Chromium renders it (falling back to curl): title, visible text (3,000 characters), up to 30 form fields and up to 10 form targets.** Most apps render client-side, so the raw HTML is often empty; form targets show where credentials would go. Chromium is already in the sandbox image (share cards), so no image change. Only a held check keeps that evidence (for the admin); a clear one keeps just the probabilities.
- **2026-09-30: A held app is offline for the public, not deleted:** its publish status becomes `review` (the Tailscale/Funnel endpoint is stopped) and its share page is a 404. Approving republishes it; publishing publicly again while held stays held without another Jev call.
- **2026-09-30: An approval stands until the owner sends the agent another message; after that, the next public publish or share is checked again.** Admins shouldn't have to re-approve the same app, but an approved app the agent then changes is a new app.
- **2026-09-30: Public or shared apps are re-checked after a successful main-chat agent turn, at most once a day per project** (cache key, 20 s after the turn). Cheap enough to run for every public app, and catches an app that turns into phishing after it was published. Task turns aren't re-checked separately; applying a task's work to main doesn't run the check (noted, not built).

## Hosting

HOST-001..010, ADMIN-007. Published apps can run for good off their sandbox: a front end on Cloudflare, an app with a server on a Fly.io machine, its data in managed services (Neon, Upstash, R2) or on a Fly volume, in the install's accounts or the organization's own. Building stays in the sandbox and costs nothing outside it.

### Decisions

- **2026-10-03: Nothing is made at a hosting provider while an app is built; only publishing to Hosting makes what it needs.** Building happens in the sandbox with local services, so an app that's never published costs nothing outside it.
- **2026-10-03: A managed service where there is one, a Fly volume for everything else.** Postgres goes to Neon, Redis to Upstash and S3 files to R2, so their backups and durability are the provider's problem; data with no managed service (SQLite, App Storage folders, Mongo or anything else kept on disk) goes on a volume, so every app can be hosted, not only ones rewritten for managed services. A typical Postgres app has no volume and its machine is disposable. Volumes are snapshotted daily by Fly (kept 14 days), and SQLite databases are also backed up continuously with Litestream (HOST-008). App Storage stays folders (on the volume when hosted): moving it to S3 would change its panel, guide and every app using it.
- **2026-10-03: Front ends go to Cloudflare Workers static assets; apps with a server to Fly.io Machines.** A front end needs no server: free, worldwide and nothing to crash. Fly runs any server, from a few dollars a month always on to nearly nothing when it sleeps. Hetzner boxes with Docker Compose (Kamal, Coolify) are cheaper per app but mean running servers ourselves, so they'd be a later provider. Apps that only run under their own Docker Compose aren't hostable yet.
- **2026-10-03: The agent describes the app in `.onedrop/host.json` (static folder, services, data paths), with `.onedrop/build` and `.onedrop/start` beside `.onedrop/dev`.** The agent already owns `.onedrop/dev`, and only it knows whether the app is a front end and what it stores where.
- **2026-10-03: Without host.json, a plain Vite app (a `build` script, `vite`, a root `index.html`, no server framework, database driver or server file, no `.onedrop/start`) is deployed as a front end from Vite's `outDir` (`dist`), built with its package manager's `build` script; anything else is an app with a server, keeping `.onedrop/data` and Laravel's SQLite file.** A Vite counter whose agent never wrote host.json was sent to Fly running Vite's dev server, and never started. A front end needs no server and nothing CPU-specific. An explicit host.json always wins, and the log says when it was guessed.
- **2026-10-03: The builder installs the release's packages again (from each lockfile: npm, pnpm, yarn or bun) when the sandbox that packed it has another CPU than Fly's x86_64 machines.** Local Docker on a Mac is arm64, so native packages (Vite's rolldown, esbuild, sharp, SWC) had only arm64 binaries and the hosted app couldn't load them. The builder runs the same base image on the target CPU, so installs (and native builds) come out right with no cross-compiling. Rejected: `npm ci --cpu=x64` in the sandbox (npm only, and packages compiled in their install scripts would still be arm64); installing at every boot (slow, and on every restart).
- **2026-10-03: A hosted app that stops three times within 30 s of starting answers 503 with `X-OneDrop-App: crashed` and its last 40 lines of output for a minute, then is tried again; the deploy fails on that answer at once (putting the last good version back) and adds the output to its log.** The deploy otherwise waited its full 5 minutes for an app that had crashed on its first second, then said only "didn't start". `hosting app` serves it on `$PORT`, so it needs no change to the base image's proxy; a minute, then a retry, so a crash at boot from a briefly missing service doesn't keep a live app down.
- **2026-10-03: The hosted app reads its services from the same environment variables as in the sandbox** (`DATABASE_URL`, `DB_CONNECTION`/`DB_URL` for Laravel, `REDIS_URL`, `AWS_*`); in the sandbox its `.env` points them at local services. Real environment variables win over `.env` in Laravel and dotenv, so the same code runs in both with no hosting-only branch. Not a platform-run Postgres/Redis/S3 in every sandbox: agents already run what the app needs from `.onedrop/dev`.
- **2026-10-03: A hosted app runs the sandbox's own image with the project's files added as one layer, pushed to Fly's registry by a short-lived builder machine in the app's own Fly account using crane.** It runs exactly as in the preview (same runtimes, same proxy rewriting localhost links), with no Dockerfile per app and no Docker daemon. The builder, not the sandbox or Laravel, holds the Fly token: no secrets in sandboxes, and no long-running pushes in the app's queue. The image runs as root only to put the volume's data in place, then starts the app as the sandbox user. The sandbox uploads the release through signed links, as snapshots do. Rejected: machines downloading the release at each boot (a signed link expires, and a restart would then fail).
- **2026-10-03: Releases wait on the snapshot disk when it's S3-compatible, otherwise in a `onedrop-releases` R2 bucket made once per Cloudflare account, with a key for that bucket only (kept encrypted in the `hosting_releases` setting).** Fly has to download the release, and a local install's snapshot disk is the laptop's own; the user hit that right after setting up Fly and Cloudflare. Cloudflare is already a hosting provider, so this needs no new setting. Rejected: requiring an S3 `SANDBOX_SNAPSHOT_DISK` just for hosting. A new bucket key is tried (up to 90 seconds) before any link is signed with it: the first real deploy failed with a 401 because Cloudflare hadn't activated the key 20 seconds after making it.
- **2026-10-03: Hosted apps are public only for now.** Private would need a OneDrop sign-in in front of a fly.dev or workers.dev address; Your domain and Tailscale already do private.
- **2026-10-03: One provider per role (servers, volumes, front ends, buckets, Postgres, Redis), set up in Settings → Hosting, not an ordered list like sandbox providers.** There's only one candidate for each role today; an order is easy to add when a second host comes. Each provider is its own API class (FlyApi, NeonApi, UpstashApi, CloudflareApi), tested against faked HTTP responses written from their docs.
- **2026-10-03: Organizations can use OneDrop's hosting accounts or connect their own, per provider (HOST-003).** The user wanted both: their own account bills them directly with no limits from us; ours is simpler. On a self-hosted install "OneDrop's" means the install admin's accounts. Something stays in the account it was made in, and an account can't be disconnected while its apps have something there, since OneDrop couldn't manage or delete it any more. How much hosting each paid plan includes on our accounts is decided with paid plans (hosting never uses AI credits).
- **2026-10-04: Hosting providers show their logo, a one-colour Simple Icons mark in `/images/logos` on a tile in the brand's colours, in Settings → Organization and Admin → Hosting (HOST-003).** The user asked for logos on the hosting options. Same look as the AI provider tiles (a CSS mask, so one SVG per provider); Neon and Upstash keep their green mark on black, since white on their bright green was hard to read.
- **2026-10-03: Sandbox data is copied once, on the deploy that makes the volume or the Postgres; later deploys ship code only.** After going live the hosted data is the real data, and overwriting it with the sandbox's test data would lose users' work. The volume's copy is unpacked by the app's first boot from a signed link (a day long); Postgres is restored by the builder. Redis is a cache, so it isn't copied.
- **2026-10-03: A release that never answers puts the previous image back.** "A failed deploy leaves the last good version running"; earlier failures never touch the running machine.
- **2026-10-03: Hosted apps scale to zero: the Fly machine suspends when idle (`autostop: suspend`, `min_machines_running: 0`) and wakes on the next request, and Neon databases keep Neon's default sleep.** The user saw the first hosted app running around the clock and chose scale to zero: an always-on 1 GB machine is about $5–6 a month per app, an idle suspended one nearly nothing (the volume is billed either way). Suspend, not stop: Fly keeps the machine's memory and resumes it in well under a second, where a stop would reboot the large sandbox image and Laravel. Fly stops a machine it can't suspend. A deploy checks the app by asking it, which wakes it, so a release that fell asleep isn't taken for a failure. Replaces "Neon's scale-to-zero is turned off where the plan allows" and the hosted half of "published apps never pause" (apps published from the sandbox still never pause).
- **2026-10-03: Publishing to hosting stays manual, with the changes since the live deploy shown (a dot on Publish, the commit messages, an Update button), rollback to an earlier deploy, and opt-in auto-deploy (HOST-004..006).** The agent often spreads one change over several turns, and every deploy runs the app's migrations against real data, so redeploying on every change would ship half-finished work with no review. Changes come from the workspace's git (each deploy records the commit it shipped; `git log` since it, read after each turn's backup), since the platform already commits after every turn.
- **2026-10-03: Rollback restarts the machine on the earlier deploy's image, without building again, and leaves the data as it is now.** Each deploy's image is kept in Fly's registry, so going back is a machine update. Front ends have no images to go back to, so they can't roll back yet. Data isn't rolled back: a migration the newer version ran stays, which the confirmation says.
- **2026-10-03: Auto-deploy is off by default and waits a minute after a turn, then only goes ahead when the agent is done (not waiting on the user, not working again, no newer message), the preview showed no new errors since the turn, nothing is deploying, and there are changes.** A minute lets the preview check and the backup that reads the changes go first; an error the autofix sends back starts a new turn, which cancels this one. The app's own tests aren't run first: they can take minutes and not every app has them.
- **2026-10-03: Customers see their hosted data in Tools → Database (a Sandbox / Hosted switch) and can download a SQLite copy, rather than connecting to the database themselves (HOST-007).** SQLite has no network port, and handing out access to OneDrop's Fly account isn't an option; this works the same on OneDrop's accounts and the organization's own. The same db.php runs on the hosted machine through Fly's exec API, woken first, as the sandbox user so SQLite's journal files stay the app's, with the hosted services' addresses passed in the command (exec doesn't promise the machine's environment). Each release carries its own db.php (`/opt/onedrop-hosting/db.php`) so it doesn't depend on the published base image's copy. Downloads are `VACUUM INTO` copies (consistent while the app writes) uploaded to release storage through a signed link and deleted an hour later. Writes to the hosted database are confirmed. Organizations with their own Fly account can still use `fly ssh` themselves.
- **2026-10-03: SQLite on a hosted volume is backed up continuously with Litestream to its own R2 bucket, by default (HOST-008).** A volume lives on one host: with only Fly's daily snapshots, losing it lost up to a day. Litestream ships each change within about a second and restores the databases onto a new volume before the sandbox's first-deploy copy (which then only fills gaps, `tar --skip-old-files`). The databases to replicate are the SQLite files `hosting inspect` finds in the data paths when packing, passed in `ONEDROP_SQLITE`, so a fresh volume knows what to restore. Litestream is fetched on first boot (pinned, `hosting.litestream_version`) and cached on the volume rather than baked into the sandbox image, and the app still starts if it can't be fetched. It's skipped, with a note in the log, when there's no Cloudflare account. Tested against an S3 stand-in (adobe/s3mock) in Docker; MinIO's images weren't pullable.
- **2026-10-03: Redundancy and worldwide speed by default stop at durability for now.** Litestream makes SQLite data safe; front ends are already served from Cloudflare's edge. A server app still runs in one region on one machine: SQLite can't be shared across machines, LiteFS is no longer actively developed and Turso needs code changes, and multi-region Postgres means read replicas plus machines per region. Those come as a per-app upgrade (Move to Postgres, machine size) rather than a default every app pays for.
- **2026-10-03: Every app stays on SQLite; an app that needs to scale moves to Postgres on Neon (Move to Postgres), not Turso.** The user's call. Turso (libSQL, open source, with a hosted service and embedded replicas) keeps SQLite's dialect and would make reads fast anywhere, but our default stack is Laravel and its PHP drivers are community packages over an extension or FFI, while Postgres is first-class in Laravel and Neon is already a provider.
- **2026-10-03: Move to Postgres copies the hosted SQLite data into tables the app's own migrations make, on the hosted machine before the app starts, once (HOST-009).** The schema comes from the app (`.onedrop/migrate`, e.g. `php artisan migrate --force`), so Postgres gets the types its framework expects (Laravel's booleans, timestamps), and `pg-import.php` only copies rows, converting values by the Postgres column type (0/1 into booleans, Unix times into timestamps, blobs into bytea), in foreign-key order, in one transaction, with sequences moved past the copied ids; Laravel's `migrations` table is left as migrate made it. It refuses if a SQLite table or column has nowhere to go, rather than silently dropping data. Rejected: pgloader (not in the image, and it would make its own schema that Laravel's migrations then disagree with) and the builder machine (it can't mount the volume the data is on). The sandbox stays on SQLite (it has no Postgres server) and the hosted app gets Postgres through its environment; a failed move puts the SQLite version back with the Postgres variables taken out of its environment. A marker on the volume (`.onedrop-moved-to-postgres`) keeps a restart from copying again.
- **2026-10-03: Machine size is four fixed sizes per app (Small, Medium, Large, Extra large), and changing it restarts the live image on the new size rather than building again (HOST-010).** Most apps that outgrow Small need a bigger machine, not more of them. Fixed sizes keep the choice simple and within what Fly offers (performance CPUs need at least 2 GB per CPU); Small keeps the install's memory setting. Fly only suspends machines up to 2 GB, so Large and Extra large stop when idle and wake a few seconds slower, which the panel says. One machine per app still: more than one needs Postgres (Move to Postgres) and is left for later.
- **2026-10-03: The Publish menu only holds what's needed to publish; managing a hosted app is in Tools → Publishing.** With deploy history, auto-update, services, machine size and Move to Postgres added, the dropdown ran off the screen. The menu keeps the status, target, visibility, the changes since publishing, the latest deploy's log and a Manage hosting link, and scrolls within the window if it still doesn't fit.
- **2026-10-03: No hosted Elasticsearch** (about $95 a month a cluster): agents are steered to Postgres full-text search, Meilisearch or Typesense, and anything else runs from the volume.

## Custom domains

DOM-001..004. A published app can be served at domains its owner already has, with HTTPS, on Your domain and on Hosting.

### Decisions

- **2026-10-03: Custom domains work on every public target: Your domain (Caddy on a server, the Cloudflare Worker on Laravel Cloud) and Hosting (Fly.io, Cloudflare front ends). Tailscale can't have one.** The user's call. Each target uses its own provider's way, not one proxy for all: the server's Caddy issues certificates on demand, the Worker's zone uses Cloudflare for SaaS custom hostnames, Fly apps get Fly certificates, and front ends get Workers custom domains. Rejected: sending every domain through the gateway and proxying to hosted apps, since a hosted app would then depend on the OneDrop server staying up, and a laptop install with Hosting has no gateway at all.
- **2026-10-03: Connect only, no buying domains.** The user's call: buying means a registrar, billing and renewals; users point a domain they already have.
- **2026-10-03: Several domains per project, one primary; on Your domain the others and the project's own address redirect to it.** The user's call, so `example.com` and `www.example.com` can both work. The primary becomes `published_url` (shown everywhere, used for sign-in callbacks); the target's own address is kept in `published_default_url` so it can come back. On Hosting there's nothing in front of the app to redirect, so every domain serves it.
- **2026-10-03: Private apps on a custom domain keep OneDrop sign-in, through the same hand-off as the project's own address (a short-lived token traded for a cookie for that host only).** The user's call. No new mechanism: the gateway already never shares the app's login cookie with app addresses.
- **2026-10-03: Pointing DNS at us is the proof of ownership; no TXT record.** A certificate only issues when the domain resolves to the server (Caddy), Cloudflare (SaaS, Workers) or Fly, so whoever controls DNS decides. A hostname belongs to one project on the install, first come.
- **2026-10-03: Front ends on Hosting need the domain's DNS in the same Cloudflare account as the site.** Workers custom domains only work on zones in that account; anything else needs Cloudflare for SaaS in the hosting account, which isn't worth it yet. With the install's account, the panel says so.
- **2026-10-03: Waiting domains are checked by a self-rescheduling job (every 30 s for 10 minutes, then every 5 minutes for two days), not a scheduled command.** Laravel Cloud wakes the app for every scheduled run, so a per-minute check would keep it awake for good (as noted in routes/console.php). Active domains aren't re-checked; Check now is there when DNS moves.
- **2026-10-03: Caddy only gets certificates for hostnames a project has added.** Its on-demand `ask` approves them, so an attacker pointing random names at the server can't run up Let's Encrypt's rate limits.

## Git

GIT-001..012.
History, commit/discard, branches, restore, push/pull, the GitHub App, commit and push from the header, pull requests, combining commits, hunk/line staging, undoing the last commit, asking the agent about a change, and readable diffs.

### Decisions

- **2026-09-29: Remotes are HTTPS only;** the local bundle steps (git's `file` transport) are exempt.
- **2026-09-30: Commit, push and Create PR live in a split button next to Share,** so the everyday steps don't need Tools → Git. With no remote it says "Commit" and its menu offers "Connect a repository…" (opening Tools → Git).
- **2026-09-30: There is one commit dialog,** "Commit changes", used by the header and by Tools → Git (which lost its inline message box), so reviewing and committing work the same everywhere.
- **2026-09-30: The commit message is optional; left blank, the project's own AI writes it** (the same one-off run as project naming), falling back to naming the files. Pull request text and combined-commit messages work the same way. The AI never blocks the action: every AI-written text has a plain fallback.
- **2026-09-30: "Default branch" means `main` or `master`,** a guess: the sandbox doesn't know the remote's real default. Pull requests go into it by default.
- **2026-09-30: Parts of files are picked at commit time; there's no lasting staging area.** The agent's checkpoint adds everything after every turn, so anything staged by hand would be swept into its next commit. Picking rebuilds the index from the last commit for each commit.
- **2026-09-30: The browser sends which lines to leave out plus a hash of the diff it showed, never patch text;** the sandbox rebuilds the patch and refuses ("This file changed. Review it again.") when the hash doesn't match, so a commit is always what the user saw. Only edited or new text files can be split; deleted, renamed and binary files go whole. Discarding a hunk is for edited files only.
- **2026-09-30: Sandboxes on an older git tool fall back quietly:** without line counts the Edit button is hidden (an old tool would commit every file), and without a diff hash parts can't be picked or discarded.
- **2026-09-30: Pull requests open GitHub's own new pull request page with the title and description in the link,** rather than being created through the API: it works for token and GitHub App remotes alike without asking for pull request permissions, and the user finishes on GitHub. Create PR says why it isn't available instead of hiding.
- **2026-09-30: Combining and undoing only touch commits no remote branch has,** so pushing never needs to overwrite (force-push) the remote. Combining refuses merges and uncommitted changes; undo refuses the first commit and merges, and checks the newest commit is still the one shown.
- **2026-09-30: "Ask" puts the hunk in the chat box and doesn't send it,** so the user writes the question; the dialog closes and the chat box keeps the focus.
- **2026-09-30: Diffs are colored with the CodeMirror grammars the chat already uses,** no new dependency. Changed words are found by comparing a removed line with the added line paired with it (common start and end, by whole words). Hiding whitespace is done in the browser, so picking and discarding wait until whitespace is shown again (the lines must match what the sandbox sees).

## Agent skills

SKILL-001..004. Reusable instructions for the agent in the open Agent Skills format (a folder with a `SKILL.md`). Two kinds: a user's own skills, kept by the app and turned on per project, and project skills committed in the repo.

### Decisions

- **2026-09-30: Both a library and project skills,** because a team wants the same skill across projects (library) and a skill that travels with one repo (project). Library skills live in the app's database, never in the repo.
- **2026-09-30: Sharing is all or nothing: private, or everyone in the skill's organization (ORG-007).** No per-group or per-person picker for now. Only the owner (or an admin) edits a shared skill. Stopping sharing turns it off in other people's projects, so nobody keeps running a skill they can't see anymore.
- **2026-09-30: Add menu: write one, create with agent, import from GitHub, upload.** Writing, importing and uploading add to the user's skills and turn it on in the current project. "Create with agent" writes a project skill in `.agents/skills` (following `guides/skills.md`), because the agent works on the repo; "Save to your skills" copies it into the library.
- **2026-09-30: The app puts skills in place before each run** (`SandboxSkills`, `docker/sandbox/skills.php`): library skills go to `~/.claude/skills` for Claude Code and `~/.agents/skills` for OpenCode and Codex. The bundle is only uploaded when it changed (the sandbox keeps a hash), so an unchanged run costs one exec. Only one of the two folders is filled at a time, because OpenCode reads both and would see every skill twice.
- **2026-09-30: Every agent sees every project skill.** Claude Code only reads `.claude/skills` and Codex only `.agents/skills`, so project skills from the other folders are copied into the agent's home skills folder. New project skills go in `.agents/skills`, the open standard's folder.
- **2026-09-30: The sandbox tracks what it installed** (`~/.onedrop/skills/installed.json`) and only removes those, so skills a user put in `~/.claude/skills` by hand are left alone, and win over one of ours with the same name.
- **2026-09-30: A project skill wins over a library skill with the same name,** and two library skills with one name can't both be on in a project. Agents need unique names.
- **2026-09-30: Skill problems never stop a run.** A missing or old `skills.php` (an older image) is skipped quietly, and the run goes on without skills.
- **2026-09-30: The Requirements switch (REQ-002) sits in a "Built-in" card at the top of Agent Skills,** because it changes how the agent works the way a skill does. It's a project setting, not a skill in the library.
- **2026-09-30: At most 50 files and 1 MB per skill,** stored in the database (files base64 in JSON), so no extra disk and skills come back with a database backup.
- **2026-09-30: Saving a project skill to the library skips symlinks,** so a shared skill can't pull in files from outside its folder.
- **2026-09-30: SKILL.md's frontmatter is read by a small parser,** not symfony/yaml, because that's only a dev dependency here. Editing a skill rewrites only `name` and `description` and keeps its other keys (license, allowed-tools, ...).

## Requirements tracking

REQ-001..003, TEST-001..008. The agent in a user's app keeps that app's requirements the way this repo keeps its own: what the user asked for ("User should be able to…" with IDs) and every decision behind it, with the reason, and backs each with browser tests it runs as it works. The user reads the requirements in a Requirements tab to check the agent understood, and watches the tests' recordings in a Tests tab; the agent reads them so it doesn't undo an earlier choice.

### Decisions

- **2026-09-30: One file, `.onedrop/REQ.md`, holding both the stories and the decisions.** This repo splits them into `SPEC.md` and `REQ.md`, but for a non-developer one page per area (its stories, then its decisions) is easier to read and review. It lives in `.onedrop/`, the platform's folder, so an app that has its own `REQ.md` or `SPEC.md` never gets it overwritten; it's still committed and backed up with the app.
- **2026-09-30: On by default for every project, existing ones included,** with a switch in the Requirements tab and in Tools → Agent Skills. Turning it off only stops the agent adding to it; the file stays.
- **2026-09-30: Delivered as extra instructions, not as a skill.** The forwarder appends `guides/requirements.md` to the agent's instructions when `APP_REQUIREMENTS=1` (a copy of `opencode.json` listing it, for OpenCode), so every run follows it. A skill is only loaded when the agent decides it's relevant, and this has to happen on every change. The switch is shown among the skills because that's where users look for how the agent behaves.
- **2026-09-30: The agent writes it in the same turn as the change, in the user's words,** and skips questions and changes that don't touch what the app does. For an app that already exists it only records requests from now on; it doesn't invent history.
- **2026-09-30: The tab reads Main's sandbox** (like Files); tasks write to their own copy and their additions arrive with Apply to Main.
- **2026-09-30: Playwright Test for every stack, not Pest's browser plugin for Laravel apps,** so there's one format to run, parse and record, with video and traces built in. Tests live in `tests/e2e` and are committed with the app.
- **2026-09-30: The platform's own Playwright config runs them** (`docker/sandbox/playwright.config.mjs`), not the app's: the preview's dev server as `baseURL`, one worker (the tests share the app's one database), a video and a trace of every test, and the image's Debian Chromium, so no browser download. Only Playwright's ffmpeg (for video) is needed; the image has the pinned version's (1.63.0, which the guide tells the agent to install), and an app on another version fetches its own once.
- **2026-09-30: Tests are linked to requirements by Playwright tags** (`{ tag: '@REQ-001' }`, or `@REQ-001` in the title). A test can check several; untagged ones are listed under "Not linked". The Requirements tab badges each `REQ-NNN` heading, and the Tests tab names each group from REQ.md.
- **2026-09-30: The agent runs the tests of what it touched before finishing (`/opt/onedrop/run-tests @REQ-003`), and the user can run all, a requirement's, or one from the tab.** Runs from the tab happen in the sandbox in the background (`tests.mjs run --background`) and the tab polls a state file, so Laravel never waits on a run. One run at a time.
- **2026-09-30: Only each test's latest result and recording is kept,** in `.onedrop/tests` (excluded from git by the checkpoint), each run in its own folder so running one test keeps the others' videos; folders no result points to are deleted. Videos are fetched whole into the browser so they can be scrubbed through.
- **2026-09-30: Tests are a required step of the requirements checklist, not a separate guide the agent may skip, on every stack and from the turn that first builds the app.** In the first version the agent kept REQ.md on every turn but wrote no tests for a small change ("+5 button"), and requirements from before tests existed never got any. Later, Claude Code built a plain Vite counter and skipped both REQ.md and tests because the app was "not the Laravel starter" and "minimal". Both guides now say a turn that changes the app isn't done until its requirements have passing tests, that this holds for any stack and however small the app, that the first request is the first requirement, and to backfill tests for requirements without them. The Tests tab also lists requirements without tests with a "Write them with agent" button, like Feature Flags' agent actions.
- **2026-09-30: Watching and interacting with tests is Playwright's own UI mode, opened in its own window.** It already shows each step's DOM snapshot, timings, source, console and network, picks locators, and reruns on file changes (watch mode), so no custom live viewer. Its own window because there's more room, and because an iframe couldn't carry its cookie across hosts over local http. Not a headed browser over VNC: heavier (a display server per sandbox) for little more than UI mode's snapshots give.
- **2026-09-30: The runner goes through the preview's host proxy under `/__onedrop/tests-ui/`, not a new port,** so every provider and the server gateway work unchanged. It's guarded by a random token per runner, handed out by the app only to people who can change the project and traded for an HttpOnly cookie scoped to that path, and it's never served on a published address. Relying on the preview hostname alone wasn't enough: Blaxel and Runtime preview URLs are public, and the runner can run code. Its port is reserved so `routes.json` can't expose it.
- **2026-09-30: The runner stops after 30 minutes unused** (the proxy notes every request and open socket), so a forgotten window doesn't hold a Node process and browsers in the sandbox. Runs made in it don't update the Tests tab's results, which come from the tab's and the agent's runs.
- **2026-09-30: Taking over a test's page means a live browser streamed into the workspace, starting from a step of an existing test.** The user chose exact state (open dialogs, form input) over handing the page to the Preview with only its cookies and address, and steps of a test over scenarios written from chat. The stream is the debugging protocol's screencast, and input goes back the same way, so no display server.
- **2026-09-30: A taken-over test can carry on (TEST-006): one more step, or to its end,** by waking its worker (SIGCONT) after writing how far to go to a control file the preload reads on waking; it pauses again after the step, or at its end before the teardown that would close the page. Resumed steps wait 500 ms each (the worker blocks with `Atomics.wait`, the browser carries on), since steps run too fast to follow otherwise; not Playwright's `slowMo`, which would also slow the run up to the step and can't change mid-run. A failing step is reported with Playwright's own message, and the page stays open.
- **2026-09-30: Tests run in the Browser tab have no timeout.** Their timeout's clock runs on wall time, so a test paused for longer than 30 seconds would time out the moment it resumed.
- **2026-09-30: A test stops at its step by freezing its worker (SIGSTOP) from inside it,** in a preload (`test-steps.mjs`) that watches the step reports a worker sends just before each step. That's the only point before the next action reaches the browser; patching Playwright's internals isn't possible in 1.63 (it's one bundle), and stopping from the runner's reporter would be too late. The browser is its own process and keeps the page. The same preload records every test's steps during normal runs, for the step list.
- **2026-09-30: The Browser tab is a viewer served from the sandbox under `/__onedrop/browser/`,** in an iframe with its token in the address (every request and its socket are checked), because a cookie from the preview's address isn't sent inside the workspace's iframe. Never on a published address. It was going to be `/__onedrop/live/`, but that path belongs to live reload (LIVE-002).
- **2026-09-30: Each take-over's browser gets the first free debugging port of 9224–9233,** all reserved from `routes.json`, so one left over from a crashed session is never the one attached to. One take-over at a time per sandbox; a new one replaces it.
- **2026-09-30: While a take-over is open the agent's prompt says which test and step it came from, and how to look** (`/opt/onedrop/browser screenshot`). The note is kept in the cache for an hour (the browser closes itself after 30 minutes unwatched), so no migration.
- **2026-09-30: The platform checks each turn with Jev (TEST-007), because guide wording alone kept failing.** Twice the agent talked itself out of the requirements step ("+5 button" was too small; a plain Vite counter was "not the Laravel starter"). Jev, TypeSafe's decision model on OpenRouter, answers typed yes/no questions with a probability, so the platform can decide cheaply and reliably without parsing a chat model's text. It sees the request, the agent's actions and reply, REQ.md and the test list; whether REQ.md exists and which requirements lack tests are worked out without it. Not the project's own AI through `OneOffPrompt`: that's a full agent run in the sandbox and its answer would need parsing.
- **2026-09-30: Jev is asked with the project owner's OpenRouter key, else the platform's `OPENROUTER_API_KEY`, else not at all.** The owner's key keeps the cost on their account when they have one; the platform's makes it work for everyone else; with neither, the turn just isn't checked rather than failing.
- **2026-09-30: One follow-up per turn, sent like Autofix's (ERR-001), and the turn it starts isn't checked.** It runs after the preview check (12 s vs 8 s), and only one of them asks the agent for a turn: whichever sends first makes the other see a newer turn and stop. It asks only when Jev is at least 60% sure the turn changed the app, so questions and refactors don't get nagged. Main chat only for now, like Autofix.
- **2026-09-30: The requirements switch covers tests too.** Tests exist to back the requirements, so one switch; turning it off saves the time a turn spends writing and running tests.
- **2026-09-30: Jev guesses why each failing test failed (TEST-008): the app broke, the test is out of date, or flaky/timing.** One choice question per failing test, in one request (at most 8; the rest go in the next), seeing the test's title, error, steps run and its own source lines (from its line to the next `test(`, read once per file), plus the last five user requests and the agent's last 40 actions, which is what tells "out of date" from "broke". Not `git diff`: the workspace isn't always a repo and the requests say what changed on purpose more cheaply. The label only shows when Jev's top choice is at least 50% likely.
- **2026-09-30: Test verdicts are worked out lazily, once per result, in a queued job.** The status endpoint only reads verdicts kept in the cache (by project, test id and the result's `ran_at`, for 30 days) and, for failures without one, dispatches `TriageFailingTests` behind a per-project lock, so polling never waits on Jev and a result is never asked twice. After a run the tab checks back every 2 s, at most 15 times, while `triage_pending`. When Jev fails, the result is kept as "no verdict" for 10 minutes before it's asked again, so a Jev outage isn't hit on every look. No triage when no one opens the tab: nothing is computed for results no one looks at.
- **2026-09-30: The TEST-007 follow-up doesn't yet name failing tests Jev says the app broke.** The verdicts are only worked out when the Tests tab is open, so the follow-up couldn't rely on them; left for when triage runs after each agent test run.
- **2026-09-30: A chat message that would undo a recorded decision waits for the user's Go ahead (REQ-003), when Jev is at least 80% sure,** so it's caught before the agent spends a turn, rather than relying on the agent noticing. Jev gets the decision bullets (every `### Decisions` section of Main's REQ.md, the last 40, 300 characters each) as a choice with "none" (live: "Switch the database to Postgres" picked the SQLite decision at 0.97, "Make the header green" the blue-header one at 0.99; unrelated messages "none" at 0.99–1.0). The prompt shows the decision's bold title.
- **2026-09-30: Go ahead tells the agent the change is intended through its prompt (`messages.meta.changes_decision`), not the chat text,** so the user's message stays as typed and the agent rewrites the decision instead of pushing back. Cancel leaves the message in the box: the composer keeps the text and attachments until a message is actually sent, so nothing has to be put back.
- **2026-09-30: REQ.md is read with one `cat` in Main's sandbox and its decisions cached until anything new appears in the project's chats** (keyed by the newest non-user message id), since only the agent changes it. A stopped sandbox or a failed read means no decision question.

## Demo videos

### Decisions

- **2026-10-03: Demos are made from the app's Playwright tests (TEST-002), not recorded by hand or from chat-written scenarios.** The tests already walk through each requirement and pass, so the demo shows what really works and can be rendered again after every change.
- **2026-10-03: The tests are re-run in demo mode, not cut from the Tests tab's recordings.** Those run at machine speed, have no cursor and are blurry VP8 at 1280×720. Demo mode waits 700 ms before each action (not before checks, which only add dead time), holds a second on the final state, and gives each test 2 minutes instead of 30 seconds so the pauses can't make it time out.
- **2026-10-03: Frames come from the browser's screencast over the debugging protocol, not Playwright's video.** Sharp JPEGs at 1920×1080 (the tests' 1280×720 layout at device scale 1.5, so pages look the same as in the tests), each with its time, on the same clock as the steps and the mouse. - **2026-10-03: Remotion's packages are installed in the image (`/opt/onedrop/remotion`), the composition's source is a tool file (`demo-video/`), and the bundle is built on first render and cached by the source's hash,** so a change to the composition reaches sandboxes like other tool files, without a new image. Renders use the image's Chromium.
- **2026-10-03: The storyboard is `.onedrop/demo.json`, committed with the app; renders live in `.onedrop/demo/`, excluded from git like test recordings.** A scene names its test by file and title (the title is the requirement's "User should be able to…" bullet), since lines move as tests are edited. Only the latest render is kept.

## App tables

TABLE-001..010.
Apps that keep lists of records get Airtable's table: a spreadsheet-like grid, rich field types, fields and formulas people add themselves, linked records with lookups and rollups, saved views (grid, board, calendar, gallery), an expanded record with comments and history, and CSV import and export. The rest stays a custom app: its own pages, roles, logic and public forms.

### Decisions

- **2026-10-02: Apps built from Airtable-like templates should feel like Airtable in their tables, without becoming an Airtable clone.** People expect to edit cells in place, paste from a spreadsheet, add a field in seconds and save filtered views; the agent-built app is what makes them better than Airtable (any layout, real roles, real logic), so that part isn't replaced by a generic database UI. People who want Airtable itself can install an open-source one (Baserow, NocoDB, Teable) from the free apps.
- **2026-10-02: The table kit is code copied into each app (`/opt/onedrop/kit tables`), not a Composer or npm package.** The app owns it, so the agent can change any part for that app, and nothing is fetched from outside. Every app gets the same tested grid instead of the agent improvising one each time. A newer kit only reaches apps that install it afterwards; apps keep the copy they have.
- **2026-10-02: The grid is our own, on `@tanstack/react-virtual`, styled like the starter kit's shadcn components.** Rejected: Glide Data Grid (its stable release doesn't support React 19, and its canvas cells don't look like the rest of the app), AG Grid Community (heavy, with range selection, fill and grouping in its paid edition), Handsontable (its free license is non-commercial only), HyperFormula for formulas (GPL).
- **2026-10-02: Fields the app was built with are real database columns the agent declares in a table class; fields people add are kept in a `custom_fields` JSON column, described in `table_fields`.** The app's own code (pages, rules, reports) keeps working on its columns, while people can still add fields without the agent. Built-in fields can't be renamed, retyped or deleted from the grid, since the app's code relies on them. Rejected: keeping every field as data (a Baserow-style engine), which would make the app's own features harder to build than with plain models.
- **2026-10-02: A table's records are all sent to the browser (up to `tables.max_rows`, 5,000 by default), which filters, sorts, groups and summarizes them.** Views then change instantly and work for formula and lookup fields, which SQL can't sort by. Airtable works the same way. Tables expected to outgrow that should get their own paged pages from the agent.
- **2026-10-02: Formulas are worked out on the server only, in one PHP evaluator, and stored with field keys rather than names,** so there's one set of rules, and renaming a field doesn't break formulas that use it. The browser shows names, and gets each record's results with the record.
- **2026-10-02: The other table's side of a link (TABLE-005) is read-only for now;** links are changed from the field they were added on. @mentions in comments don't notify anyone yet.
- **2026-10-03: The kit has form and timeline views (TABLE-009, TABLE-010), but no automations or API.** Forms and timelines were the Airtable features people missed most (intake forms are in most templates; the roadmap, project and grant templates expect a timeline). Automations and APIs are what the agent writes as code, with any logic, so the kit doesn't imitate Airtable's builders.
- **2026-10-03: Public forms leave out person and link fields, are throttled per visitor, and are off until someone who may manage views turns them on.** A person or link picker would list the app's users or records to anyone with the link. The link is a random token that can be replaced, so a leaked link can be cut off.
- **2026-10-03: Making a form public also needs permission to add records, and a public personal form stops working when its owner loses it,** so nobody can let strangers add records they couldn't add themselves. Public uploads go under `<table>/form-uploads/`, and a public form only accepts files from there, so a visitor can't attach the table's other files.
- **2026-10-03: A form only sends the fields that were answered,** so fields left empty get the table's `defaults()` (e.g. a new deal starts as "Lead") instead of being cleared.
- **2026-10-03: The form page opts out of the app's layout (`layout` returning the page, or null in Inertia 3),** so visitors without accounts see only the form, not the app's sidebar.
- **2026-10-03: A timeline's lanes come from the view's first group only;** deeper groups would make lanes within lanes, which Airtable doesn't do either.
- **2026-10-02: The table kit is where an app starts for its record lists, not its whole shape.** The user's worry was ending up with "a slower Airtable". The agent starts from the kit for lists people edit, and still builds the app's own pages around them (home page, dashboards, public forms, screens shaped around the work), so each app does what Airtable can't. The instructions say so; an earlier "don't build your own table" line was dropped as pushing every app towards the same look.
- **2026-10-02: Every template's prompt asks for spreadsheet-like lists (`AppTemplate::SPREADSHEET`, before "Add some sample data…"),** so apps from Airtable-like templates get the table kit, and the user sees what they're asking for.
- **2026-10-02: The kit's tests are PHPUnit classes, with fixture tables prefixed `kit_test_`.** The starter kits use PHPUnit (Pest runs them too), and a CRM app has its own `deals` and `companies` tables, which unprefixed fixtures collided with.
- **2026-10-02: The grid's endpoints and attachment links are paths, not full URLs,** because an app is opened under several hostnames (the preview, the published `*.ts.net` address), and a full URL from another host loses the session.
- **2026-10-02: A CSV import maps unmatched columns to "Skip", not to new fields, and can't be undone with ⌘Z,** so an import never adds fields by accident, and undo (which would only remove its last batch of 200) isn't misleading. A board leaves out its "Uncategorized" column when it's empty.

## Install, deploy and admin

INSTALL-001..002, DEP-001, ADMIN-001..007.
One-line install on a computer or a server; AWS via Pulumi; Laravel Cloud; admin settings for name and logo, sandbox providers, server monitoring, domain/HTTPS and database backups.

### Decisions

- **2026-09-29: The Docker install is one FrankenPHP container** (app and queue worker) with SQLite in a volume; projects run in sibling sandbox containers through the Docker socket.
- **2026-09-29: A server install only publishes 80/443;** previews and shells are `preview-<id>.<domain>` / `shell-<id>.<domain>` behind the gateway's sign-in check.
- **2026-09-30: Admin settings saved in the app win over `.env`,** and queue workers pick them up without a restart.
- **2026-09-30: Sandbox providers are an ordered list with on/off switches, not one "active" pick.** New projects run on the first one that's on and has its required settings; an admin drags to reorder, and selects one to see its settings in a pane beside the list. The order is the place to later send a project that needs something (e.g. Docker inside the sandbox for Compose) to the first provider that supports it. Installs that saved an active provider before there was an order keep it first. No failing over to the next provider when one errors, for now.
- **2026-09-30: The install command is `curl -fsSL https://onedrop.io/install | sh`,** a redirect to `install.sh` on main's raw GitHub URL. The raw URL was too long to fit on the home page without a horizontal scroller. A redirect, not serving the file, so the script stays whatever is on main (not the deployed app's copy) and GitHub stays the source people can read; the raw URL still works and the install guide shows it. Every install has the route, which is harmless. The home page's command box wraps rather than scrolls on narrow screens.
- **2026-09-30: When `tests` fails on main or a same-repo PR, the `ci fix` workflow opens a `ci-fix` issue with the end of the failed log and assigns it to Copilot cloud agent,** which fixes it in a PR into the failed branch; nothing lands until a person merges it. Copilot, not the Claude Code action, because it's built into GitHub and needs no Anthropic key. An issue assigned to Copilot, not the agent tasks API, because that API is Business/Enterprise only; Copilot automations need no workflow but aren't available in public repos. Copilot can't be assigned with `GITHUB_TOKEN`, so it needs a `COPILOT_TOKEN` user token, and does nothing without one. It skips fork PRs (their logs could steer the agent), Copilot's `copilot/*` branches (no fix-the-fix loops), runs whose branch has moved on, and branches that already have an open `ci-fix` issue. Copilot must fix the root cause (flaky tests included) and may not skip, delete or loosen tests, or add sleeps or longer timeouts. `copilot-setup-steps.yml` sets Copilot up the way CI is set up.
- **2026-10-01: On Laravel Cloud (`LARAVEL_CLOUD` set), the Docker idle check (every 15 seconds) and the server sample (every minute) aren't scheduled,** because Cloud wakes a sleeping app for each scheduled task and keeps it up for its sleep timeout, so either would keep the app awake for good. Neither does anything useful there: Cloud has no Docker sandboxes and no host of ours. Cloud's scheduler runs the rest (image pruning, database backups); it's turned on for the App instance. Not `->when()`: Cloud reads the wake times from `schedule:list`, which lists a task even when its filter would skip it.
- **Images are `ghcr.io/onedrop-io/onedrop` and `onedrop-sandbox`,** published for amd64 and arm64 once main's tests pass. The `drop` command, container, volume and network keep their short names.
- **2026-09-30: Held apps are reviewed under Admin → Reviews (ADMIN-006), shown only on the hosted install.** Platform admins can't open an organization's projects there (ORG-006), so the page shows what Jev saw instead of linking to the project.
- **2026-09-30: Taking an app down stops its public app and deletes its share page, and it can't be published publicly or shared until an admin approves it; private publishing and building still work.** A takedown that the user could undo by clicking Publish again wouldn't be one, and the app may be fixable, so admins can reverse it from the decided list. No email to admins or owners yet; admins find held apps on the page.
- **2026-09-30: `phpunit.xml` blanks `OPENROUTER_API_KEY`,** because the key in a developer's `.env` otherwise reached tests, and with the sync queue every finished run in a test would call Jev for real. Tests that need a key set `services.openrouter.key` themselves.

## Competitors

Who we compete with and how we differ. The full landscape (who uses what stack, how each does mobile) is in `docs/internal/competitors.mdx`, a hidden docs page; keep the two in step. Facts about other products are from memory as of October 2026, so re-check them before quoting them anywhere public.

- **Prompt-to-app builders (the main fight):** Lovable, Bolt.new, Base44, Replit Agent, v0, Google AI Studio "Build" and Firebase Studio. Replit is the closest to OneDrop.
- **Mobile-first builders:** Rork, a0.dev, Vibecode. All of them build Expo (React Native) apps.
- **Cloud coding agents:** Claude Code on the web, Codex, Cursor background agents, Devin, Copilot coding agent, Jules. They hand back a pull request or a screenshot, not a running app.
- **Open-source / self-hostable builders:** bolt.diy, Dyad, OpenHands, Open Lovable, Onlook. These are the most direct threat to the self-hosting pitch.
- **Hosting / PaaS:** Dokploy, Coolify, CapRover, Railway, Render, Fly.

### Decisions

- **2026-10-04: Our edge is self-hosting, any stack, your own AI and agent choice, orgs for internal tools, and a backend that needs no setup but lives in the app's own code; our gaps are mobile publishing and price.** The hosted builders keep you on their infrastructure, their models and usually one stack (Lovable and Base44 use React plus a backend service; v0 is Next.js on Vercel). Base44, Firebase Studio, Replit, Lovable Cloud and Bolt Cloud also need no backend setup, but through their own SDK or services, so the app can't leave the platform. OneDrop's apps get the same with no vendor: the app's own database and table kit, Users & Auth built in with Fortify/Socialite, App Storage buckets, and databases created when the app is hosted. This was first listed as a gap by mistake. Replit and Bolt publish mobile apps through Expo; Google gives its builder away free. Of the polished builders, only Dyad and bolt.diy can be self-hosted.
- **2026-10-04: The default app stays Inertia + Laravel, not a mobile-first Expo app on a Laravel API, even though most builders generate a client-only app on a hosted backend.** The user chose it as the more responsible stack: one app to deploy and run, with no API layer, CORS or tokens between a front end and a back end, and server routing gives the agent fewer places to break things. Pages are faster too: each page's data comes in its first HTML response instead of a client fetching from an API after load. An Expo app that also runs on the web (one UI for web, iOS and Android, like Rork and a0) was ruled out because it means two deployables, client-side data fetching and weaker SEO, and our Laravel tools (Tables, Users & Auth) are built for Inertia pages. Generated apps don't turn on Inertia's server-side rendering yet (it needs a Node process beside PHP when hosted); that's a separate choice. The cost of Inertia is mobile: there's no JSON API for a native app to call.
- **2026-10-04: Every app is an installable web app (PWA) by default, and a native store app is a mode the user turns on.** By default the starter kit gets a web manifest, service worker and Apple meta tags, the App Icon tool also makes 192, 512 and 1024 px PNGs, Publish shows an "Open on your phone" QR code, and the agent checks layouts at phone width. That costs almost nothing and gives home-screen installs and push without the stores. Asking for a phone app (or picking Mobile app when starting) adds an Expo Router app in `mobile/` and a Sanctum API in `routes/api.php` beside the Inertia pages, previewed on a phone through Expo Go with its own tokened device link, and built and sent to the stores with EAS using the user's own Expo, Apple and Google accounts; the store app calls the hosted app, so Hosting is required. It's a mode rather than the default because the agent then builds every screen twice. Rejected: a Capacitor shell around the web app (Apple rejects apps that are only a website, guideline 4.2) and NativePHP for Mobile (new and hard to run in a sandbox). Not built yet.

## Computers and Drive

CMP-001..003, DRIVE-001..004. Each person gets their own cloud computer (a Linux desktop with Chromium, streamed into the page) that they and the AI use, like Grok's or Manus's computer; Drive holds their files and the files they share with the organization and their groups, reachable from the web, their computer and projects.

### Decisions

- **2026-10-06: The user and the AI both drive the computer.** The user asked for a desktop with a browser and files "like Grok's"; the AI taking tasks on it while they watch is what makes it more than a remote desktop. Ruled out: a desktop without the AI.
- **2026-10-06: A computer is a project of kind `computer` (`projects.kind`), hidden everywhere projects are listed.** It needs everything a project's main chat already has: a sandbox made, woken, suspended and kept up to date by the same code, the chat, queue, agents, model picker, events, usage and credits, the Shell and Files tabs, and the gateway's sign-in. Rejected: a separate model implementing `Conversation`, which meant widening `AgentRunner`, `ModelCatalog`, `CreateSandbox`, `SandboxUpdater`, idle suspension, usage and the gateway from `Project` to a new owner type, about forty places, for the same behavior. `User::projects()` and the organization's list only return apps, so the sidebar, search, ordering and desktop activity leave computers out without each having to remember; what a computer doesn't do (publishing, hosting, tasks, Tools, icons, naming, checkpoints, backups, preview checks) is turned off where each starts.
- **2026-10-06: Only its owner can open a computer, not the organization's admins** (`ProjectPolicy`). Unlike a project, it holds the person's browser sign-ins and personal files. Platform admins impersonating a user (USR-003) still act as that user.
- **2026-10-06: One computer per person per organization, made the first time they open it.** A person in two companies keeps their work apart; nothing runs (or costs) for people who never open it.
- **2026-10-06: Computers are on for every organization, and owners and admins can turn them off (`organizations.computers_enabled`); self-hosted installs can turn them off for the whole install (`COMPUTERS_ENABLED`).** Each one is a sandbox, so it costs what a project's does while it runs, and it sleeps when unused like any sandbox. Turning them off puts running ones to sleep and keeps them, so turning them on again gives everyone their computer back.
- **2026-10-06: The desktop runs in the same image as projects, started only in computers (`ONEDROP_DESKTOP=1`): TigerVNC's `Xvnc` as the display, Openbox, a Plank dock, PCManFM drawing the desktop, Thunar for files, xfce4-terminal and the Chromium already in the image, streamed by noVNC through the sandbox's own proxy at `/__onedrop/desktop/`.** One image keeps one build, one update path (`SandboxTools`, `SandboxUpdater`) and every provider working unchanged; the desktop adds about 150 MB to it. `Xvnc` is the X server and VNC server in one, and resizes its screen to the viewer's (`resizeSession`), so the desktop always fills the page; XFCE or GNOME would add hundreds of MB for panels and settings nobody needs here. Going through the preview's proxy means no new port for Blaxel or Docker to publish and no new gateway kind: the gateway already signs the viewer in, and only the owner may view a computer. Rejected: reusing the Browser tab's CDP screencast (TEST-005), which shows one tab, not a desktop with windows, files and a terminal.
- **2026-10-06: The desktop looks dark and Mac-like, not like Windows: flat dark title bars with round close, minimize and zoom buttons on the left (our Openbox theme), rounded windows with soft shadows (picom, xrender, no fading or blur so the stream stays light), a frosted rounded dock with icons that grow under the pointer, Adwaita-dark with Papirus icons and Inter, Chromium in dark mode, Thunar (GTK3) for files instead of PCManFM's GTK2 windows, a deep blue-violet wallpaper, and the desktop's folders as launchers rather than links (no shortcut arrows). The dock is always shown and reserves its space, so maximized windows stop above it.** The user found the first look (Clearlooks title bars, light widgets, a boxy dock, a grey wallpaper) hideous and like Windows. It stays on the same small stack: XFCE or KDE would look polished out of the box but add hundreds of MB to every sandbox's image.
- **2026-10-06: The dock is started again whenever the screen changes size.** Plank stays where it was when Xvnc resizes to the viewer, so after the first resize it sat below the screen. Openbox keeps maximized windows above it. Noto and WenQuanYi fonts are in the image so pages in Arabic, Chinese and other scripts don't show boxes.
- **2026-10-06: The viewer is our own page on noVNC's `RFB` module, not noVNC's `vnc.html`.** It fits the workspace (no noVNC control bar), syncs the clipboard both ways while the page has focus, sends ⌘ shortcuts as Ctrl on a Mac (⌘C, ⌘V, ⌘L work as expected), and reconnects by itself after the sandbox wakes.
- **2026-10-06: The AI uses the desktop through a `computer` command in the sandbox (screenshots, mouse, keyboard, windows: `xdotool` and ImageMagick on the display) and Chromium through its DevTools port (`computer browser …`, Playwright over CDP), told how in its own instructions (`/opt/onedrop/computer.md`, chosen by `APP_MODE=computer`).** The agents (Claude Code, Codex, OpenCode) already run shell commands and read images, so a CLI works for all three without an MCP server for each. Driving Chromium by its page rather than by pixels is faster and more reliable for the web, and it's the same window the user watches. The AI hands sign-ins (passwords, codes, captchas) to the user rather than typing secrets.
- **2026-10-06: A computer's Home is `/workspace` (Desktop, Documents, Downloads, Drive), kept across updates like a project's files but not backed up as code (no checkpoints, no git bundles).** It's a person's scratch space, not a repository; files they care about belong in Drive, which lives outside every sandbox.
- **2026-10-06: Drive is files the platform stores (rows in `drive_items`, contents on the app's default disk, S3 in production), not a folder on a sandbox.** It has to be the same from the web, every computer and every project, and survive any sandbox. Files are kept as blobs named by a random id, with the SHA-256 when the uploader gives one (S3 checks it on upload); there's no deduplication or version history.
- **2026-10-06: Drive has three kinds of place: My Drive, the organization's, and one per group.** The user chose these over sharing single files and folders with chosen people: they match the groups people already manage, and access is simply membership. Organization owners and admins can open every group's drive, as they can manage every group.
- **2026-10-06: Projects get the organization's drive and their owner's groups' drives, read and write, but not the owner's My Drive.** The user chose read-write so agents can save what they make. My Drive stays out because a project is visible to the organization's admins and runs code anyone with access can change.
- **2026-10-06: Sandboxes sync Drive with a small daemon (`docker/sandbox/drive.mjs`), not a network filesystem.** It keeps `~/Drive` (computers) or `/home/sandbox/drive`, linked at `/drive` (projects), in step with Drive over the app's HTTPS API: a change feed by revision, uploads in parts, renames and moves (found by the file's inode) sent as moves, so an item keeps its identity. Rejected: mounting S3 or WebDAV with FUSE, which needs `/dev/fuse` and privileges on every provider, would put storage credentials in the sandbox, and makes every file read a network round trip for agents that read many files; and a PHP WebDAV server, a new dependency the hosted install's PHP workers would have to hold large transfers through. Each sandbox proves itself with a token derived from the app key and its id (`DriveSync::token`), so nothing needs storing; it can only reach the drives its owner or project may.
- **2026-10-06: The daemon only polls for changes while its sandbox is in use (the desktop or preview opened, the Shell, an agent running, or a local change in the last two minutes): every 3 seconds then, not at all otherwise; it checks once whenever its sandbox wakes.** Docker sandboxes are suspended after a minute without network traffic (SBX-007), so a steady poll would keep every sandbox awake for good. Local changes are pushed at once whatever the state.
- **2026-10-06: Uploads, from browsers and sandboxes alike, go through the app in 8 MB parts (S3 multipart on S3); downloads go straight to the disk by a signed link.** Browsers can't upload to the bucket directly without CORS set on it, which Laravel Cloud's buckets don't have by default; one path for both keeps it one set of tests. 8 MB is S3's smallest part size rounded up, small enough for any request limit. Rejected: signed upload URLs for sandboxes only (a second path), and hashing every upload in the browser (a whole file in memory); the SHA-256 is kept when a sandbox sends it, to skip downloading a file that only moved.
- **2026-10-06: When a file changed in two places since they last agreed, both are kept: the one that arrives second is saved beside it as "<name> (conflict <date>)".** Losing someone's edit silently is worse than an extra file, and the rare case doesn't justify merging.
- **2026-10-07: Show every file the browser can, as it is: images (SVG too), video, audio and PDFs, in the Files tab and in Drive; Markdown rendered and CSV/TSV as a table in Drive; image thumbnails in Drive's list (FILE-001, DRIVE-001).** The user found MP4s didn't preview. In Drive the cause was the type picked from the name: the general list gives `application/mp4` (and `image/pdf`) first, so a fixed table now names the types of the files we show, and the type is taken from the name when a file is served, so files saved before still show. The Files tab only ever showed text: the sandbox's proxy now serves a workspace file's bytes and a page that shows it (`/__onedrop/files/raw` and `/view`), on the preview's address only and only inside `/workspace`, rather than through the app, because exec returns a whole file at once in base64 and a video would pass through PHP's memory. Both answer ranges (the app's local disk with a file response, S3 by itself), so video seeks and Safari plays it. SVGs are served with a sandboxing CSP so one opened on its own can't run scripts as the preview's address; PDFs aren't, because Chrome won't show a PDF in a sandboxed frame.
- **2026-10-06: Deleting from Drive, a computer or a project moves to Trash for 30 days (DRIVE-002).** Agents can now delete shared files, so a mistake must be recoverable. A daily job deletes older items and their contents for good.
- **2026-10-06: Drive's size limit is per organization, `DRIVE_QUOTA_GB`, none when unset.** The hosted install sets one; a self-hosted install pays for its own storage. Trash counts until it's emptied.

## Desktop app

DESK-001..011. A native app for macOS, Windows and Linux (Tauri) that runs the web app's own pages, talking to an install over HTTP with a token it gets by signing in through the browser.

### Decisions

- **2026-10-04: The desktop app runs the web app's own Inertia pages, bundled, over HTTP with its token; not screens of its own, and not the server's site in a window.** Every page and tool is the web's code, so the app has all of it and nothing to keep in step; it talks to whichever install it signed in to. Its own screens (an earlier version had a sidebar, chat and new-project page of its own over a `/api/v1`) fell behind the web as soon as the web changed, and only covered a few tools. Showing the server's site in a window would also have worked, but it's the website rather than an app that talks to its server over HTTP. The cost: a desktop build and a server of different versions can disagree on a page's props, so the app updates itself and says when the server is older (DESK-004).
- **2026-10-04: The web routes take the desktop app's token (UseDesktopToken); nothing else changes for browsers.** A request with a valid token is that token's user, with a session of its own named after the token (an HMAC of its id with the app key), so flashed messages and redirects work; it skips the CSRF check, since a browser never sends the token by itself; and the web's UI cookies, which can't reach the server from the app's origin, come in X-Onedrop-Cookies. Only the app's origins (`tauri://localhost`, `http(s)://tauri.localhost`, and its development server locally) may call the server across origins, with Inertia's headers exposed.
- **2026-10-04: What browsers do on their own, the app does in `desktop/src/lib/transport.ts`.** Inertia's requests and the page's fetches get the server's address and the token; `<img>` addresses on the server are caught as they're set and loaded with the token (an unsigned request would be sent to the sign-in page, whose preload links the webview follows); the server's pages open in the app, other sites in the browser, downloads in the Downloads folder; `document.cookie` lives in local storage. The window itself won't navigate to the server (a signed download link opens in the browser instead).
- **2026-10-04: The API is only signing in: `POST`/`DELETE /api/v1/desktop/token`.** Sanctum personal access tokens, prefixed `onedrop_` so secret scanners catch leaked ones, kept in the system keychain, revoked by "Log out" in the app or in Settings → Desktop app.
- **2026-09-30: Tauri.** It builds for all three platforms from one codebase and ships small installers on each system's own webview, which the web's code runs in. Not Electron (a browser bundled in every install), and not a native toolkit (Flutter, Qt), which would mean rewriting the UI; the preview needs a browser engine anyway.
- **2026-10-04: The app signs in to onedrop.io unless the user changes the server.** New users get one button instead of an address to find; teams and people running OneDrop on their own computer click Change (with a shortcut for `http://localhost:8000`), and the app remembers the last server.
- **2026-09-30: Sign in through the browser, back to a loopback address with PKCE (RFC 8252).** The browser already has the user's passkeys, single sign-on and password manager, so the app never asks for a password. Only `http://127.0.0.1|localhost|[::1]:<port>/callback` is ever redirected to, so a code can't leave the computer; codes last 5 minutes and work once; the "Allow" page names the computer so a forged sign-in link stands out. Not a custom URL scheme: it doesn't work in development builds and any app can claim one.
- **2026-09-30: AI credentials stay on the server.** The app never sends or receives them; connecting an AI happens in the web's own pages, which the app shows.
- **2026-10-04: The desktop app sells what a browser can't do: reach your network, the project's ports on your computer, your own editor, running projects on your own computer, and the menu bar (DESK-006..011).** The user found "the web app in a window" no reason to download it. Using your own AI from your computer (Ollama, a signed-in Claude Code) was left out for now: credentials would have to be proxied without ever reaching a sandbox.
- **2026-10-04: One way in for ports, editors and the network: a WebSocket from the desktop app to a tunnel process in the sandbox (`docker/sandbox/tunnel.mjs`), through the preview's own gateway address (DESK-007..009).** The gateway already passes WebSockets to every provider (Caddy, the Cloudflare Worker, Runtime's HTTPS previews, local ports), and keeps its sign-in check on the path; no relay or new server, since the hosted app is PHP and can't hold connections. Each connection is its own WebSocket, so TCP's own backpressure works and there's no multiplexing to get wrong. The tunnel also checks a ticket the app signs with a key per sandbox (`DesktopTunnel`), valid for a minute, so a preview cookie alone (anyone who may view the project) can't open one; only people who can change the project get tickets, and only the owner gets SSH. It starts on demand with `exec`, so it's a tool file, not a base-image change.
- **2026-10-04: The network is reached the other way round: the desktop app keeps a control WebSocket open to the sandbox's tunnel, which listens on `127.0.0.1:<port>` per listed host (and an HTTP proxy for HTTP and HTTPS hosts) and asks the app to dial each connection over a new WebSocket (DESK-009).** The computer dials only the hosts on the project's list, and only for projects it was told to share its network with (kept on that computer), so neither the server nor code in the sandbox can make it connect anywhere else. Listed hosts get local addresses rather than their own names: changing the sandbox's `/etc/hosts` needs root, and a proxy set for everything would send npm installs through the user's computer; the HTTPS proxy keeps names (and so certificates) right for web hosts. The user accepted that only building reaches the network, not published apps on OneDrop's hosting, which run on Fly; those self-host or publish to the tailnet. The list lives on the project (editors change it), what's reachable right now in the sandbox user's `~/.onedrop/network.json` (outside the project's files, so it's never committed), which the agent's instructions point at.
- **2026-10-05: A computer dials only the hosts its own user agreed to: the project's list when they turned sharing on, or saved it in the desktop app (DESK-009).** The list lives on the project, which org admins can change too; without this, someone else adding `router.lan:80` would have reached into the user's network within a minute, unasked. Hosts added since wait, and the panel says how many, until the user turns sharing off and on.
- **2026-10-04: Editors connect over SSH through the tunnel, with the desktop app itself as SSH's `ProxyCommand` (`OneDrop ssh-proxy <project>`) (DESK-008).** The sandbox's sshd and the owner-only key rule already exist; this makes them reachable from anywhere, even with the app's window closed, because the binary signs in with the keychain's token. The app makes an ed25519 key per computer and adds it to the owner's SSH keys named after the computer, and writes its entries to `~/.ssh/onedrop/config`, which `~/.ssh/config` includes after the user agrees once; it never edits the rest of their config. Host key checks are off for these entries (each sandbox makes its own host key), as on the Developer → SSH page; the tunnel's TLS and ticket are what prove the other end.
- **2026-10-04: The user chose to build running projects on their own computer now, with the rest (DESK-010).** A sandbox there is a `device` provider sandbox: the same image (`ghcr.io/onedrop-io/onedrop-sandbox`) in the computer's Docker, managed by the desktop app. A computer is a desktop-app sign-in (its token), so signing it out in Settings → Desktop app also cuts off its sandboxes.
- **2026-10-04: The hosted app reaches a computer through a Durable Object in the preview gateway Worker (`DeviceRelay`), which the desktop app keeps a WebSocket open to (DESK-010).** The app is behind NAT and the hosted app can't hold connections, so something in between must. The Worker already sits in front of every preview and proves the app with `GATEWAY_SECRET`, so the app's calls (exec, copying files, the container's lifecycle) go to `/__onedrop/devices/<id>/rpc` with that secret, and the authorize answer for a device sandbox's preview or Shell names `device:<id>/<container>:<port>`, which the Worker hands to the same object. The app connects with a ticket the server signs with the secret, so the Worker checks it without asking. Self-hosted installs behind Caddy have no Worker, so they don't offer it; their server is usually already the user's own machine. Requests and responses stream in chunks over the one WebSocket, each with an id.
- **2026-10-04: A device sandbox's id names its computer (`<token id>:<container>`), so the provider needs no lookup, and moving a project to or from a computer is a provider change that `SandboxUpdater` already does with files kept (DESK-010).** Projects pick their computer, not the install: `projects.device_id`, which `CreateSandbox` uses ahead of the install's provider. Snapshots use signed links only (the `copy` transport assumes the server's own Docker). The project's AI credentials reach the container, as in any sandbox; it's the user's own computer.
- **2026-10-04: The new-project page has no "run on this computer" choice; a project moves there from the "This computer" panel (DESK-010).** The user found that page too busy already, and moving keeps the files, so starting in the cloud costs nothing.
- **2026-10-04: Closing the window keeps the app running in the menu bar; quitting is in the icon's menu (DESK-011).** Forwards, the network and projects on the computer need the app; a closed window that stopped them would look like a bug. Quitting says what will stop first.
- **2026-10-04: The new-project shortcut is ⌘⌥O (Ctrl+Alt+O elsewhere), with an off switch in the icon's menu, not a settings page (DESK-011).** Common shortcuts with Shift or Space clash with editors and launchers; one switch is all the setting it needs.
- **2026-10-04: The web app offers the desktop app in the sidebar only after the user's first project, until it's signed in anywhere, and never inside the app (DESK-005).** Downloading first is the slowest way in for a newcomer (install, open, then sign up anyway), so the home page leads with the browser and the app is offered once it would help: when they're coming back to projects. "Signed in anywhere" is any of the user's tokens, which are only the desktop app's. Closing it is remembered in the browser (`localStorage`), like Droppy: it's only a hint, and a column for it isn't worth it.
- **2026-10-05: The app releases itself from `main` at most once a day, and updates itself (DESK-004).** `.github/workflows/desktop.yml` builds the newest commit on `main` whose tests passed, for macOS (Apple Silicon and Intel), Windows and Linux, each morning if it changed since the last release (and on demand), into a `desktop-v1.0.<run>` release; the rolling `desktop-latest` release holds the `latest.json` the Tauri updater reads. Updates are signed with a key kept in the `TAURI_SIGNING_PRIVATE_KEY` secret, whose public half is in `tauri.conf.json`; the app installs nothing else. macOS builds are signed and notarized once the Apple secrets exist, and ad-hoc signed until then (`signingIdentity: "-"`): an Apple Silicon app the bundler leaves unsigned keeps only the linker's signature on its binary, which doesn't cover the bundle, so a downloaded copy is "damaged and can't be opened" with no way past it; ad-hoc signed, macOS asks once (System Settings → Privacy & Security → Open Anyway). Not a release on every push: users would restart several times a day for nothing. Servers stamp their image with the commit time (`APP_RELEASED_AT`) and send it to the app in `X-Onedrop-Released`; an app newer than its server says so, since only the server's owner can update it. Working offline isn't a goal: someone who wants that runs OneDrop on their own computer.
- **2026-10-03: The Shell's links open in the browser.** Claude Code prints its sign-in link as a terminal hyperlink, and xterm.js asks `confirm()` before opening one, which the webview can't show: a script in every frame opens the link instead, and the window sends new windows to the browser.

Every tool and its link stays (they're what IT teams look for), but the group labels go, the logos are grey until hovered, and it pauses under the pointer. With reduced motion it's one still, wrapped block instead.
- **2026-10-01: Signing up or logging in with something picked on the home page shows it beside the form, and the AI onboarding says what's next (HOME-004).** The user found that clicking a free app landed newcomers on a bare login page with no trace of what they'd picked. The left side shows the app's card (picture, logo, name, version, description), or the template or prompt they wrote, and the three steps ahead; "Not now" drops it. It's a shared Inertia prop (`pendingStart`) read from the session the new-project page later takes, so it disappears on its own once used; the auth pages without a pick are unchanged. The onboarding gets one line rather than the whole card, since that page is about choosing an AI.
- **2026-10-01: The home page shows the new-project page's three ways to start, using the same components (HOME-004).** The user sees that page as the call to action and asked to share it on the home page. The panels (`ways-to-start.tsx`) and the free apps' gallery and details are shared, so the two can't drift; the home page's prompt has no agent picker, attachments or repository import, since a visitor has no AI connected yet. What they pick is kept in the session (`start`) and filled in on the new-project page after signing up (and the AI onboarding), the way "Remix this" works (SHARE-002); the home page lists only the first 12 free apps (popular first) until they search, pick a category or ask for all, so the rest of the page isn't 500 cards further down; a free app opens its details there rather than starting at once, so they see it again before using it with the AI they just connected. The free apps' pictures route (`templates/screenshots`) is now public, throttled to 60 a minute: it only takes app ids from the catalog, and each app's pictures are cached a week, so a visitor can only make it look up an app it already lists, at most once a week per app.
- **2026-10-02: OneDrop is for everyone from first-timers to experts, building any app in any technology, and for hosting and remixing existing open-source apps.** The user ruled out narrowing it to one buyer (companies' own tools, or Lovable-style solo makers). Positioning leads with "no ceiling": start from a sentence or a free app and grow into your own repository, any stack, Docker, your own AI or your own server, where Lovable is locked to one stack and Dokploy/Coolify assume DevOps knowledge.
- **2026-10-02: The hosted install gets a Free plan whose AI credits are enough to build something useful, with no AI account needed.** Today a newcomer must connect a Claude or ChatGPT plan before building anything, which loses beginners. Credits run on a cheap model (DeepSeek Flash, about $0.025–0.05 a build), so a useful allowance costs a few dollars per person.
- **Pricing:** self-hosted is free with no limits; paid plans are flat (not per seat), never mark up the user's own AI, never use credits for hosting, and published apps never pause. Yearly is the default and saves 20%.
- **2026-09-30: The demo video plays in a dialog from a Watch the demo button in the hero, streamed from Cloudflare R2** (`DEMO_VIDEO_URL` in `resources/js/lib/links.ts`). A dialog keeps the hero's animated demo in place, and hosting the MP4 off-repo keeps a large binary out of git and off the app server.

Self-hosting is mostly what makes people trust the hosted one ("free to self-host, source available"), and the desktop app is a client for an account they already have. So the hero leads with "Build your first app" and "free to start, no AI account needed", with small links to the desktop app and self-hosting; a "Use it wherever suits you" section right after the ways to start shows the three side by side, the browser marked "Start here", and each card is enough to start: the download for their system, and the install command. The local installer already opens the sign-up page, and a server's first account comes from its setup link, so nothing there needed the home page.
