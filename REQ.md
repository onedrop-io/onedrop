# REQ

Everything OneDrop has to be, in one place: the requirements (the stories in `SPEC.md`, summed up by area) and the decisions made along the way, with the reasons for them. `SPEC.md` says _what_ users can do; this file also says _why it is that way_ and what was ruled out, so a later change doesn't undo a choice by accident. See `AGENTS.md` for when and how to update it.

## Product

- OneDrop is a self-hostable, Replit-style app builder: a person describes an app in chat, a coding agent builds it in a sandbox, and the running app is live at a URL while they work.
- Target users are trusted staff, not anonymous strangers. Real-time multi-user editing of one app is out of scope.
- Any stack, but Laravel's React starter kit by default (AGT-008).
- Bring your own AI: each user connects their own Claude, Codex/ChatGPT, OpenRouter or Gemini account. No markup on AI.
- Runs on a laptop (Docker), a single server, AWS, or Laravel Cloud from the same codebase.

### Decisions

- **2026-09-30: One codebase for self-hosting and for our multi-tenant hosted OneDrop.** Anyone can self-host one install; we also run one hosted install that serves many companies, so organizations must be a real boundary, not a kind of group. Groups stay as teams inside an organization (see Organizations).

- **2026-09-30: Name is OneDrop, never "zap".** `zap` is only the local checkout folder. Use `onedrop` in code, paths, images, headers; `APP_*` env vars on the platform server, `ONEDROP_*` inside sandboxes (where `APP_*` belongs to the user's app). Everything was renamed as a clean break, no migration for old sandboxes.
- **2026-09-28: Source available under the Elastic License 2.0.** Say "source available", never "open source".
- **2026-09-27: Inertia + React throughout; no Livewire,** in the platform and in the default app template.
- **2026-09-28: Postgres unless `DB_CONNECTION` says otherwise.** Local, tests, servers and the Docker install set `sqlite` explicitly; hosts like Laravel Cloud that only inject Postgres settings just work. Avoid SQL that only one of them supports.
- **2026-09-29: Dark theme by default.**
- **Build plan:** Laravel never holds a long-lived connection or supervises a process. Long-running work happens in the sandbox (agent, forwarder) or a queue job; Laravel coordinates, stores and broadcasts.

## Accounts, people and settings

AUTH-001..003, GRP-001..003, USR-001..003, INV-001, SET-001, BRAND-001.
Email/password (Fortify) plus Google, Microsoft, GitHub, GitLab and OIDC sign-in; two-factor and passkeys; groups with owners; admin user management; invite links; an account menu with settings in a modal.

### Decisions

- **Sign-up stays open to everyone;** invites are a convenience, not a gate (INV-001).
- **2026-09-29: The first account on a server install can only be made from the installer's one-time setup link** (`SETUP_TOKEN`), so a stranger who finds a new server first can't make themselves admin. On a local Docker install the first person to sign up is admin.
- **2026-09-30: Email verification is off by default when `APP_ENV=local`** (mail only goes to the log); on everywhere else. `AUTH_VERIFY_EMAIL` still wins.
- **Provider emails count as verified only when the provider says so;** Microsoft's never do. An unverified email is never auto-linked to an existing account.
- **2026-09-29: One GitHub App covers Tools → Git and "Continue with GitHub"** (`GITHUB_APP_CLIENT_ID/SECRET`); `GITHUB_CLIENT_*` override it for a separate OAuth app.
- **2026-09-28: Trust Laravel Cloud's load balancer** so OAuth callbacks come out as `https://` (the loopback-only `trustProxies()` had turned Cloud's handling off).
- **2026-09-28: Groups, Invite people and Users live in the settings modal,** not as top-level pages.
- **2026-09-30: An admin's user page (USR-002) shows what the install holds about the person, never their secrets.** AI connections show only their hint, GitHub only the login. Changing admin access stays on the list. Projects link only when the admin could open them anyway, so a platform admin still can't open another organization's projects (ORG-006). Recent sessions show only when sessions are kept in the database.
- **2026-09-30: Its usage section reuses the Usage page's report (`UsageReport`), fixed at 30 days,** plus all-time totals, so the two pages can't disagree about the numbers.
- **2026-09-30: Sign-ins are recorded on the user (`last_login_at`, `last_login_method`), not in a log table.** Admins needed "when did they last sign in" for support; a full history wasn't asked for. The method comes from the route that signed them in; a remember-me cookie resuming a session isn't recorded, and a provider sign-in that goes through the two-factor challenge still records the provider.
- **2026-09-30: The first admin actions on a user are Sign out everywhere and Reset two-factor,** the two support requests that come up most. Both ask for confirmation, not the admin's password, and neither works on the admin themselves (they have Settings → Security for that, and resetting your own two-factor there needs your password). Sign out everywhere deletes their database sessions and rotates the remember-me token. Suspending and deleting users were left for later: each needs its own decisions (what happens to their projects).
- **2026-09-30: Admins can impersonate users (USR-003), with an audit trail and guardrails.** It's a session swap (`Auth::login` as the user, the `impersonations` row's id kept in the session), not a package, so stopping signs the admin back in without a password. Other admins can't be impersonated, so one admin can't act as another and hide behind their name; the target already being a non-admin also keeps admin pages out of reach while impersonating. The user's profile, password, two-factor, passkeys, sign-in providers and account deletion are blocked by route name (`BlockWhileImpersonating`), so the admin can see and act as them but not take the account over. Everything else works as the user, including running agents on their AI connection. Every impersonation is a row (admin, user, IP, start, end) listed on the user's page; signing out ends it, and a session that just expires leaves it "not stopped". The banner is a fixed pill at the bottom, above the settings modal, because the sidebar is fixed full-height. Stopping only needs `auth`, since the user may not have verified their email. Confirming is enough; no password re-entry, like the other admin actions.

## Organizations

ORG-001..007 (see `docs/plans/organizations.md`; all built: the boundary, the switcher, members, settings, usage, logos, and the platform admin's list). Billing comes next, separately. Organizations are the boundary between companies: projects, groups, invites and skills belong to one, and nothing crosses it.

### Decisions

- **2026-09-30: Organizations always exist, on every install.** A self-hosted install has one, made by a migration that moves everything into it; the hosted install has many. One code path, not an "org mode", so self-hosted can't drift from hosted. No making "organization" a kind of group: groups have no settings, admins or data of their own, and it would mix a company boundary with a team inside it.
- **2026-09-30: A person can belong to several organizations and switch between them.** Adding this later would mean re-keying every membership, and consultants and agencies need it.
- **2026-09-30: The current organization comes from the URL, not the session.** Two tabs can be in two organizations, and a link always opens in the right one. Organization pages live under `/o/{slug}/` (new project, groups, invites; search and creating projects too). `/o/` rather than a bare `/{slug}` so a slug can never clash with a top-level route (`login`, `s`, `invite`, …). Project pages keep `/projects/{id}`: the project already names its organization, and putting the slug in every project route would have changed about 150 routes, every link to them and ~700 test lines for no gain in isolation. Opening an organization page or a project makes that organization the user's current one, and `/dashboard` (where signing in lands) redirects to it.
- **2026-09-30: Things that belong to a person stay with the person, outside any organization:** profile, password and 2FA, passkeys, social logins, SSH keys, AI connections (bring your own AI, REQ Product), and for now the GitHub accounts they connected. Projects, groups, invites and skills belong to an organization. A person's own skills stay in the organization they made them in. AI usage belongs to both: the person's Usage page shows what their connections paid for, and the organization's shows every run in its projects.
- **2026-09-30: Two kinds of admin.** Platform admin (`users.is_admin`) runs the install: sandbox providers, server, monitoring, backups, and on hosted, the list of organizations. Organization owners and admins run their organization: members, groups, invites, name and logo, usage. Being a platform admin gives no access to an organization's projects on the hosted install. On a self-hosted install platform admins also run its one organization, so making someone admin on the Users page still works as before, and the first account owns it.
- **2026-09-30: "Everyone" means everyone in the organization,** never everyone on the server: sharing a skill, Sign in with OneDrop set to everyone, its group picker and `groups` claim, and privately published apps. On the hosted install the old meaning would reach other customers. The Users list stays a platform-admin tool for the whole install; an organization's own members are in Settings → Organization (ORG-004).
- **2026-09-30: Sign-up depends on the install.** Self-hosted: new sign-ups join the one organization, as today (sign-up stays open). Hosted (`APP_MULTI_TENANT=true`, an `APP_` variable because it's the platform's own setting): signing up without an invite creates "<first name>'s organization", owned by that person; an invite joins the inviter's instead. New self-hosted accounts join as members.
- **2026-09-30: Something in another organization is a 404, not a 403,** so nobody can learn that another company's project, skill, group or invite exists. That includes a group or invite opened under the address of a different organization the person is also in.
- **2026-09-30: Leaving an organization takes away its projects, even your own.** Projects stay with the organization, where its owners and admins can still open them.
- **2026-09-30: Groups only take people from their organization,** and adding someone from outside gets the same message as an unknown email, so it doesn't reveal who is on the install.
- **2026-09-30: The migration names the install's organization after the install (ADMIN-001's name) and makes its admins its owners** (the first account when there's no admin). A fresh install gets its organization when its first account signs up.
- **2026-10-01: Each usage row records its project's organization** (`agent_usages.organization_id`), rather than finding an organization's runs through its projects, so a deleted project's runs still count in the organization's usage, as they already do in the person's. Its usage page is the person's Usage page with a breakdown by person added, opened from the account menu (it's a full page, not a settings tab).
- **2026-10-01: Members and the organization's details share one settings tab, Organization.** Everyone in it sees the list; owners and admins change it. Admins switch people between member and admin; making, changing or removing an owner is for owners only, so an admin can't take over or lock out the owners. On a self-hosted install a platform admin counts as an owner.
- **2026-10-01: On a self-hosted install nobody leaves or is removed from its one organization.** Everyone on the install is in it by design, and a removed person would just join again on their next page; an admin deletes the account instead. On the hosted install removing someone also takes them out of the organization's groups.
- **2026-10-01: Changing an organization's address breaks links to the old one.** No redirects from old slugs for now: a slug is chosen once, rarely changed, and keeping old ones would reserve them forever.
- **2026-10-01: The organization switcher is a submenu of the account menu at the bottom of the sidebar, and the app's logo and name are the sidebar's header again, on every install.** Switching organizations is rare, so it shouldn't take the whole top left. The organization's name shows under the user's name in the footer so they still see where they are. Stacking the app's header above a full-width switcher was ruled out earlier because it looked silly. A self-hosted install shows its one organization (named after the install), so the submenu still opens Organization settings. The install's own name and logo (ADMIN-001) stay on sign-in pages, the browser tab and emails.
- **2026-10-01: An organization without a logo shows the install's logo on a self-hosted install, and its initial on the hosted one.** Self-hosted then looks as it did; on the hosted install the droplet for every organization would make them look alike. Organization logos are only served to its members, unlike the install's, which the sign-in page needs.
- **2026-10-01: The Organization submenu lists the user's organizations, opens the organization's settings, and (hosted only) creates one;** switching goes to that organization's new-project page.
- **2026-10-01: The shared props are `currentOrganization` and `userOrganizations`, not `organization`/`organizations`.** A page's own prop with the same name replaces a shared one, and the admin user page's list of that user's organizations did, which crashed the switcher into a blank page.
- **2026-10-02: Anyone on the hosted install can create organizations, with only a name, but while AI credits are on (CREDIT-001) each person can own only one.** The address is made from the name and can be changed in settings. Every organization gets free credits, so unlimited organizations would mean unlimited credits; joining others by invite is unlimited. The limit lifts with paid plans.
- **2026-10-01: Platform admins get Admin → Organizations on the hosted install,** a list with owners and counts that links to the owners' user pages but never into an organization's projects. Searching happens in the browser, like the Users list, until there are too many to send.
- **2026-09-30: Tenancy first, billing later.** Plans and billing attach to the organization, but are a separate piece of work once the boundary is in place.
- **2026-10-01: Tests always run as a single-organization install (`APP_MULTI_TENANT=false` in `phpunit.xml`); tests for the hosted install turn it on themselves.** A local `.env` with `APP_MULTI_TENANT=true` made 83 tests fail with 404s, since their users weren't in the install's organization.

## AI connections and agents

AI-001..007, AGT-001..015, USAGE-001.
Users connect an AI before building; each project picks its agent (OpenCode, Claude Code or Codex), model and reasoning level; runs can be stopped, queued or sent now; prompts can be recalled; attachments work; usage and estimated cost are tracked per agent, model and project.

### Decisions

- **The platform never pools subscriptions.** Every run uses the project owner's own connection. Keys are encrypted and never sent back to the browser.
- **2026-09-29: Claude subscriptions use Claude Code's own sign-in** (`claude auth login` in the Shell tab). No token is stored; pasted setup tokens are refused and saved ones deleted. One sign-in covers all of a user's Docker sandboxes (per-user `CLAUDE_CONFIG_DIR`).
- **2026-09-30: A Docker sandbox with a dead host folder mends itself on its next wake:** the folder is made again and the container restarted, since a bind mount whose source was deleted can't be fixed from inside the container. Only folders under `storage_path` are recreated, never any other path a container mounts. A restart is the cheapest fix (files and home kept); recreating the sandbox would take minutes. Checked in `wake()` because it already runs on project open and the workspace's activity pings, at most every 30 seconds.
- **2026-09-30: Signing out of Claude empties the user's shared login folder; it never deletes it.** Running Docker sandboxes bind-mount that folder, and deleting it left them a dead mount: the next `claude auth login` said "Login successful" but couldn't save, so Claude Code stayed signed out until the sandbox was recreated.
- **2026-10-01: Tests point Docker's `storage_path` at a throwaway temp folder (`Tests\TestCase`), never `storage/app/sandboxes`.** Test users start at id 1, so tests that sign a user out of Claude (`SignOutOfClaude`) emptied the dev user's real shared login: running the suite locally signed every sandbox out of Claude.
- **2026-09-30: A Claude sign-in that succeeds switches the workspace back to the Preview tab.** Once the Shell says "Login successful" there's nothing left to do there; the app is what the user came to see. It only fires when the chat saw Claude Code signed out first, so opening an already-signed-in project doesn't move tabs. The Shell tab stays open, not closed, in case they want its output.
- **2026-09-30: The chat carries on after a Claude sign-in whenever it sees Claude Code signed in while a message waits for one** (the server says so: `waiting_for_sign_in`). It used to need to see "signed out" then "signed in" in the same page load, so switching tabs or reloading during the sign-in left the chat stuck until something else woke it.
- **2026-10-01: The chat keeps trying to pick up a message after a Claude sign-in until it runs or stops waiting.** The resume request once failed (SQLite "database is locked" in the rate limiter) and the chat, already seeing "signed in", stopped checking, so the message never ran. The resume answer now says whether a message still `waiting`; while one is, a failed or unsuccessful try is retried every 5s.
- **2026-09-30: A rejected Claude sign-in is retried once,** because Claude Code refreshing a shared login elsewhere revokes the token a run started with. Rejected twice, Claude Code is signed out in that sandbox so the chat offers to sign in.
- **2026-09-30: "Sign in to Claude" shows whenever a message waits for a sign-in, and each chat's sign-in check has its own rate limit (60 a minute).** The failed message tells the user to click that button, so it can't depend on the check answering. The check used `throttle:30,1`, which Laravel counts in one bucket per user across every route with the same limit: two signed-out chats polling every 5s ran out, the 429 was taken as "don't know", and the button disappeared. A failed check now keeps the last known answer.
- **2026-09-29: A run that failed because Claude Code wasn't signed in is remembered** and re-run once the user signs in.
- **2026-09-30: Codex is a third agent** next to OpenCode and Claude Code. Codex gets the ChatGPT tokens without the refresh token; the platform keeps refreshing it.
- **2026-09-30: AI onboarding is a picker, not a wall of forms.** The user picks one AI from a row of icons, then sees only that provider's setup. Subscriptions come first (Claude subscription, ChatGPT sign-in, OpenRouter sign-in); an API key is the small "instead" link. Gemini is key-only, since Google forbids subscription use. Settings → AI keeps the full list of cards, with Claude also subscription-first there, so both pages agree.
- **2026-09-30: Ollama connects with an Ollama Cloud key, or the user's own server by URL plus an optional Bearer key.** Cloud is the main option; it's models.dev's `ollama-cloud` provider, so OpenCode runs it as-is. The key is checked with `POST ollama.com/api/me`, because Ollama's model list answers without a key.
- **2026-09-30: A user's own Ollama server reuses OpenCode's `ollama-cloud` provider,** with its `baseURL` and the server's models (at zero cost) passed in `OPENCODE_CONFIG_CONTENT`. That keeps model ids, usage and the picker the same as Cloud, and the zero costs stop OpenCode pricing self-hosted runs at Cloud prices. The model list comes from the server's `/api/tags`, cached for an hour.
- **2026-09-30: The platform won't call private, loopback or internal Ollama addresses** (e.g. the cloud metadata address): the URL is user-typed, so this blocks server-side request forgery. The checked address is pinned for the request, and redirects aren't followed. `SANDBOX_OLLAMA_PRIVATE_SERVERS` allows them, and it's on by default when `APP_ENV=local`. There, Docker sandboxes reach a `localhost` server as `host.docker.internal`.
- **2026-09-30: A narrow chat composer shrinks its controls instead of wrapping them.** The model name truncates first, then Autofix (below 32rem) and the agent (below 24rem) drop to icons; the send buttons never shrink. Sizes follow the composer (a container query), not the window, since the chat pane is resizable.
- **2026-09-30: Annotate (AGT-013) takes its picture inside the preview's page** (modern-screenshot, pinned in `docker/sandbox/Dockerfile` and served by `host-proxy.mjs`), so it shows what the user sees: open menus, typed input, scroll position, their signed-in session. Rejected: the sandbox's headless Chromium (a fresh visit loses all of that) and the browser's tab sharing by default (a permission prompt every time). The library loads only when Annotate is clicked. It comes from the sandbox, never from a URL the workspace sends, since any page framing the preview could then run its own script there.
- **2026-09-30: The page only answers its own parent frame, at that frame's origin,** because the picture can show private data.
- **2026-09-30: The picture is the visible viewport, not the whole page.** That's what the user is pointing at, and a long page would be hard to draw on. Fixed headers and scrolled boxes (a dashboard's main column) are moved so the copy matches the screen.
- **2026-09-30: Marks are numbered on the picture, and the agent gets a line per mark naming the element under it,** like a CSS selector (tag, id, first 3 classes, `data-test`) with its text in brackets: `1. Note "too big" on div.card ("Counter")`. The agent can search the code for those instead of guessing from pixels. A box gets the element that fits it best; an arrow or note gets the element at its tip, skipping icons and formatting inside it.
- **2026-09-30: Those lines go to the agent only, never into the chat box or the chat** (`agent_context` on the request, kept in the message's `meta` and added to the agent's prompt). In the chat they read as stray HTML (`<div.card>`), and even as `div.card ("…")` the user saw them as noise they hadn't typed. They belong to the picture in the composer, so removing the picture before sending drops them.
- **2026-09-30: Annotate opens with the Text tool picked,** because a note saying what to change is what users reach for first.
- **2026-09-30: The marked-up picture goes into the chat box as a normal attachment (AGT-006), not sent automatically.** The user still says what to change, and vision-model fallback works as for any image. PNG, or JPEG if the PNG would be over the 10 MB attachment limit.
- **2026-09-30: Pressing an existing mark drags it, whatever tool is picked; pressing anywhere else draws.** Users need to nudge a mark onto the right element, and switching to a separate move tool would be one more step. A mark is hit by its line (within 8px), a note's text, or its number. Undo keeps a history of changes, so it reverses a whole drag or a Clear, not just the last mark added.
- **2026-09-30: Tab sharing is the fallback, offered only after the page fails to answer,** behind its own click, since the browser only lets a click start tab sharing.
- **2026-10-01: Inspect (AGT-014) works on the live page, not a picture:** hover highlights, click picks, drag moves, and Add to chat takes the picture at the end. The agent gets exact elements instead of guesses from where a mark was drawn, and moves show the result before anyone writes code.
- **2026-10-01: No libraries for Inspect; `docker/sandbox/inspector.js` does it in about 600 lines.** Rejected: bippy (it must load before React to hook it, but the inspector loads only when turned on), react-grab (its own UI and clipboard flow, not ours), @medv/finder (our short selector is enough: id, `data-testid`/`data-test`/`name`/`aria-label`, else a path of up to 5 steps using class names that aren't utilities), Moveable/interact.js (only drag is needed, not resize or rotate handles), and Stagewise or Onlook (whole editors). The proxy serves the file from the sandbox, loaded the first time the workspace asks, like the capture library.
- **2026-10-01: Components are read from the page's own DOM:** React's fiber on the element (`__reactFiber$…`): `_debugOwner` for the component, `_debugSource` for file and line (React 18), or the first app file in `_debugStack` (React 19, file only, because the stack isn't source-mapped). Vue's `__vueParentComponent` gives `__name` and `__file`. Production builds have none of these, so the agent gets the selector and text only.
- **2026-10-01: Moves are shown with copies, and the originals are hidden, never moved.** Moving an element React or Vue manages breaks the framework's next update ("removeChild" errors). A copy isn't the framework's, so it can't break it, and stopping removes the copies and shows the originals again. Removing a move from the list puts the page back the same way. The app's code and files never change; the agent makes the move.
- **2026-10-01: Dropping on the outer 30% of an element at either end moves before or after it; the middle 40% swaps.** Along the row for flex rows, inline elements and grid cells, otherwise down the column. Swapping is the common ask ("swap these buttons"), so it gets the biggest area.
- **2026-10-01: The file open in the editor goes with every message automatically, as a chip the user can remove (AGT-015).** Users say "this file" while looking at it; making them attach it each time is a step they'd skip. Only the path is sent, as an `agent_context` note (not in the chat), never the contents: the agent reads the file in the sandbox itself, and a big file would bloat every prompt. Unsaved changes are mentioned, since the agent can't see them.
- **2026-10-01: Removing the chip lasts until another file is opened, not just for one message.** Bringing it back after every send would make the user remove it again and again for the same file.
- **2026-10-01: While inspecting, the page's clicks, presses, drags and form submits are swallowed** (capture-phase listeners on the window), so picking a link or button doesn't use it. Esc in the page stops inspecting, and the inspector stops when the preview reloads, since a reloaded page has lost its picks.
- **2026-09-30: A user's own Ollama server with Nimble pulled answers the platform's checks in Jev's place (AI-007).** Nimble (Bespoke Labs, 9B, Apache 2.0) speaks Jev's API at `/v1/systemone`, so the questions and thresholds are unchanged; only where they're sent differs. It's free for the user, and keeps their prompts and code on the server they chose instead of sending them to OpenRouter. Self-hosted only: Nimble isn't on Ollama Cloud.
- **2026-09-30: Nimble on the server comes before the owner's OpenRouter key.** Someone who points the platform at their own server wants it used. It's found by name (`nimble` or `nimble:*`) in the server's cached model list (an hour), so pulling it takes effect within the hour, and nothing new to set up.
- **2026-09-30: A Nimble failure isn't retried on OpenRouter.** Falling back would quietly send the user's prompts somewhere else, and a down server would make a 3 s message check take two timeouts. It fails open like any Jev failure. Nimble's 8K-token context is smaller than Jev's, so the largest states (a long REQ.md, eight failing tests) can fail there; left as is until it shows up.
- **2026-09-30: Nimble is called through the same pinned, no-redirect, private-address-guarded request as the server's model list,** because the URL is user-typed (AI-006).
- **2026-09-30: The abuse check (PUB-003) never uses Nimble,** for the same reason it never uses the owner's OpenRouter key: an abuser's own server could answer whatever it liked.
- **Agent CLIs are pinned in `docker/sandbox/Dockerfile`.** Bumping one means re-checking its events parser (`OpenCodeEvents`, `ClaudeCodeEvents`, `CodexEvents`) against the CLI's real output.
- **2026-10-02: Usage counts only money spent as cost; runs on a Claude or ChatGPT plan say "Included", with their API-price estimate in small type.** Showing every run at API prices (even subscription ones, so models could be compared) read like a bill: the user, on Claude Max, saw $59 they never paid. Each run now records what paid for it (`agent_usages.paid_by`: AI credits, plan, API key, own server), from how the owner connected that provider; earlier runs were filled in the same way from today's connections, and ones whose provider is gone stay unknown and count as spent. Own-server runs say "Free". The estimate is still kept, so the comparison isn't lost. The AI credits balance is the page's biggest number, the spent total below it smaller: the user found a $0.00 headline outshining the credits. The card and its bars are neutral (no purple: nothing else in OneDrop uses it, and amber already means a warning); colour only warns, amber under $0.50 and red at $0, as beside the model picker.
- **Laravel by default (AGT-008):** asking for React, TypeScript, Tailwind or a landing page still gets the Laravel starter kit, which already uses them. Only a named framework, "no server", or an existing app changes it.
- **2026-09-30: An agent error none of the `Str::contains` patterns match gets a second look from Jev (AGT-010); the patterns stay.** They're instant, free and exact for the errors we've seen; Jev only handles the rest, choosing among the same causes (bad key, out of credits, rate limited, model unavailable, context too long, network, or other) from the error (its last 2,000 characters).
- **2026-09-30: The generic message is posted at once, then replaced in place by the cause's message when Jev is at least 70% sure,** from a queued job, since the events arrive in the sandbox's webhook request. Replacing, not a second message, so the chat doesn't explain one failure twice. "Other", an unsure answer, a Jev failure or no key keep the generic message; so does a message that changed meanwhile.
- **2026-09-30: Each harness words each cause itself (`AgentEvents::failureMessage()`), reusing its existing messages,** so Claude Code still says "Claude is overloaded" and Codex on a ChatGPT sign-in still points at signing in again. Causes no harness had a message for (rate limited, context too long, network) got new generic ones. A Claude subscription's "bad key" asks to sign in again but doesn't queue the message to re-run, since that only happens for the known "Not logged in" case.
- **2026-09-30: Every chat message is checked by Jev once, with all the questions that apply in one `decide()` call and a 3 s timeout** (`MessageChecks`): a secret, an earlier decision, queue or interrupt, and Auto's size. ## Sandboxes

SBX-001..009, TOOL-001, and every workspace tool (DB-001, SECRET-001..002, STORE-001, FLAG-001, MON-001, APPAUTH-001..002, GROW-001..003, RT-001).
One sandbox per project, on Docker locally and Runtime Cloud (or Blaxel) in production, kept up to date, checkpointed after every turn, backed up outside the provider, and suspended when idle.

### Decisions

- **One image definition** (`docker/sandbox/Dockerfile`) for every provider; nothing provider-specific in it except Blaxel's extra steps in `docker/sandbox/blaxel`.
- **No secrets in images or repos.** The user's AI credential is injected per run.
- **2026-09-28: Each sandbox is driven by the provider it was created on** (`RoutingSandboxProvider`); `SANDBOX_PROVIDER` only picks where new ones go. A project on another provider counts as outdated, so the normal update moves it.
- **2026-09-28: Updates keep all of `/home/sandbox`,** not just the agent's history, because agents install things there (a project's Postgres lived in `/home/sandbox/pgsql`).
- **2026-09-28: The old sandbox is deleted only after the new one has every kept file.** Any failure before that deletes the new one and puts the project back on the old one, unfrozen. (A queue timeout redelivering a long update job once lost a project's database.)
- **2026-10-01: Docker sandboxes copy kept files through tar, not plain `docker cp`.** Docker refuses to unpack a relative symlink that climbs out of the folder it copies into, both ways (`corepack enable` leaves `~/.local/bin/pnpm -> ../../../../usr/lib/...`), so every update of that sandbox failed and the preview sat on "Updating sandbox…". Out: `docker cp … -` unpacked by the host's tar (works on a stopped container). In: the host's tar unpacked by the new container's tar.
- **2026-09-28: Freezing for a copy always has a watchdog** that thaws the app after the longest an update may run, so a deploy that cuts an update off never leaves an app frozen.
- **2026-09-30: Build steps that run as the sandbox user set `HOME=/home/sandbox` on the step itself,** because Runtime's builder keeps `HOME=/root` after `USER` (Docker doesn't), and npx then can't write its cache. Not an image-wide `ENV HOME`, which would change the `HOME` Runtime gives sandboxes.
- **2026-10-01: Old Runtime image versions are deleted hourly and right before each `sandbox:build-image` on Runtime (`sandbox:prune-images`),** because Runtime charges $0.08/GB-month for every stored image (~4.8 GB each), caps how many an account holds (a build failed with "Image quota exceeded" at 20), and every build leaves one behind. Daily was too slow, and the prune only looked at the current name, so the 14 images from before the rename (`zap-sandbox`, plus a `zap-probe` from trying Runtime out) were never deleted, 5 of them failed builds. The GitHub `runtime image` workflow doesn't prune first, since it has no PHP app; the hourly run covers it. Kept: the current version (deleting it would also drop its build checkpoints), newer builds (a failed one holds the checkpoints its fix starts from), and any version a running, paused or stopped-persistent sandbox came from (read from its image label, `zap.image` for sandboxes made before the rename), since we don't know that a paused sandbox wakes without its image. Only the configured image's name and its former names (`RuntimeSandboxProvider::FORMER_IMAGE_NAMES`) are touched, never other images on the account; the current version is never deleted, whatever the listing says. It runs whenever `RUNTIME_API_KEY` is set, not only with `SANDBOX_PROVIDER=runtime`, because Runtime sandboxes outlive a provider switch.
- **2026-09-29: `sandbox:update` suspends each sandbox it updated,** to stay within Runtime's trial limit of 8 running sandboxes.
- **2026-10-01: While a new sandbox is made for an update, the preview shows the "Updating sandbox…" placeholder, not the app; only then, not while the update waits in the queue.** The sandbox row keeps its old preview address until the new one is up, and the old sandbox is frozen for the copy, so on servers the iframe showed the browser's "unable to connect" page. The iframe comes back (a fresh load) once the update is done. The placeholder used to show from the moment the job was queued: a 12-second swap showed it for minutes behind agent runs on the one queue, and for 15 minutes after a job that failed before it started.
- **2026-10-01: Sandboxes update once their project has gone unused for 10 minutes (`UpdateSandbox`), never when it's opened or before an agent run.** Updating on open put it on the user's time, exactly when they wanted the project. Not every sandbox after each image build, because that wakes and rebuilds dormant ones for nothing (cost, and Runtime's trial cap of 8 running); a sandbox nobody uses is updated after its next use. Not on a schedule: Laravel Cloud wakes a sleeping app for every scheduled task. Instead each use (`Sandbox::markActive()`) queues one delayed job per project, put back while the project is in use or its agent works; it suspends the sandbox again afterwards. Only Main's sandbox: task copies are made from it and don't live long.
- **2026-10-01: Changed tool files are copied into the running sandbox (`SandboxTools`) instead of making a new one.** Of about 110 file changes to `docker/sandbox` in the week before, 13 touched the Dockerfile; the rest were files it copies into `/opt/onedrop` (the proxy, the forwarder, `start.sh`, guides, the PHP tools). Which files differ is decided by hashing them in the sandbox against the app's own `docker/sandbox` (one command; remembered per sandbox until the source changes), so there's no version file to keep in step, only the changed files are copied, and locally a script change no longer needs an image rebuild. The tool files are read from the Dockerfile's `COPY … /opt/onedrop` lines, and a test fails for any file in `docker/sandbox` that's neither a tool nor a base file. Processes that load a file once (the proxy, the file watcher, sshd) are restarted with `pkill`; `start.sh`'s loops start them again. Before an agent run, and before a task's copy, changed tool files are copied in too (a second or two) so the agent has the current guides; a new sandbox never is.
- **2026-10-01: A new sandbox is made only when the image's base changed: `Dockerfile`, `start.sh` (the container's main process), `dockerd` (the sandbox user's only sudo rule, so it stays root's) and `shell-keys.js` (built into `shell.html` with ttyd's page at build time).** The image keeps a copy of them in `/opt/onedrop-base` so the platform can tell which base a sandbox has. A sandbox on an older base gets no tool files until a newer image is built, then a new sandbox: scripts written for a newer base may call what the older one lacks. Sandboxes made before the copy existed count as an older base, so each gets one new sandbox after the first image with it.
- **2026-10-01: On Blaxel, tool files can't be copied in,** because its sandbox API runs everything as the sandbox user and `/opt/onedrop` is root's (making it the sandbox user's would let it rewrite `dockerd`, its sudo rule). A rebuilt image gives Blaxel sandboxes a new one, as before.
- **2026-10-01: No forced update when a project is opened, for now.** Every image change so far works with older sandboxes until they're next idle. If one ever has to reach a sandbox before that (a protocol change between the app and the forwarder), add a minimum version then.
- **2026-10-01: The one-container install's app image keeps `docker/sandbox`** (no longer in `.dockerignore`), so it can copy tool files into its sandboxes; without it, only a new image updates them.
- **`RUNTIME_FUNDING=trial` until the owner says to use paid credit.**
- **Code backups (git bundles) live on a disk outside every sandbox provider,** so a lost sandbox can get its code back.
- **2026-09-30: A queued project backup whose project was deleted is dropped (`DeleteWhenMissingModels`), not failed,** since there's nothing left to back up; it had shown up on Laravel Cloud as a failed job.
- **2026-09-29: Share cards, icons, attachments and backups use the app's default disk,** because on Laravel Cloud web and queue instances don't share a local disk.
- **Checkpoints never include `node_modules`, `vendor`, `.cache` or `.env`,** whatever the app's `.gitignore` says.
- **2026-09-28: The sandbox's host proxy rewrites `localhost` links** to the visitor's address, so apps that ignore `X-Forwarded-Host` work in previews without per-app config.
- **2026-10-01: The host proxy drops `X-Frame-Options` and CSP `frame-ancestors` on preview responses, never on published ones.** The preview is the app in the workspace's iframe, so Chatwoot (Rails' default `SAMEORIGIN`) showed only the browser's broken-page icon while the app ran fine. Published addresses are opened directly by visitors, so they keep the app's clickjacking protection. Rejected: asking the agent to change each app's headers, since it means editing a template's config.

- **2026-10-02: Docker inside sandboxes on Runtime first, Blaxel later.** Tested both: Runtime's VMs have an ext4 root and `sudo`, so Docker runs with overlayfs and no extra volume, and compose stacks survive pause/resume. Blaxel's root is overlay (Docker falls back to the slow `vfs` driver) and its sandbox API holds port 8080, which compose stacks often publish.
- **2026-10-02: Whether new projects can run Docker is asked of the provider they run on (`SandboxProviders::runsDocker`),** each answering from its own setting. Free apps on prod said Docker was off while it was on for Runtime, because only the Docker provider's setting was read.

Privileged is refused outside a local install. - **2026-10-02: Tools → Database also finds database containers in the sandbox's Docker** (DB-001), because a self-hosted Supabase stack's Postgres (`db`) is set only in the container's env (`POSTGRES_PASSWORD`, `POSTGRES_HOST=db`), with no URL the tool could read, and a host like `db` resolves only inside the compose network. No d3/topojson/Leaflet, because dependencies need approval and tiles would be an outside service seeing every viewer. Antarctica is left out (no visitors, lots of space). Countries use the sequential blue ramp (log scale, 5 steps; the dark ramp starts brighter so one visitor still shows against land), cities the orange hue, per the dataviz skill.
- **2026-09-30: A chat message that looks like it has a secret is held before it reaches the agent, offering to save it in Secrets instead (SECRET-002).** Sending the message to Jev to ask is acceptable: it goes to the user's own AI anyway. It's held when Jev is at least 70% sure (live: a Stripe key 0.86, an OpenAI key 0.77, a password 0.96, a database URL 0.97; placeholders and "add a password field" 0.03).
- **2026-09-30: The platform finds the secret's value itself, and Jev only chooses between candidates.** Jev answers with probabilities, not text, so candidates are pulled from the message (database URLs with a password, `NAME=value` values, words of 8+ characters mixing letters and digits); with several, a Jev choice question picks one. When none fits ("my password is swordfish"), the user pastes the value into a second field. It's saved only if it's in the message.
- **2026-09-30: The name is suggested without Jev:** the name it's assigned to (`MAILGUN_KEY=…`), else a known prefix (`sk_live_` → `STRIPE_SECRET_KEY`, `sk-ant-` → `ANTHROPIC_API_KEY`, `ghp_` → `GITHUB_TOKEN`…), a URL scheme (`postgres://` → `DATABASE_URL`), else the words before it ("the admin password is" → `ADMIN_PASSWORD`), else `SECRET`.
- **2026-09-30: The secret's value is never flashed, cached or logged by the platform.** The hold shows only its first four characters; on save the value is found again from the message the composer resends. The saved message reads "(saved as NAME in Secrets)" in its place. An existing name isn't overwritten (the user picks another), unlike Tools → Secrets' confirm-to-replace, to keep the prompt to one step.
- **2026-09-30: In a task's chat, the secret goes into the task's own copy while it has a running one, otherwise Main's** (which the copy is made from), since that's where the agent reads it.
- **2026-10-01: A project's state lives on the snapshot disk, not only in its sandbox (SBX-009),** so switching providers, or a provider deleting a sandbox, never costs files or a slow move. Before, a move copied everything out of the old sandbox to the platform's disk and back in, with the app frozen, and needed the old sandbox to still exist; without it only the git bundle came back (no uncommitted work, home folder, database or dependencies). Cost decides providers, so they have to be cheap to leave.
- **2026-10-01: Snapshots work on every kind of install: an S3-compatible bucket on Laravel Cloud and AWS (signed links, straight between sandbox and bucket), and the local disk on a laptop or single server, where sandboxes are Docker on the same machine and the platform packs and copies with `docker cp`.** The bytes never pass through PHP over HTTP, which would be slow (`php artisan serve` handles one request at a time) and tie up the app; so Laravel's signed upload routes for local disks aren't used. Remote sandboxes with a local disk take no snapshots rather than falling back to PHP. No self-run S3 server (MinIO) for single servers: one more service to run and update; a local disk with an optional off-site bucket is simpler. A local disk isn't an off-site backup, which the docs say.
- **2026-10-01: Snapshots are layers (`workspace`, `deps`, `home`, `storage`), each fingerprinted in the sandbox and only packed and stored again when it changed;** stored files are named by their fingerprint, so an unchanged layer is shared between snapshots. Fingerprints are file names, sizes and times (cheap for big trees), except dependencies, keyed by the lockfiles and the list of dependency folders so a 500 MB `node_modules` isn't walked or uploaded after every turn. Only the top-level `vendor` counts as dependencies: a source folder named `vendor` deeper down is the app's own. zstd (multi-threaded) where the image has it, gzip otherwise. Not restic or another incremental tool inside layers: a new dependency in the image, revisited only if layers are routinely large.
- **2026-10-01: The app is frozen (SIGSTOP of the sandbox user's processes, with a watchdog that thaws them after two minutes) only while the stateful layers are packed into the sandbox's `/tmp`, not while they upload;** dependencies are packed after it's thawed. For an update, the old sandbox is stopped once its snapshot is taken, so nothing it does afterwards is lost.
- **2026-10-01: The snapshot tool (`/opt/onedrop/snapshot`) is copied into sandboxes on any base (`SandboxTools::ANY_BASE`),** since it only needs bash, coreutils, tar and curl, so existing sandboxes get snapshots without waiting for a new one.
- **2026-10-01: Kept: the latest 10 snapshots and the newest of each of the last 7 days per project, pruned daily with the daily snapshot (04:00).** Daily on Laravel Cloud is fine; only frequent tasks keep a sleeping app awake. Admins list and restore with `sandbox:restore`; an admin page for snapshots is left for later.
- **2026-10-01: Layers over 5 GB aren't supported over signed links yet** (one PUT per layer; S3 and R2 cap a single PUT at 5 GB), and each pack, upload and restore must finish within the provider's two-minute command limit. Multipart uploads and running long ones detached come when a project needs them.
- **2026-10-01: Sandboxes get signed links per upload and download, never storage credentials,** keeping "no secrets in sandboxes"; and the bytes go straight between sandbox and storage, not through the platform, so moves run at datacenter speed and in parallel.
- **2026-10-01: Runtime is production, chosen on cost, with Blaxel as the fallback.** Runtime bills CPU used ($0.025/vCPU-hour, $0.0075/GiB-hour), about $0.03/hour for a 2 vCPU / 4 GiB sandbox waiting on the model, against ~$0.166/hour on Blaxel, E2B or Daytona, which bill resources held. Its risks (a 2026 company, API on one OVH address, a trial capped at 10 image builds a day) are why leaving it has to be cheap. Blaxel's free tier was ruled out as the main host because it deletes sandboxes after 7 days.
- **2026-10-01: The `runtime image` workflow's builds count against Runtime's trial (10 a day, 1 at once) until the account has bought credit;** credit makes builds free and allows 4 at once. The account had no credit, only trial hours.

## Previews, publishing and sharing

PUB-001..003, GW-001..002, REM-001, SHARE-001..002, HOME-002.
Every app is reachable while it's built; publish to Tailscale or to the server's own domain, Private or Public; share a project on a public page with a preview card and Remix.

### Decisions

- **Every path to a sandbox goes through the platform's auth check** (`SandboxGatewayController`). Never hand out a provider's own preview URL.
- **2026-09-29: On Laravel Cloud, previews and shells go through a Cloudflare Worker** on `*.<domain>`, because Blaxel's and Runtime's preview cookies don't work inside OneDrop's frame (Runtime didn't load at all; Blaxel lost CSS/JS in Safari). The browser only ever sees OneDrop addresses and cookies.
- **2026-10-02: The Cloudflare Worker tells the sandbox's proxy which address the browser used (`X-OneDrop-Host`, always set by the Worker, stripped by Caddy), and the proxy uses it instead of Host to localize Origin/Referer and as the app's `X-Forwarded-Host`.** The Worker fetches the provider's address, so Host there is the provider's: the proxy didn't see the page's own Origin as same-site and passed `https://preview-25.onedrop.io` on unchanged, and Plausible's LiveView (Phoenix `check_origin`, against `BASE_URL=http://localhost:8000`) refused every WebSocket. A custom header, not `X-Forwarded-Host`, because providers' proxies may set that themselves; `X-OneDrop-Geo-*` already proved custom headers get through. Rejected: setting each app's base URL to the preview address, since templates are set up for localhost on purpose (the proxy maps it) and the address changes when the app is published.
- **2026-09-30: Publish targets: Your domain or Tailscale,** remembered per project. Private on your domain means anyone in the project's organization (ORG-007), not only the project's people. A project named like a preview address gets an `app-` prefix so it can't take one over.
- **2026-09-30: Tailscale publishing checks the node's capabilities (`https`, and `funnel` for Public) before running `tailscale serve`/`funnel`, and waits for them.** With Funnel off, `tailscale funnel` prints an enable link and blocks until someone turns it on; our timeout killed the job and left the project "Publishing…" forever while the command kept waiting in the container (so the URL later worked but the panel never updated). Now the panel links to the setting and publishing carries on once it's on. Both publishing jobs also mark the project Failed if they crash.
- **2026-09-29: Share cards are rendered in the sandbox** with headless Chromium (1200×630, prompt beside the app).
- **2026-09-30: On the hosted install, Jev checks an app for abuse before it's published as Public or after it's shared (PUB-003).** Anyone can sign up there and put an app on a public address or a OneDrop share page, so phishing pages, scams and malware are the platform's problem. Private publishing isn't checked (only the organization or the tailnet can open it), and self-hosted installs aren't (the owner runs the server).
- **2026-09-30: The abuse check uses the platform's OpenRouter key (`Jev::platformKey()`), never the owner's; without one there's no check.** It's the platform's protection, so the owner shouldn't pay for it, and an abuser could otherwise skip it by connecting a key that fails.
- **2026-09-30: Jev never blocks anything by itself: above 0.8 on any question (phishing, scam or malware, otherwise harmful) the publish or share is held for a platform admin, who approves it or takes it down.** One probabilistic answer isn't enough to refuse someone; a person decides. 0.8 was tuned live: a PayPal copy (0.99), a "Chase" login (0.92), an ETH giveaway (0.99), a cracked-download page (0.97) and a doxxing page (0.98) were over it; a todo app, a SaaS's own sign-in, an Instagram clone (0.35), a Netflix clone (0.30), a bakery with checkout and a crypto tracker were well under it.
- **2026-09-30: The abuse check fails open: if Jev errors or times out (15 s), the app publishes as normal and the exception is reported.** Jev being down shouldn't stop every publish on the hosted install; the daily re-check catches it later. Rejected: failing closed, which would turn every Jev outage into a publishing outage for everyone.
- **2026-09-30: The publish check runs inside the queued PublishProject job, before the endpoint starts; the share check is its own queued job (CheckForAbuse) after the share is saved.** Publishing is already asynchronous, so the check adds no request latency (the panel just says Publishing… a few seconds longer). The share page is visible for those few seconds; its slug is unguessable and only the owner has the link yet, so hiding it until the check ends wasn't worth the extra state.
- **2026-09-30: Jev sees the project's name, its first 2 and latest 8 prompts (500 characters each), and the home page as headless Chromium renders it (falling back to curl): title, visible text (3,000 characters), up to 30 form fields and up to 10 form targets.** Most apps render client-side, so the raw HTML is often empty; form targets show where credentials would go. Chromium is already in the sandbox image (share cards), so no image change. Only a held check keeps that evidence (for the admin); a clear one keeps just the probabilities.
- **2026-09-30: A held app is offline for the public, not deleted:** its publish status becomes `review` (the Tailscale/Funnel endpoint is stopped) and its share page is a 404. Approving republishes it; publishing publicly again while held stays held without another Jev call.
- **2026-09-30: An approval stands until the owner sends the agent another message; after that, the next public publish or share is checked again.** Admins shouldn't have to re-approve the same app, but an approved app the agent then changes is a new app.
- **2026-09-30: Public or shared apps are re-checked after a successful main-chat agent turn, at most once a day per project** (cache key, 20 s after the turn). Cheap enough to run for every public app, and catches an app that turns into phishing after it was published. Task turns aren't re-checked separately; applying a task's work to main doesn't run the check (noted, not built).

## Git

GIT-001..012.
History, commit/discard, branches, restore, push/pull, the GitHub App, commit and push from the header, pull requests, combining commits, hunk/line staging, undoing the last commit, asking the agent about a change, and readable diffs.

### Decisions

- **2026-09-29: Remotes are HTTPS only;** the local bundle steps (git's `file` transport) are exempt.
- **2026-09-30: Commit, push and Create PR live in a split button next to Share,** so the everyday steps don't need Tools → Git. With no remote it says "Commit" and its menu offers "Connect a repository…" (opening Tools → Git).
- **2026-09-30: There is one commit dialog,** "Commit changes", used by the header and by Tools → Git (which lost its inline message box), so reviewing and committing work the same everywhere.
- **2026-09-30: The commit message is optional; left blank, the project's own AI writes it** (the same one-off run as project naming), falling back to naming the files. Pull request text and combined-commit messages work the same way. The AI never blocks the action: every AI-written text has a plain fallback.
- **2026-09-30: "Default branch" means `main` or `master`,** a guess: the sandbox doesn't know the remote's real default. Pull requests go into it by default.
- **2026-09-30: Parts of files are picked at commit time; there's no lasting staging area.** The agent's checkpoint adds everything after every turn, so anything staged by hand would be swept into its next commit. Picking rebuilds the index from the last commit for each commit.
- **2026-09-30: The browser sends which lines to leave out plus a hash of the diff it showed, never patch text;** the sandbox rebuilds the patch and refuses ("This file changed. Review it again.") when the hash doesn't match, so a commit is always what the user saw. Only edited or new text files can be split; deleted, renamed and binary files go whole. Discarding a hunk is for edited files only.
- **2026-09-30: Sandboxes on an older git tool fall back quietly:** without line counts the Edit button is hidden (an old tool would commit every file), and without a diff hash parts can't be picked or discarded.
- **2026-09-30: Pull requests open GitHub's own new pull request page with the title and description in the link,** rather than being created through the API: it works for token and GitHub App remotes alike without asking for pull request permissions, and the user finishes on GitHub. Create PR says why it isn't available instead of hiding.
- **2026-09-30: Combining and undoing only touch commits no remote branch has,** so pushing never needs to overwrite (force-push) the remote. Combining refuses merges and uncommitted changes; undo refuses the first commit and merges, and checks the newest commit is still the one shown.
- **2026-09-30: "Ask" puts the hunk in the chat box and doesn't send it,** so the user writes the question; the dialog closes and the chat box keeps the focus.
- **2026-09-30: Diffs are colored with the CodeMirror grammars the chat already uses,** no new dependency. Changed words are found by comparing a removed line with the added line paired with it (common start and end, by whole words). Hiding whitespace is done in the browser, so picking and discarding wait until whitespace is shown again (the lines must match what the sandbox sees).

SKILL-001..004. Reusable instructions for the agent in the open Agent Skills format (a folder with a `SKILL.md`). Two kinds: a user's own skills, kept by the app and turned on per project, and project skills committed in the repo.

### Decisions

- **2026-09-30: Both a library and project skills,** because a team wants the same skill across projects (library) and a skill that travels with one repo (project). Library skills live in the app's database, never in the repo.
- **2026-09-30: Sharing is all or nothing: private, or everyone in the skill's organization (ORG-007).** No per-group or per-person picker for now. Only the owner (or an admin) edits a shared skill. Stopping sharing turns it off in other people's projects, so nobody keeps running a skill they can't see anymore.

"Create with agent" writes a project skill in `.agents/skills` (following `guides/skills.md`), because the agent works on the repo; "Save to your skills" copies it into the library.
- **2026-09-30: The app puts skills in place before each run** (`SandboxSkills`, `docker/sandbox/skills.php`): library skills go to `~/.claude/skills` for Claude Code and `~/.agents/skills` for OpenCode and Codex. The bundle is only uploaded when it changed (the sandbox keeps a hash), so an unchanged run costs one exec. Only one of the two folders is filled at a time, because OpenCode reads both and would see every skill twice.
- **2026-09-30: Every agent sees every project skill.** Claude Code only reads `.claude/skills` and Codex only `.agents/skills`, so project skills from the other folders are copied into the agent's home skills folder. New project skills go in `.agents/skills`, the open standard's folder.
- **2026-09-30: The sandbox tracks what it installed** (`~/.onedrop/skills/installed.json`) and only removes those, so skills a user put in `~/.claude/skills` by hand are left alone, and win over one of ours with the same name.

- **2026-09-30: Saving a project skill to the library skips symlinks,** so a shared skill can't pull in files from outside its folder.
- **2026-09-30: SKILL.md's frontmatter is read by a small parser,** not symfony/yaml, because that's only a dev dependency here. Editing a skill rewrites only `name` and `description` and keeps its other keys (license, allowed-tools, ...).

## Requirements tracking

REQ-001..003, TEST-001..008. The agent in a user's app keeps that app's requirements the way this repo keeps its own: what the user asked for ("User should be able to…" with IDs) and every decision behind it, with the reason, and backs each with browser tests it runs as it works. The user reads the requirements in a Requirements tab to check the agent understood, and watches the tests' recordings in a Tests tab; the agent reads them so it doesn't undo an earlier choice.

### Decisions

- **2026-09-30: One file, `.onedrop/REQ.md`, holding both the stories and the decisions.** This repo splits them into `SPEC.md` and `REQ.md`, but for a non-developer one page per area (its stories, then its decisions) is easier to read and review. It lives in `.onedrop/`, the platform's folder, so an app that has its own `REQ.md` or `SPEC.md` never gets it overwritten; it's still committed and backed up with the app.
- **2026-09-30: On by default for every project, existing ones included,** with a switch in the Requirements tab and in Tools → Agent Skills. Turning it off only stops the agent adding to it; the file stays.
- **2026-09-30: Delivered as extra instructions, not as a skill.** The forwarder appends `guides/requirements.md` to the agent's instructions when `APP_REQUIREMENTS=1` (a copy of `opencode.json` listing it, for OpenCode), so every run follows it. A skill is only loaded when the agent decides it's relevant, and this has to happen on every change. The switch is shown among the skills because that's where users look for how the agent behaves.
- **2026-09-30: The agent writes it in the same turn as the change, in the user's words,** and skips questions and changes that don't touch what the app does. For an app that already exists it only records requests from now on; it doesn't invent history.
- **2026-09-30: The tab reads Main's sandbox** (like Files); tasks write to their own copy and their additions arrive with Apply to Main.
- **2026-09-30: Playwright Test for every stack, not Pest's browser plugin for Laravel apps,** so there's one format to run, parse and record, with video and traces built in. Tests live in `tests/e2e` and are committed with the app.
- **2026-09-30: The platform's own Playwright config runs them** (`docker/sandbox/playwright.config.mjs`), not the app's: the preview's dev server as `baseURL`, one worker (the tests share the app's one database), a video and a trace of every test, and the image's Debian Chromium, so no browser download. Only Playwright's ffmpeg (for video) is needed; the image has the pinned version's (1.63.0, which the guide tells the agent to install), and an app on another version fetches its own once.
- **2026-09-30: Tests are linked to requirements by Playwright tags** (`{ tag: '@REQ-001' }`, or `@REQ-001` in the title). A test can check several; untagged ones are listed under "Not linked". The Requirements tab badges each `REQ-NNN` heading, and the Tests tab names each group from REQ.md.
- **2026-09-30: The agent runs the tests of what it touched before finishing (`/opt/onedrop/run-tests @REQ-003`), and the user can run all, a requirement's, or one from the tab.** Runs from the tab happen in the sandbox in the background (`tests.mjs run --background`) and the tab polls a state file, so Laravel never waits on a run. One run at a time.
- **2026-09-30: Only each test's latest result and recording is kept,** in `.onedrop/tests` (excluded from git by the checkpoint), each run in its own folder so running one test keeps the others' videos; folders no result points to are deleted. Videos are fetched whole into the browser so they can be scrubbed through.
- **2026-09-30: Tests are a required step of the requirements checklist, not a separate guide the agent may skip, on every stack and from the turn that first builds the app.** In the first version the agent kept REQ.md on every turn but wrote no tests for a small change ("+5 button"), and requirements from before tests existed never got any. Later, Claude Code built a plain Vite counter and skipped both REQ.md and tests because the app was "not the Laravel starter" and "minimal". Both guides now say a turn that changes the app isn't done until its requirements have passing tests, that this holds for any stack and however small the app, that the first request is the first requirement, and to backfill tests for requirements without them. The Tests tab also lists requirements without tests with a "Write them with agent" button, like Feature Flags' agent actions.
- **2026-09-30: Watching and interacting with tests is Playwright's own UI mode, opened in its own window.** It already shows each step's DOM snapshot, timings, source, console and network, picks locators, and reruns on file changes (watch mode), so no custom live viewer. Its own window because there's more room, and because an iframe couldn't carry its cookie across hosts over local http. Not a headed browser over VNC: heavier (a display server per sandbox) for little more than UI mode's snapshots give.
- **2026-09-30: The runner goes through the preview's host proxy under `/__onedrop/tests-ui/`, not a new port,** so every provider and the server gateway work unchanged. It's guarded by a random token per runner, handed out by the app only to people who can change the project and traded for an HttpOnly cookie scoped to that path, and it's never served on a published address. Relying on the preview hostname alone wasn't enough: Blaxel and Runtime preview URLs are public, and the runner can run code. Its port is reserved so `routes.json` can't expose it.
- **2026-09-30: The runner stops after 30 minutes unused** (the proxy notes every request and open socket), so a forgotten window doesn't hold a Node process and browsers in the sandbox. Runs made in it don't update the Tests tab's results, which come from the tab's and the agent's runs.
- **2026-09-30: Taking over a test's page means a live browser streamed into the workspace, starting from a step of an existing test.** The user chose exact state (open dialogs, form input) over handing the page to the Preview with only its cookies and address, and steps of a test over scenarios written from chat. The stream is the debugging protocol's screencast, and input goes back the same way, so no display server.
- **2026-09-30: A taken-over test can carry on (TEST-006): one more step, or to its end,** by waking its worker (SIGCONT) after writing how far to go to a control file the preload reads on waking; it pauses again after the step, or at its end before the teardown that would close the page. Resumed steps wait 500 ms each (the worker blocks with `Atomics.wait`, the browser carries on), since steps run too fast to follow otherwise; not Playwright's `slowMo`, which would also slow the run up to the step and can't change mid-run. A failing step is reported with Playwright's own message, and the page stays open.
- **2026-09-30: Tests run in the Browser tab have no timeout.** Their timeout's clock runs on wall time, so a test paused for longer than 30 seconds would time out the moment it resumed.
- **2026-09-30: A test stops at its step by freezing its worker (SIGSTOP) from inside it,** in a preload (`test-steps.mjs`) that watches the step reports a worker sends just before each step. That's the only point before the next action reaches the browser; patching Playwright's internals isn't possible in 1.63 (it's one bundle), and stopping from the runner's reporter would be too late. The browser is its own process and keeps the page. The same preload records every test's steps during normal runs, for the step list.

## App tables

TABLE-001..008.
Apps that keep lists of records get Airtable's table: a spreadsheet-like grid, rich field types, fields and formulas people add themselves, linked records with lookups and rollups, saved views (grid, board, calendar, gallery), an expanded record with comments and history, and CSV import and export. The rest stays a custom app: its own pages, roles, logic and public forms.

### Decisions

- **2026-10-02: Apps built from Airtable-like templates should feel like Airtable in their tables, without becoming an Airtable clone.** People expect to edit cells in place, paste from a spreadsheet, add a field in seconds and save filtered views; the agent-built app is what makes them better than Airtable (any layout, real roles, real logic), so that part isn't replaced by a generic database UI. People who want Airtable itself can install an open-source one (Baserow, NocoDB, Teable) from the free apps.
- **2026-10-02: The table kit is code copied into each app (`/opt/onedrop/kit tables`), not a Composer or npm package.** The app owns it, so the agent can change any part for that app, and nothing is fetched from outside. Every app gets the same tested grid instead of the agent improvising one each time. A newer kit only reaches apps that install it afterwards; apps keep the copy they have.
- **2026-10-02: The grid is our own, on `@tanstack/react-virtual`, styled like the starter kit's shadcn components.** Rejected: Glide Data Grid (its stable release doesn't support React 19, and its canvas cells don't look like the rest of the app), AG Grid Community (heavy, with range selection, fill and grouping in its paid edition), Handsontable (its free license is non-commercial only), HyperFormula for formulas (GPL).
- **2026-10-02: Fields the app was built with are real database columns the agent declares in a table class; fields people add are kept in a `custom_fields` JSON column, described in `table_fields`.** The app's own code (pages, rules, reports) keeps working on its columns, while people can still add fields without the agent. Built-in fields can't be renamed, retyped or deleted from the grid, since the app's code relies on them. Rejected: keeping every field as data (a Baserow-style engine), which would make the app's own features harder to build than with plain models.
- **2026-10-02: A table's records are all sent to the browser (up to `tables.max_rows`, 5,000 by default), which filters, sorts, groups and summarizes them.** Views then change instantly and work for formula and lookup fields, which SQL can't sort by. Airtable works the same way. Tables expected to outgrow that should get their own paged pages from the agent.
- **2026-10-02: Formulas are worked out on the server only, in one PHP evaluator, and stored with field keys rather than names,** so there's one set of rules, and renaming a field doesn't break formulas that use it. The browser shows names, and gets each record's results with the record.
- **2026-10-02: The other table's side of a link (TABLE-005) is read-only for now;** links are changed from the field they were added on. @mentions in comments don't notify anyone yet.
- **2026-10-02: No form, timeline or Gantt views, automations or API in the kit.** An app's own pages and public forms do the form's job better, and automations are what the agent writes as code.
- **2026-10-02: The table kit is where an app starts for its record lists, not its whole shape.** The user's worry was ending up with "a slower Airtable". The agent starts from the kit for lists people edit, and still builds the app's own pages around them (home page, dashboards, public forms, screens shaped around the work), so each app does what Airtable can't. The instructions say so; an earlier "don't build your own table" line was dropped as pushing every app towards the same look.
- **2026-10-02: Every template's prompt asks for spreadsheet-like lists (`AppTemplate::SPREADSHEET`, before "Add some sample data…"),** so apps from Airtable-like templates get the table kit, and the user sees what they're asking for.
- **2026-10-02: The kit's tests are PHPUnit classes, with fixture tables prefixed `kit_test_`.** The starter kits use PHPUnit (Pest runs them too), and a CRM app has its own `deals` and `companies` tables, which unprefixed fixtures collided with.
- **2026-10-02: The grid's endpoints and attachment links are paths, not full URLs,** because an app is opened under several hostnames (the preview, the published `*.ts.net` address), and a full URL from another host loses the session.
- **2026-10-02: A CSV import maps unmatched columns to "Skip", not to new fields, and can't be undone with ⌘Z,** so an import never adds fields by accident, and undo (which would only remove its last batch of 200) isn't misleading. A board leaves out its "Uncategorized" column when it's empty.

## Install, deploy and admin

INSTALL-001..002, DEP-001, ADMIN-001..006.
One-line install on a computer or a server; AWS via Pulumi; Laravel Cloud; admin settings for name and logo, sandbox providers, server monitoring, domain/HTTPS and database backups.

### Decisions

- **2026-09-29: The Docker install is one FrankenPHP container** (app and queue worker) with SQLite in a volume; projects run in sibling sandbox containers through the Docker socket.
- **2026-09-29: A server install only publishes 80/443;** previews and shells are `preview-<id>.<domain>` / `shell-<id>.<domain>` behind the gateway's sign-in check.
- **2026-09-30: Admin settings saved in the app win over `.env`,** and queue workers pick them up without a restart.
- **2026-09-30: Sandbox providers are an ordered list with on/off switches, not one "active" pick.** New projects run on the first one that's on and has its required settings; an admin drags to reorder, and selects one to see its settings in a pane beside the list. The order is the place to later send a project that needs something (e.g. Docker inside the sandbox for Compose) to the first provider that supports it. Installs that saved an active provider before there was an order keep it first. No failing over to the next provider when one errors, for now.
- **2026-09-30: The install command is `curl -fsSL https://onedrop.io/install | sh`,** a redirect to `install.sh` on main's raw GitHub URL. The raw URL was too long to fit on the home page without a horizontal scroller. A redirect, not serving the file, so the script stays whatever is on main (not the deployed app's copy) and GitHub stays the source people can read; the raw URL still works and the install guide shows it. Every install has the route, which is harmless. The home page's command box wraps rather than scrolls on narrow screens.
- **2026-09-30: When `tests` fails on main or a same-repo PR, the `ci fix` workflow opens a `ci-fix` issue with the end of the failed log and assigns it to Copilot cloud agent,** which fixes it in a PR into the failed branch; nothing lands until a person merges it. Copilot, not the Claude Code action, because it's built into GitHub and needs no Anthropic key. An issue assigned to Copilot, not the agent tasks API, because that API is Business/Enterprise only; Copilot automations need no workflow but aren't available in public repos. Copilot can't be assigned with `GITHUB_TOKEN`, so it needs a `COPILOT_TOKEN` user token, and does nothing without one. It skips fork PRs (their logs could steer the agent), Copilot's `copilot/*` branches (no fix-the-fix loops), runs whose branch has moved on, and branches that already have an open `ci-fix` issue. Copilot must fix the root cause (flaky tests included) and may not skip, delete or loosen tests, or add sleeps or longer timeouts. `copilot-setup-steps.yml` sets Copilot up the way CI is set up.
- **2026-10-01: On Laravel Cloud (`LARAVEL_CLOUD` set), the Docker idle check (every 15 seconds) and the server sample (every minute) aren't scheduled,** because Cloud wakes a sleeping app for each scheduled task and keeps it up for its sleep timeout, so either would keep the app awake for good. Neither does anything useful there: Cloud has no Docker sandboxes and no host of ours. Cloud's scheduler runs the rest (image pruning, database backups); it's turned on for the App instance. Not `->when()`: Cloud reads the wake times from `schedule:list`, which lists a task even when its filter would skip it.
- **Images are `ghcr.io/onedrop-io/onedrop` and `onedrop-sandbox`,** published for amd64 and arm64 once main's tests pass. The `drop` command, container, volume and network keep their short names.
- **2026-09-30: Held apps are reviewed under Admin → Reviews (ADMIN-006), shown only on the hosted install.** Platform admins can't open an organization's projects there (ORG-006), so the page shows what Jev saw instead of linking to the project.
- **2026-09-30: Taking an app down stops its public app and deletes its share page, and it can't be published publicly or shared until an admin approves it; private publishing and building still work.** A takedown that the user could undo by clicking Publish again wouldn't be one, and the app may be fixable, so admins can reverse it from the decided list. No email to admins or owners yet; admins find held apps on the page.
- **2026-09-30: `phpunit.xml` blanks `OPENROUTER_API_KEY`,** because the key in a developer's `.env` otherwise reached tests, and with the sync queue every finished run in a test would call Jev for real. Tests that need a key set `services.openrouter.key` themselves.
