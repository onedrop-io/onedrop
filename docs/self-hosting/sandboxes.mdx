title: 'Sandboxes'
description: "How project sandboxes run in Docker, on Blaxel or on Runtime Cloud, what's inside them, and how to maintain them."
---

Each project runs in its own sandbox. Locally that's a Docker container made from the `zap-sandbox` image. In production it's a microVM made from the same image, on [Blaxel](https://blaxel.ai) or [Runtime Cloud](https://withruntime.com).

## What's in the image

The image is defined in `docker/sandbox/`:

- PHP 8.4 (with SQLite, PostgreSQL and MySQL drivers), Composer, Node.js 22, SQLite
- OpenCode (the agent, pinned version), plus the Claude Code and Codex CLIs
- `ttyd`, the web terminal behind the Shell tab
- `start.sh`, which keeps three processes running: the app's dev server (or a placeholder page), the host-rewriting proxy, and the terminal
- `forwarder.mjs`, which runs an agent task and streams its events back to OneDrop
- `db.php`, which finds the app's databases and runs the queries behind **Tools → Database**
- `auth.php` and `guides/auth.md`, behind **Tools → Users & Auth**: the tool that lists the app's users and saves provider keys, and the guide the agent follows to add sign-in
- `instructions.md`, the rules the agent follows (plain language, how to start a dev server, default stacks)

Build or rebuild it with:

```bash
php artisan sandbox:build-image
```

## Container setup

Each container gets:

- A 2 GB memory and 2 CPU limit
- Ports published on `127.0.0.1` only: the proxy (preview) and the terminal
- The `zap.sandbox` label, so you can find all sandboxes
- The owner's default AI key as an environment variable, passed by name so it never appears in the process list

## Run sandboxes on Blaxel

Blaxel runs each sandbox in its own microVM. OneDrop talks to its REST APIs, so the server needs no Docker.

<Steps>
  <Step title="Create an API key">
    In the Blaxel console, create an API key. Set it as `BL_API_KEY`, and your workspace name as `BL_WORKSPACE`, in your secret manager, with `SANDBOX_PROVIDER=blaxel`. Set `SANDBOX_CALLBACK_URL` to your public `APP_URL`, and leave `SANDBOX_GATEWAY_DOMAIN` empty.
  </Step>
  <Step title="Push the image to Blaxel">
    Install the [Blaxel CLI](https://docs.blaxel.ai/cli-reference/introduction) (`bl`), then run:
    ```bash
    php artisan sandbox:build-image
    ```
    With `SANDBOX_PROVIDER=blaxel`, this builds `docker/sandbox` on Blaxel with the steps in `docker/sandbox/blaxel/` appended: Blaxel's sandbox API and an entrypoint that starts it, then `start.sh` as the sandbox user. The Docker image is unchanged. Set `BLAXEL_CLI` if `bl` isn't on the `PATH`. Run it again after changing `docker/sandbox/`; existing sandboxes then update themselves.
  </Step>
</Steps>

How it differs from Docker:

- **Settings and the AI key** are passed as Blaxel sandbox settings when the sandbox is created. The key is marked secret, so the API and console never show it. Blaxel sets `PORT=80` in every process, so OneDrop passes the app's port as `ZAP_PORT` and sets `PORT` again for each command.
- **Previews and the Shell tab** use private Blaxel preview links under `bl.run`. Each link carries a token, and OneDrop hands it only to people allowed to see the project. The first visit trades the token for a cookie. Tokens last 7 days, and OneDrop fetches new links at most once a day when someone opens the project.
- **Idle sandboxes go to standby** a few seconds after the last connection, with memory and processes kept, and wake on the next request. Agent runs keep their sandbox awake until they end.
- **Size.** `BLAXEL_MEMORY_MIB` (4096 by default, the most a new account allows) also sets CPUs, one per 2048 MB. About half of it holds the sandbox's files.
- **Not available yet:** SSH (Tools → Developer → SSH) and Tailscale publishing, which need Docker.

To find or delete sandboxes by hand:

```bash
bl get sandboxes
bl delete sandbox <name>
```

## Run sandboxes on Runtime Cloud

Runtime Cloud runs each sandbox in its own Firecracker microVM. OneDrop talks to its HTTPS API, so the server needs no Docker.

<Steps>
  <Step title="Create an API key">
    Create a key at [API keys](https://withruntime.com/account/keys) and set it as `RUNTIME_API_KEY` in your secret manager, with `SANDBOX_PROVIDER=runtime`. Set `SANDBOX_CALLBACK_URL` to your public `APP_URL`, and leave `SANDBOX_GATEWAY_DOMAIN` empty.
  </Step>
  <Step title="Build the image on Runtime">
    ```bash
    php artisan sandbox:build-image
    ```
    With `SANDBOX_PROVIDER=runtime`, this builds `docker/sandbox` on Runtime as `zap-sandbox:latest`. It needs Node.js 22.12 or later. Run it again after changing `docker/sandbox/`; existing sandboxes then update themselves.
  </Step>
  <Step title="Choose paid credit when ready">
    Sandboxes use the free trial until you set `RUNTIME_FUNDING=paid`. Add credit at [billing](https://withruntime.com/account/billing) before production traffic runs.
  </Step>
</Steps>

How it differs from Docker:

- **Settings at start.** Runtime can't set a sandbox's environment when it's created, so OneDrop writes the settings and the owner's AI key to `/home/sandbox/.zap-env`, readable only by the sandbox user. `start.sh` and the Shell tab read it. They never appear in a command line.
- **Previews and the Shell tab** use private Runtime preview links under `runtimehost.com`. Each link carries a token, and OneDrop hands it only to people allowed to see the project. Tokens last 7 days, and OneDrop fetches new links at most once a day when someone opens the project.
- **Idle sandboxes pause.** After 60 seconds with nothing happening, a sandbox pauses with its memory and processes kept. The next preview visit, command or agent run wakes it in about a second.
- **Leases.** A trial sandbox pauses when its hour-long lease ends, even during an agent run. With paid credit, set `RUNTIME_PERSISTENT=true` so leases renew.
- **Not available yet:** SSH (Tools → Developer → SSH) and Tailscale publishing, which need Docker.

To find or stop sandboxes by hand, use the Runtime CLI with the same key:

```bash
npx withruntime sandbox ls
npx withruntime sandbox stop <id>
```

## Switch providers

Each sandbox keeps running on the provider it was created on, so you can change `SANDBOX_PROVIDER` at any time without breaking existing projects. Sandboxes on Docker, Blaxel and Runtime Cloud can run side by side, as long as each provider's settings stay in place.

After a switch:

- New projects get sandboxes on the new provider.
- An existing project counts as outdated while its sandbox is on another provider, so it moves the next time someone opens it, or before the agent's next run. A move works like an update: the files, App Storage and home folder are copied to the new provider, and the old sandbox is removed only once the new one has them.
- To move every project now, or one:

  ```bash
  php artisan sandbox:update
  php artisan sandbox:update 12
  ```

Build the image on the new provider first (`php artisan sandbox:build-image` with the new `SANDBOX_PROVIDER`). Moves copy files through your queue workers, so give them enough time: a timeout of 900 seconds, and on Laravel Cloud managed queues a visibility timeout above that.

## How the app's dev server runs

The agent creates an executable `/workspace/.zap/dev` script that starts the app's dev server on `$PORT`, then runs `/opt/zap/restart`. The container's loop starts that script instead of the placeholder. Output goes to `/tmp/zap-server.log`, which the Console tab shows.

## Sandboxes update themselves

The guides the agent follows, the tools behind panels like Database and Growth, and the proxy all ship in the sandbox image. After you change anything in `docker/sandbox/`, rebuild the image (`php artisan sandbox:build-image`; the server deploy script does this when those files change). Existing sandboxes then move to the new image on their own:

- **When someone opens the project.** The update runs in the background and the preview shows **Updating sandbox…** until the app is back. It waits if the agent is working.
- **Before the agent's next run**, so the agent always has the current guides and tools.

An update keeps the app's files (`/workspace`), App Storage buckets, and the sandbox user's home folder (`/home/sandbox`), which holds the agent's conversation history and anything the agent installed there, such as a local database. Shell settings in the home folder stay as they were rather than taking the image's. The app's processes are paused while the files are copied, so a database is copied in a consistent state. The app restarts, and published projects are published again. Only one update runs per project at a time.

To update every outdated sandbox now, or just one project:

```bash
php artisan sandbox:update
php artisan sandbox:update 12
```

Projects the agent is working on are skipped; they update before their next run.

## Recreate a sandbox

To replace a sandbox even when it's up to date (for example, one that's broken):

```bash
php artisan sandbox:recreate 12 --keep-files
```

`--keep-files` copies the app (`/workspace`), App Storage and the sandbox user's home folder (with the agent's conversation history) into the new sandbox. Without it, the project starts from an empty workspace. Published projects are published again automatically.

## Clean up

Nothing removes old containers automatically yet. To remove every sandbox and publish container:

```bash
docker rm -f $(docker ps -aq --filter label=zap.sandbox) $(docker ps -aq --filter label=zap.sandbox.publisher)
```

## Real-Docker tests

The normal test suite uses a fake provider. To test against real containers:

```bash
RUN_DOCKER_TESTS=1 vendor/bin/pest tests/Integration
```
