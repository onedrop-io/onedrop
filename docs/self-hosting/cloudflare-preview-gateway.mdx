---
title: 'Previews on Laravel Cloud'
description: 'Serve project previews and shells through a Cloudflare Worker when OneDrop runs on Laravel Cloud with Blaxel or Runtime sandboxes.'
---

On a server, Caddy serves each project's preview and shell at its own address and checks every request with OneDrop ([Previews and shells on a server](/self-hosting/server-mode)). Laravel Cloud has no Caddy, so a Cloudflare Worker does the same job in front of the sandbox's provider:

| Address                         | Goes to                                       |
| ------------------------------- | --------------------------------------------- |
| `preview-<sandbox id>.<domain>` | The project's app, on Blaxel or Runtime       |
| `shell-<sandbox id>.<domain>`   | The project's web terminal                    |
| `<name>-<project id>.<domain>`  | A project [published](/guides/publish) to your domain |

## Why not the provider's own preview links

Blaxel and Runtime protect private previews with a cookie on their own domain. Browsers limit cookies for another site shown inside a page, so inside OneDrop's Preview tab:

- **Runtime** previews don't load at all.
- **Blaxel** previews load in Chrome but lose their styles and scripts in Safari.

Through the Worker, the browser only deals with addresses and cookies under your own domain, and the provider's token never reaches it.

## How a request is checked

1. Opening a project's preview sends the browser to `preview-<id>.<domain>/__onedrop/enter` with a short-lived token. The Worker asks OneDrop to check it, and OneDrop sets that address's own cookie. The app's login cookie never reaches these addresses.
2. On every other request, the Worker asks OneDrop whether that cookie may see the project, and where the sandbox lives. Answers are reused for a minute per cookie, so a page's assets don't each cost a request.
3. The Worker forwards the request to the provider with the private preview token in a header, and points links to the provider's address back at the gateway address. WebSockets (the Shell tab, hot reload, Phoenix LiveView) pass through. It also tells the sandbox which address the browser used (`X-OneDrop-Host`), because the provider sees its own address. With it, the sandbox can tell the page's own `Origin` apart from another site's, so apps that check it (Phoenix LiveView in Plausible, Vite's hot reload) accept their WebSockets.

A project published publicly to your domain needs no cookie, so the Worker shares that answer between visitors for a minute. A privately published one answers with a redirect to sign in to OneDrop, which the Worker passes on. Names under your domain that only look like a published app, but aren't one, go on to their own origin.

Only the Worker can ask OneDrop where a sandbox lives: it proves itself with a shared secret.

## Set it up

You need your domain's DNS on Cloudflare, with a proxied wildcard record (`*.<domain>`). Keep your app's own records (the root, `www`, docs) on **DNS only**.

<Steps>
  <Step title="Create a shared secret">
    ```bash
    openssl rand -hex 32
    ```
  </Step>
  <Step title="Deploy the Worker">
    Edit `infra/cloudflare/preview-gateway/wrangler.toml` for your domain (`routes`, `APP_URL`, `GATEWAY_DOMAIN`), then, with a Cloudflare API token that can edit Workers scripts and routes:
    ```bash
    cd infra/cloudflare/preview-gateway
    npx wrangler deploy
    npx wrangler secret put GATEWAY_SECRET
    ```
  </Step>
  <Step title="Turn it on in OneDrop">
    On Laravel Cloud, set `SANDBOX_GATEWAY_DOMAIN` to your domain and `SANDBOX_GATEWAY_SECRET` to the same secret (as a Secrets Manager secret), then redeploy.
  </Step>
</Steps>

<Note>
    Laravel Cloud runs web requests and queue jobs on separate instances, each with its own local disk. Attach an object storage bucket to the environment as its **default disk**, so share cards, project icons, chat attachments and code backups are saved where every instance can read them.
</Note>

<Note>
    Turn on the **Scheduler** for the environment's App cluster, so database backups and old sandbox image clean-up run. On Laravel Cloud, OneDrop leaves out the scheduled tasks that only matter on a server of your own (the Docker idle check and server monitoring), so the app can still sleep when nobody's using it.
</Note>

## Custom domains

Users can point their own domains at apps published to your domain ([Custom domains](/guides/domains)). Through the Worker, each one is a [Cloudflare for SaaS](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/) custom hostname on your zone: the user adds a CNAME to a fallback origin of yours, Cloudflare validates it and issues the certificate, and the Worker serves the app. A custom domain no app has gets a "not connected" page.

<Steps>
  <Step title="Turn on Cloudflare for SaaS">
    In the Cloudflare dashboard, open your zone, then **SSL/TLS → Custom Hostnames**, and enable it. The first 100 custom hostnames are free; more cost $0.10 a month each.
  </Step>
  <Step title="Add a fallback origin">
    Add a proxied DNS record for the name users will point at, such as `domains.onedrop.io` (an `AAAA` record to `100::` works, since the Worker answers every request), and set it as the **Fallback Origin**.
  </Step>
  <Step title="Route every hostname to the Worker">
    The `*/*` route in `wrangler.toml` sends custom hostnames to the Worker; deploy it again. The app's own host passes straight through.
  </Step>
  <Step title="Turn it on in OneDrop">
    Set `SANDBOX_GATEWAY_CLOUDFLARE_ZONE_ID` (the zone's ID), `SANDBOX_GATEWAY_CLOUDFLARE_TOKEN` (an API token with **SSL and Certificates: Edit** on the zone) and `SANDBOX_GATEWAY_DOMAINS_TARGET` (the fallback origin, e.g. `domains.onedrop.io`), then redeploy.
  </Step>
</Steps>

Without these, Tools → Domains says custom domains aren't set up for apps published to your domain. Hosted apps don't need them: they use Fly.io certificates and Workers custom domains in the hosting accounts.

The Worker's own tests run with `node --test infra/cloudflare/preview-gateway/worker.test.mjs`.
