Admins find install-wide settings under **Admin** in [Settings](/guides/settings). The first account on a new install is an admin; admins can make others admins from **Users** (see [Groups and users](/guides/groups-and-users)).

Settings saved here win over the matching values in `.env`. OneDrop tells running queue workers to restart after their current job, so they use the new settings too.

## Organizations

On the hosted install (`APP_MULTI_TENANT=true`), **Organizations** under **Admin** lists every organization, newest first: its address, owners, and how many members and projects it has. Search by name or address. Owners link to their user pages; the list never opens an organization's projects. See [Organizations](/guides/organizations).

## Reviews

On the hosted install (`APP_MULTI_TENANT=true`, with `OPENROUTER_API_KEY` set), OneDrop asks [Jev](https://openrouter.ai/docs/guides/community/jev) whether an app looks like abuse before it's published publicly or shared: phishing or impersonating a real brand, a scam or malware, or something else clearly harmful. Jev sees the project's name, its first and latest prompts, and the home page's title, visible text, form fields and where its forms send. The check always uses the platform's key, never the owner's.

An app that looks 80% likely or more to be one of those is held: its public app stays offline (the owner sees **Waiting for a review**) and its share page is hidden. Held apps are listed under **Admin → Reviews**, with how likely each kind of abuse looked and what Jev saw.

- **Approve** lets it through: a held publish goes live and the share page comes back. An approval stands until the owner sends the agent another message.
- **Take down** takes the public app offline and deletes the share page. The owner can't publish it publicly or share it again until an admin approves it; publishing privately still works.

Public and shared apps are checked again after the agent's next turns, at most once a day per project. If Jev can't be reached, apps are published as normal and the error is reported. Self-hosted installs (one organization) aren't checked.

## Name and logo

**Settings → General** changes the name shown on the sign-in pages, the browser tab, and emails. Leave it empty to go back to `APP_NAME`. The sidebar shows your [organization](/guides/organizations)'s name instead; rename that in **Settings → Organization → General**.

Upload a logo (PNG, JPEG, WebP, or SVG, up to 1 MB) to replace the droplet on the sign-in pages and the browser tab, and in the sidebar unless your organization has a logo of its own. A square image works best. **Remove** brings the droplet back.

## Sandbox providers

**Settings → Sandboxes** lists Docker, Blaxel, Runtime Cloud and E2B, each with an on/off switch and how many sandboxes it holds. Click a provider to see its settings next to the list.

- **Order:** drag a provider by its handle to move it up or down (or focus the handle and use the arrow keys). New projects run on the first provider that's on and has its required settings, marked **Active**. Existing projects move to it right away, with their files.
- **On and off:** turn a provider off to move every sandbox off it, for example when it's down. Its projects move to the first provider that's on, from a fresh snapshot, or from their latest snapshot if the provider doesn't answer. See [Switch providers](/self-hosting/sandboxes#switch-providers).
- **Moves:** while sandboxes move, a **Moves** list shows each one and what it's doing. A move that failed says why and has **Try again**. Files recovered from a provider that had stopped answering can be restored with **Restore** (replacing what changed since the move) or dismissed.
- **Settings:** fill in a provider's settings (image, CPU and memory, idle timeouts, [Docker inside sandboxes](/self-hosting/sandboxes#docker-inside-sandboxes), region, API key) and click **Save**. API keys are stored encrypted and never shown again; leave the field empty to keep the saved key. For E2B, saving its key or a new size has E2B build its sandbox image (about 2 minutes); the panel says how the build is doing when you open it.
- **Task copies:** set the most [task copies](/guides/tasks#each-tasks-own-copy-of-the-app) one project runs at once, for every project on the install, and click **Save**. Leave it empty for no limit. An organization can set a lower limit for its own projects. This wins over `SANDBOX_MAX_TASK_COPIES`.
- **Required settings:** a provider that's on but missing them (an API key for both managed providers, and a workspace for Blaxel) says what it needs and is skipped until it has them. You can't turn off the last provider that's on and set up.

## Hosting providers

**Settings → Hosting** lists Fly.io, Cloudflare, Neon and Upstash, what each is used for, an on/off switch, and how many things are in its account. Click a provider to enter its keys and settings. Hosting shows up in the Publish panel once Fly.io or Cloudflare is on. See [Hosting providers](/self-hosting/hosting).

## Monitoring

**Settings → Monitoring** shows the server's CPU use, memory, disk space, block I/O, and network traffic, as the current value and a chart over the past hour, day, or week. It also shows Docker's disk usage (images, containers, volumes, and build cache) and how many users, projects, and sandboxes the install has.

The scheduler records a sample every minute and keeps a week of them. I/O and network charts show rates; the totals next to them count from when the server started. CPU, memory, I/O, and network come from `/proc`, so on macOS only disk space is shown.

<Note>
In the one-line container install, network traffic is the container's own, and memory is the whole server's.
</Note>

## Server domain and HTTPS

**Settings → Server** shows the address OneDrop is served at and whether it uses HTTPS.

On a [server install](/self-hosting/server-mode) (`infra/server/bootstrap.sh`), you can change:

- **Domain**: where OneDrop is served. Previews and shells move to `preview-<id>.<domain>` and `shell-<id>.<domain>`.
- **Let's Encrypt email**: where certificate notices go (optional).
- **Certificates**: Let's Encrypt for a public domain, or OneDrop's own certificate authority for a network without public DNS (browsers must trust it).

<Steps>
  <Step title="Point DNS at the server">
    Create records for the domain and `*.<domain>` that point at the server, and keep ports 80 and 443 open.
  </Step>
  <Step title="Save the new settings">
    The page shows the change as pending while the server applies it. A root systemd unit (`onedrop-server-settings.path`) runs `/opt/onedrop/bin/apply-server-settings`, which checks the settings with Caddy and then runs `set-domain`.
  </Step>
  <Step title="Log in at the new address">
    Changing the domain signs everyone out. If the server couldn't apply the change, the page shows why.
  </Step>
</Steps>

On other installs the page tells you where the address is set instead: `drop install --domain <domain>` for the [one-line install](/self-hosting/install-anywhere), or `APP_URL` and `SANDBOX_GATEWAY_DOMAIN` elsewhere.

## Database backups

**Settings → Backups** backs up OneDrop's own database: users, projects, chats, and settings. Project files are backed up separately, as git history.

- **Back up now** makes a backup straight away. SQLite databases are copied with `VACUUM INTO` and gzipped; Postgres databases are dumped with `pg_dump`, which must be installed on the server.
- **Scheduled backups** run on a cron schedule, in UTC (`0 0 * * *`, daily at midnight, by default). After each backup, only the newest **Keep latest** backups are kept.
- **Destination** is this server's disk (`storage/app/backups`) or S3-compatible storage: bucket, region, endpoint (empty for AWS), access keys, and path-style addresses for MinIO and similar. **Folder** puts backups under a prefix.
- The page shows when the last backup ran, or the error if it failed. You can download or delete any backup.

<Warning>
Restoring replaces everything in OneDrop's database with the backup, including accounts and sessions, so you may need to log in again. Type the backup's name to confirm. OneDrop backs up the current database first, as a file ending in `-before-restore`.
</Warning>

A backup stored on the same server won't survive losing the server. Use S3-compatible storage for off-site copies.
