Run these against the provider you changed. Locally that's Docker; for Runtime Cloud or Blaxel, point a local install at the provider with its keys (see [Sandboxes](/self-hosting/sandboxes)). `RUN_DOCKER_TESTS=1 vendor/bin/pest tests/Integration` covers much of this for Docker; run it first.

## Create

- [ ] A new project gets a sandbox, and the preview shows the placeholder within seconds (Docker) or a minute (remote providers).
- [ ] The Shell, Console and Services tabs connect.

## Apps that refuse frames (SBX-001)

1. Ask the agent for an app that sends `X-Frame-Options: SAMEORIGIN` (a Rails app), and another that checks for a frame in its own code (NocoDB).

- [ ] Both show in the preview, not a blank page or NocoDB's **Not allowed** page.
- [ ] NocoDB's sign-up and sign-in work in the preview.
- [ ] At the published URL, `curl -I` still shows the Rails app's `X-Frame-Options`.

## Suspend and wake

1. Leave a project's workspace closed for over a minute.

- [ ] Docker: `docker ps` shows the container paused; after five more minutes, stopped.
- [ ] Opening the project wakes it; the preview is back in under a second when paused, a few seconds when stopped.
- [ ] A sandbox whose agent is working is never suspended.
- [ ] A published URL wakes a suspended sandbox when someone opens it.
- [ ] SBX-007: with the workspace open and visible, `docker stop` its container (as the idle check does): within about 20 seconds, without touching the page, the container is running again and the preview reloads to the app.
- [ ] SBX-007: leave a workspace open and visible without touching it for 15 minutes (no mouse over it): its 20-second pings to `/projects/{id}/sandbox/activity` stop (browser network tab) and the sandbox is suspended once idle (E2B: paused about 10 minutes later in its console). Click the page: the sandbox wakes and the preview reloads.

## Updates

### Tool files

1. Change a tool file in `docker/sandbox` (a guide, say), without rebuilding the image.
2. Leave a project unused for 10 minutes, or send it a message.

- [ ] The changed file is in the sandbox's `/opt/onedrop`, and nothing else changed.
- [ ] Sending a message copies it in first, so the agent has it for that turn.

### Base files

1. Change a base file (`start.sh`), rebuild with `php artisan sandbox:build-image`, then run `php artisan sandbox:update <project>`.

- [ ] The project moves to a new sandbox; the preview shows **Updating sandbox…** meanwhile.
- [ ] Kept: the app's files, uncommitted changes, `node_modules`, App Storage, the agent's conversation (the next message continues it), and anything installed in `/home/sandbox`.
- [ ] A project whose agent is working is skipped, and updates before its next run.

## Recreate and restore

- [ ] `php artisan sandbox:recreate <project> --keep-files` gives a new sandbox with everything above kept.
- [ ] Without `--keep-files`, the code comes back from its backup, every branch included.
- [ ] `php artisan sandbox:restore <project> --list` lists snapshots, and restoring an older one brings back that state.
- [ ] Deleting the sandbox's container by hand, then opening the project, recovers it.

## Snapshots

- [ ] A turn takes a snapshot; a second turn that changes no dependencies stores only the `workspace` layer again.
- [ ] Changing a lockfile stores the `deps` layer again.
- [ ] On a bucket (`SANDBOX_SNAPSHOT_DISK`), layers go straight to the bucket.

## Docker inside sandboxes

With **Docker inside sandboxes** on for the provider:

- [ ] A project with its own `docker-compose.yml` starts its stack, and **Services** shows it.
- [ ] Turning the setting off and on updates existing sandboxes the next time their projects are opened.

## Private GitHub packages (GIT-016)

With a GitHub OAuth app set (`GITHUB_CLIENT_ID`), as someone whose GitHub account can see a private `ghcr.io` image and a private npm package:

- [ ] **Settings → Security** says **Reconnect to let your projects download your private GitHub packages**; **Reconnect** shows GitHub's consent screen asking to read packages, and afterwards says **Your projects can download your private GitHub packages**.
- [ ] Within a minute, a new Shell in one of your running projects has `GITHUB_TOKEN`; `cat ~/.docker/config.json ~/.npmrc` shows `"ghcr.io": "onedrop"` and `${GITHUB_TOKEN}`, never the token itself.
- [ ] `docker pull ghcr.io/<owner>/<private image>` works, and so does `docker compose up` in a project that uses it (e.g. Pixwel/platform).
- [ ] `npm config set @<scope>:registry https://npm.pkg.github.com && npm view @<scope>/<private package> version` works.
- [ ] Asking the agent to start a project that pulls them works without it asking for a token.
- [ ] **Tools → Secrets** shows `GITHUB_TOKEN` under **From (your name)'s GitHub**.
- [ ] A sleeping project gets it when it wakes; a task's copy has it too.
- [ ] **Disconnect** GitHub: a new Shell has no `GITHUB_TOKEN`, the two config entries are gone, and `docker pull` of the private image is refused.
- [ ] With an organization secret named `GITHUB_TOKEN`, the Shell has the secret's value instead.
- [ ] Without a connection, asking the agent to start Pixwel/platform ends with it pointing you to **Settings → Security**, not asking for a token in the chat.

## Task copies (TASK-003)

With **Docker inside sandboxes** on, in a project whose compose stack has a database (Mongo or Postgres) storing its files in the workspace (e.g. `./tmp/mongo:/data/db`):

- [ ] A new task's first message makes its copy without "Permission denied", even though the database's files belong to its container's user.
- [ ] The task's copy starts the stack, and its database has Main's data.
- [ ] Main's containers are running again afterwards (`docker ps` in Main's Shell shows none **Paused**).
- [ ] With a service Main built itself (a `build:` section), the copy's preview comes up without building it again: `docker images` in the copy's Shell lists it, and its Console shows no build steps for it.
- [ ] A second task loads the same image without Main saving it again (no new file under the project's `images` folder on the snapshot disk).

## E2B (SBX-014)

With `E2B_API_KEY` set and the template built (`SANDBOX_PROVIDER=e2b php artisan sandbox:build-image`), put E2B first in **Settings → Sandboxes**.

- [ ] A new project gets a sandbox in a few seconds; the preview shows the placeholder, then the app.
- [ ] The Shell tab connects and keeps working (it's a WebSocket through the gateway).
- [ ] `docker info` in the Shell says `overlayfs`; importing Pixwel/platform, the agent starts its whole Compose stack (API, MongoDB, Redis, Elasticsearch, workers) and the preview shows the app.
- [ ] Opening the preview's URL with its token removed (`https://<port>-<id>.e2b.app/`) is refused (403).
- [ ] In a project whose owner connected GitHub with packages (GIT-016), the Shell's `echo $PATH` ends in `/opt/onedrop/lazy`, and asking the agent to `docker pull` a private `ghcr.io` image of theirs works.
- [ ] Left alone for 10 minutes, the sandbox shows as paused in the E2B dashboard; opening the project brings the preview back in about a second, with the Compose stack still up.
- [ ] SBX-014: switch to another browser tab (or close the workspace) with no agent working: the sandbox shows as paused in the E2B dashboard within about a minute and a half. Come back within a minute: it stays running.
- [ ] SBX-014: ask the agent for something with a long, silent step (`sleep 900 && echo done` in the Shell tool, or a big install) and close the tab: the sandbox stays running until the run ends, then pauses within about a minute and a half.
- [ ] A long agent turn with the workspace closed isn't paused mid-turn.
- [ ] The Files, Git and Services panels load without errors.
- [ ] Turning E2B off (with another provider first) moves its projects off with their files, and turning it back on and first moves them back.
- [ ] Changing E2B's vCPUs or memory in Settings shows **Building the sandbox image**, then **built** after about 2 minutes (reopen the page); the project moves to the new size once it sits unused for 10 minutes, and `nproc` in its Shell shows the new count.
- [ ] After a merge to `main` that changes `docker/sandbox`, the **sandbox image** workflow runs after **images** and Settings shows a new E2B build.
- [ ] During a move, the queue shows no job waiting or re-running every few seconds: the move's next step starts when the sandbox calls back.

## Switch providers (SBX-005)

Use an install with two remote providers set up (Runtime Cloud and Blaxel) and a bucket as the snapshot disk, on a Flex queue (production, or a staging environment on Laravel Cloud). Have two projects on Runtime: one with a database the agent set up in `/home/sandbox`, one with a Shell open.

1. In **Settings → Sandboxes**, turn Blaxel on, then drag it first.

- [ ] The toast says **Moving 2 sandboxes to Blaxel.**, and **Moves** lists both, going through **Taking a snapshot**, **Making the new sandbox**, **Restoring files** to **Moved**.
- [ ] Each move takes about a minute, and the queue shows no job running longer than 90 seconds and none failed.
- [ ] Each project's preview comes back on Blaxel with its files, uncommitted changes, `node_modules`, App Storage, the database's data, and the agent's conversation (the next message continues it).
- [ ] `npx withruntime sandbox ls` no longer lists the old sandboxes.
- [ ] A message sent while a project was moving runs once it's on Blaxel.
- [ ] A project whose agent was mid-turn moves after the turn ends.
- [ ] Turning Runtime off and back on doesn't move anything back; dragging Runtime first again does.

## A provider that stops answering (SBX-013)

1. On a project on Runtime, type a few lines into a file from the Shell, wait 10 minutes without touching it (an idle snapshot), then change the file again.
2. Make its sandbox stop answering commands: in its Shell, find Runtime's command agent with `ps aux` and freeze it with `sudo kill -STOP <pid>` (the Shell goes too). A sandbox stuck in Runtime's `resuming` state, as project 45 was on 2026-10-09, is the real case.
3. Turn Runtime off.

- [ ] The project moves to Blaxel within about 2 minutes, with the file as it was at the idle snapshot (not the later change).
- [ ] Its chat says Runtime stopped answering, and from which snapshot the files came. A turn stuck on **Thinking…** is over.
- [ ] **Moves** says the old sandbox is kept and checked on when Settings → Sandboxes is opened.
- [ ] After it answers again (stop and restart it in Runtime, which keeps its disk), within 15 minutes **Moves** says its newer files were saved, and the old sandbox is gone from Runtime.
- [ ] **Restore** asks first, then brings the later change back. **Dismiss** removes the entry and leaves the project as it is.
- [ ] A project with no snapshot and no code backup on a provider that doesn't answer fails with that reason, stays where it is, and **Try again** works once the provider answers.
