---
title: 'Secrets'
description: "Keep API keys and passwords your app needs out of its code, in the app's .env file."
---

**Tools → Secrets** holds the API keys, passwords and tokens your app uses, like `STRIPE_SECRET_KEY` or `OPENAI_API_KEY`. Secrets are the variables in the app's `.env` file inside its sandbox, and the app reads them as environment variables. Laravel, Vite, Next.js and Node's `dotenv` all read this file.

## Manage secrets

The panel lists every secret by name, with its value hidden. Type in **Filter secrets by name** to narrow the list.

- **Reveal** (eye): shows the value. Click again to hide it.
- **Copy** (next to the name or the value): copies the name, or the value without revealing it.
- **New secret**: enter a name and a value. Click **Add another** for more rows. Names use letters, digits and underscores and can't start with a digit.
- **Edit** (pencil): change a secret's value.
- **Delete** (trash can): removes the secret after you confirm.

### Paste from an .env file

To add several secrets at once, copy lines like `NAME=value`, for example from an `.env` file or another host's environment settings, and paste them into a **Name** field. Each line becomes its own row, ready to check before you save.

```bash .env
STRIPE_SECRET_KEY=sk_live_51H8x
export RESEND_API_KEY="re_123" # email
```

Comments, blank lines and `export` are skipped, and quotes are removed. Multi-line values in double quotes stay whole. If a name already exists, its row says that saving replaces the current value. Only the names marked that way are overwritten, and everything is saved at once with a single restart.

Values can be any text, including spaces, quotes and multi-line keys such as PEM certificates. The app restarts after each change so it picks up the new values.

## Secrets and the agent

The agent reads secrets from the environment by name. It doesn't put their values in code, commits or the chat. When the app needs a key that isn't there yet, the agent asks you to add it in **Tools → Secrets** by its exact name. Add it there rather than pasting it in the chat.

### Pasted in the chat

If you paste a secret into a chat message anyway, OneDrop notices before the message goes to the agent (when OpenRouter is set up; see [Before a message is sent](/guides/build-a-project#before-a-message-is-sent)) and asks **This looks like a secret. Save it in Secrets instead?** It suggests a name from the kind of key (`sk_live_…` is `STRIPE_SECRET_KEY`, a `postgres://` URL is `DATABASE_URL`) or the words before it ("the admin password is …" is `ADMIN_PASSWORD`); change it if you like. **Save in Secrets** saves the value here and sends the message with `(saved as NAME in Secrets)` in its place, so the value never reaches the agent or the chat history. If OneDrop can't tell which part is the secret, paste just that part into the second field. **Send anyway** sends the message as you typed it. In a task's chat, the secret goes into the task's own copy of the app while it has one.

<Info>
    OneDrop doesn't store a project's own secrets. They stay in the app's `.env` in its sandbox,
    and the panel only fetches a value when you reveal or copy it. Anyone who
    can open the project can see them. `.env` is added to the app's `.gitignore`
    so it stays out of the app's git history.
</Info>

## Organization secrets

Credentials everyone in your organization uses, like an AWS profile, can be shared with every project instead of added to each one. Organization owners and admins add them in **Settings → Organization → Secrets**:

<Steps>
  <Step title="Add the secret">
    Click **New secret**, enter a name like `AWS_ACCESS_KEY_ID` and its value. Names use letters, digits and underscores, can't start with a digit, and can't start with `ONEDROP_`.
  </Step>
  <Step title="Choose its projects">
    Pick **All projects, including new ones**, or **Selected projects** and tick the ones that should get it. People's own [computers](/guides/computer) never get organization secrets.
  </Step>
  <Step title="Save">
    Running sandboxes get it within moments, and their apps restart to pick it up. Sleeping sandboxes get it when they wake.
  </Step>
</Steps>

For an AWS profile, add `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_REGION`. The `aws` CLI and the AWS SDKs read them, so `aws s3 ls` works in every project's Shell.

Each project's sandbox gets its organization secrets as environment variables in the Shell, the running app and the agent. A few rules apply:

- **The project's own secrets win.** A name in the project's **Tools → Secrets** replaces the organization's, so an app that runs local stand-ins with `AWS_ACCESS_KEY_ID=local` keeps using them. Settings OneDrop itself puts in the sandbox, such as the AI key, also win.
- **Open Shells keep the old values.** Open a new Shell tab after a change.
- **Values can't be seen again in Settings** once saved. To change one, enter a new value; leave it empty to keep the old one. But anyone who can open a project can read the secrets it gets, for example with `env` in its Shell.
- **They stay out of the project's files.** They aren't written to `.env`, so they don't end up in commits, [hosted apps](/guides/hosting), snapshots or remixes. A hosted app gets its settings from its own environment.

**Tools → Secrets** lists the names of the organization secrets a project gets under **From your organization**, with any its own secrets replace crossed out.

The agent may use organization secrets for what you ask, like reading a bucket or a table with your AWS profile. It doesn't print their values, never signs in to an account itself, and asks you before it creates, changes, deletes or deploys anything real in your cloud account.

Sign-in provider keys saved in [Users & Auth](/guides/users-and-auth) are secrets too, so they appear here as well.
