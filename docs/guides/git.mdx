Every project is a git repository. The agent commits everything after each turn, with your message as the commit message (see [Your code is saved after every turn](/guides/build-a-project#your-code-is-saved-after-every-turn)). **Tools → Git** shows that history and lets you work with it without the Shell.

## History

The history lists the project's commits, newest first, with who made each one (the agent's turns are marked **Agent**), how long ago, and its short id. The note under it shows when the history was last backed up outside the sandbox.

Search the history with the box next to **History**: it looks through every commit's message and author (type `agent` for the agent's turns), or finds a commit by its id. **Show more** lists older commits, 50 at a time.

Click a commit to see its full message, author and email, the exact date and time, and its full id (with a copy button), plus the files it changed with the lines added and removed. Click a file to see its diff (see [Reading a diff](#reading-a-diff)). Click the commit again to close it.

### Undo the last commit

Open the **⋮** menu on the newest commit and choose **Undo this commit** (or pick **Undo last commit** in the header's git menu). After you confirm, the commit is gone and its changes are back as uncommitted, so you can change them or commit them differently. Your files don't change.

Only a commit that isn't pushed yet can be undone, so your repository never has to be overwritten. For a pushed commit, restore the version before it instead. The very first commit and merges can't be undone.

### Restore an earlier version

Open the **⋮** menu on a commit and choose **Restore this version**. Every file goes back to how it was at that commit, and the app restarts.

A restore is saved as a new commit, so nothing is lost: to undo it, restore the version before it the same way. Any uncommitted changes are committed first, as **Changes before restoring …**.

## Commit your own changes

Changes you make in the Shell or the Files panel, or that the agent made before you stopped it, show up under **Commit** with their state: **M** modified, **A** added, **D** deleted, **R** renamed, **U** new (untracked), **!** conflicted.

Click **Review and commit**, or a file's name, to open **Commit changes**, the same dialog as the header's [Commit & push](#commit-and-push-from-the-header) button. The commit is made as you. As with the agent's commits, `node_modules`, `vendor`, `.cache` and `.env` files (except `.env.example`) are never committed.

To throw changes away, click the undo icon next to a file, or **Discard all**. Files go back to the last commit and new files are deleted. Ignored files like `node_modules` and `.env` are kept. This can't be undone.

While the agent is working, committing, discarding, switching branches and restoring wait until it finishes.

## Commit and push from the header

The **Commit & push** button next to **Share** does the everyday steps without opening Tools. Click it to review what you're committing in **Commit changes**, and it commits and pushes the branch to your connected repository. With nothing to commit but commits not yet pushed, it just pushes. A notice shows **Pushing…**, then whether it worked.

In **Commit changes**:

- **Branch** shows where the commit goes, marked **Default branch** on `main` or `master`. Pick **Commit on new branch** and type a name to commit there instead; the app restarts on the new branch.
- **Files** lists each change with its state and the lines added and removed, and the total below. Click **Edit** and untick files to leave them out; they stay uncommitted for later.
- Click a file to see its changes beside the list: added lines in green, removed in red (a new file is all green, and a new folder lists its files). Use ↑/↓ to go through the files one by one, and Space to tick or untick the one you're on while editing. Click the file again or press Esc to close it.
- To commit only part of a file, untick a part (the checkbox by each `@@` line) or click single lines to leave them out; they're struck through, the file shows **part**, and the totals count only what's left in. What you left out stays uncommitted in the file. If the file changes before you commit (say, the agent starts working), the commit is refused with **This file changed. Review it again.**
- **Discard** on a part of an edited file puts just that part back as it was in the last commit, after you confirm. This can't be undone.
- **Ask** on a part puts it, with the file's name, in the chat box and closes the dialog. Type your question ("why did you change this?", "undo just this") and send it.
- **Commit message** is optional. Leave it blank and your project's AI writes one from the changes (if it can't, the message names the files). Press ⌘/Ctrl+Enter to commit.

The arrow next to it opens a menu:

- **Commit** commits without pushing.
- **Push** pushes the commits your repository doesn't have yet. With no repository connected, this is **Connect a repository…**, which opens **Tools → Git** (and the button itself just says **Commit**).
- **Undo last commit** shows the newest commit's message; see [Undo the last commit](#undo-the-last-commit).
- **Combine N commits** appears when more than one commit is waiting to be pushed (the agent commits after every turn, so they add up). It turns them into one commit with a message your project's AI writes from them, listing the original messages underneath; edit it before combining. Only commits that aren't pushed yet are combined, so pushing never has to overwrite your repository, and your files don't change. Commit or discard your changes first.
- **Create PR** opens a pull request for the current branch (see below).

The buttons wait while the agent is working or the sandbox isn't running.

### Open a pull request

On a branch other than `main` or `master` that's pushed to a GitHub repository, **Create PR** opens a dialog. Pick the branch it goes into (`main` or `master` to start with), and your project's AI writes a title and description from the branch's commits and changes. Edit them, then click **Open on GitHub**: GitHub's new pull request page opens with both filled in, ready to create. Without an AI, the title is the branch's only commit message (or the branch name) and the description lists its commits.

When Create PR isn't available, the menu says why: **Commit on a new branch first**, **Push the branch first**, or **Needs a GitHub repository**.

### Reading a diff

Diffs show the old and new line numbers, color the code by its language, and highlight the words that changed within an edited line. In **Commit changes**, tick **Hide whitespace** to read lines whose only change is spacing (like re-indenting) as unchanged; untick it again to pick or discard parts.

## Branches

The branch menu at the top shows the current branch. Pick another to switch to it, or choose **New branch…** to start one from the current commit. The app restarts on the new branch.

## Push to GitHub or another git host

Connect a remote repository to push your commits to it and pull commits others made.

### Connect GitHub

If your OneDrop has a [GitHub App](/self-hosting/github-app) set up, click **Connect to GitHub**. A dialog walks you through it.

**The first time**, click **Continue to GitHub**. On GitHub, pick your account or an organization, choose all repositories or only the ones OneDrop may use, and approve. GitHub brings you back with the dialog open. If you end up back on the project without GitHub bringing you, open Tools → Git: the dialog asks **Finished installing on GitHub?** Click **Continue** to pick up the installation.

**Then pick an owner** (your account or an organization) at the top of the dialog, and either:

<Tabs>
    <Tab title="New repository">
        The name is suggested from your project, and OneDrop checks as you type that it's free. Choose **Private** or **Public**.

        - **In an organization**, click **Create and push**. OneDrop creates the repository and pushes your project to it.
        - **On your personal account**, click **Create it on GitHub**. GitHub doesn't let apps create repositories on personal accounts, so GitHub's new-repository page opens with the name and visibility filled in. Create it there and come back: OneDrop finds it and offers **Connect and push**. If OneDrop only reaches the repositories you chose, give it access to the new one first; the dialog links to the right page.
    </Tab>
    <Tab title="Existing repository">
        Search the owner's repositories, newest activity first, click one and choose a branch.

        - In a project with commits, click **Connect** (or **Connect and push** for an empty repository).
        - In a project with no commits yet, click **Connect and bring it in** to start from that repository's code.

        Don't see a repository? Click **Choose which repositories OneDrop can reach**, change it on GitHub, and come back. The list updates by itself.
    </Tab>
</Tabs>

The dialog opens on **New repository** when your project has commits, and on **Existing repository** when it doesn't. **Add account or organization** installs the app somewhere else.

You only see repositories that both you and the app can reach. No token is stored for the project: OneDrop gets a short-lived one from GitHub each time it pushes or pulls. If your GitHub sign-in expires, the dialog asks you to reconnect.

### Connect with a token

Without the GitHub App, or for another git host (**Other git host**), connect with an access token:

<Tabs>
    <Tab title="Create on GitHub">
        1. Click **Create on GitHub**.
        2. Enter a repository name and a GitHub [personal access token](https://github.com/settings/tokens) that can create repositories (a fine-grained token with **Administration** and **Contents** read and write, or a classic token with the `repo` scope).
        3. Leave **Private repository** checked, or uncheck it for a public one.
        4. Click **Create and push**. The repository is made on your account and the current branch is pushed to it.
    </Tab>
    <Tab title="Connect existing">
        1. Click **Connect existing**.
        2. Enter the repository's HTTPS URL, for example `https://gitlab.com/you/my-app.git`.
        3. Enter an access token that can read and write the repository. Some hosts also need your username (Forgejo and Gitea, for example); GitHub and GitLab don't.
        4. Click **Connect**, then **Push**.
    </Tab>
</Tabs>

**Push** sends the current branch to the remote. **Pull** brings in commits the remote has that the project doesn't. Both run in the background; the card shows **Pushing…** or **Pulling…**, then how many commits there are to push or pull.

- A push the remote refuses because it has newer commits says **Pull first**.
- A pull only fast-forwards. If the project and the remote both have new commits, ask the agent to merge them.
- **Disconnect** in the **⋮** menu forgets the remote and its token. The repository itself is untouched.

<Note>
    The token is stored encrypted by OneDrop and never shown again. It never goes into the sandbox: pushes and pulls run on OneDrop's server, which carries commits in and out of the sandbox. Remotes must use HTTPS, and on the public internet unless your admin allows private networks (see [configuration](/self-hosting/configuration)).
</Note>

## Private GitHub packages

Projects can download the private GitHub packages you can see, like a codespace does: Docker images on `ghcr.io` and npm packages on `npm.pkg.github.com`. No personal access token needed.

1. Go to **Settings → Security**. Under **Connected accounts**, GitHub says whether your projects can download your private packages.
2. Click **Connect** (or **Reconnect** if you connected GitHub before), and allow OneDrop to read your packages.

Every sandbox of a project you own, task copies too, then has your GitHub token as `GITHUB_TOKEN`, in the Shell, the app and the agent. Docker is signed in to `ghcr.io` with it, and npm to `npm.pkg.github.com`, so `docker compose up`, `docker pull ghcr.io/…` and `npm install` just work. **Tools → Secrets** shows it under **From (your name)’s GitHub**.

- If npm looks for a `@scope` package on npmjs.org, point the scope at GitHub once: `npm config set @scope:registry https://npm.pkg.github.com`. The agent does this when it needs to.
- It downloads as you, so your GitHub account must be able to see the packages.
- An organization secret or a project secret named `GITHUB_TOKEN` wins over yours, so an admin can share one token instead.
- **Disconnect** in Settings → Security, or leaving the organization, takes it out of your projects' sandboxes.

<Note>
    Only package reading (`read:packages`) is asked for, not access to your repositories. The token never goes into the project's files or your home folder, so it doesn't end up in commits, hosted apps, snapshots or remixes. Your organization's owners and admins, who can open your projects' Shell, could read it there. Your admin needs a GitHub OAuth app for this (see [social login](/self-hosting/social-login)).
</Note>
