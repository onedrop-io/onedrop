When your project is connected to a GitHub repository (see [Source Control](/guides/source-control)), you can follow the repository's pull requests in two places:

- **Pull requests**, a page of its own: in the project's **⋮** menu under **Board** (or press **G** with the menu open), and in the sidebar under **Board** when you've opened the project.
- **Tools → Pull requests**, beside the chat, so you can read a pull request next to its running app.

Both show the same list and pages. You can read a pull request the way you would on GitHub, run it as a [task](/guides/tasks) with its own copy of the app, and have that task's agent fix its failing checks. It works the other way too: a task's work can become a new pull request.

OneDrop reads GitHub with the same connection it pushes with: the GitHub App, or the access token you connected with. Your access token never goes into the sandbox.

## Browse pull requests

The list shows the open pull requests, the most recently changed first. Switch to **Closed** for closed and merged ones, or search by title, number, branch or author. Each row shows:

- its number, author, and its branch and the branch it goes into
- **Draft**, and the review: **Approved**, **Changes requested** or **Review required**
- how many comments it has
- its checks: a green tick when they passed, a red cross when one failed, a spinning circle while they run
- **Task** when it's checked out as a task

## A pull request's page

Click a pull request to open its page. The address keeps it and its tab (`?pr=12&pr_tab=files`), so a reload or a shared link opens it again. In Tools, switching to the Preview or another tab and back also brings back the same pull request and tab. At the top are its state, who opened it, its branches, its size, whether it has conflicts with the branch it goes into, and **Open on GitHub**. Below, four tabs:

| Tab               | What it shows                                                                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Conversation**  | The description, then comments, reviews and comments on lines, oldest first.                                                                    |
| **Commits**       | Each commit's message, author and when, with a link to it on GitHub.                                                                            |
| **Files changed** | Each file with lines added and removed. Click one to see its diff. GitHub leaves out the diff of very large files; open those on GitHub.        |
| **Checks**        | Each check and commit status on the newest commit, how long it took, and a link to its details. Click a failed check to see the end of its log. |

While any check is still running, the page looks again every 15 seconds.

## Ask the agent for a branch or pull request

You can also name a branch or pull request in the chat, such as "check out the `billing-v2` branch" or "check out PR #42 and see why the login test fails". The sandbox's repository has your remote as `origin`, with every branch and tag already brought in, so the agent uses git the way it would in a clone: `git switch`, `git fetch origin pull/42/head`, or `gh pr checkout 42`. The preview switches with the branch. If you have uncommitted changes, the agent asks before switching.

This works on Main or in any task. To run a pull request beside Main instead, check it out as a task (below).

For a repository connected through the GitHub App, git asks OneDrop for a token whenever it needs one. The token can only read that one repository and its pull requests, and expires after an hour. It isn't saved in your project. The agent can't push with it; your work still reaches GitHub through **Push** in Source Control.

<Note>
    With a repository connected with an access token (GitLab, or **Other git
    host**), your token stays out of the sandbox. Public repositories still
    fetch. For a private one, the agent asks you to **Pull** in Source Control,
    which brings in every branch.
</Note>

## Check out a pull request as a task

Click **Check out as task**. OneDrop starts a task named after the pull request, such as "#12 Fix login", and gives it a fresh sandbox with the pull request's branch at its newest commit. Nothing comes from Main: the app sets itself up as it does after an import (its `.onedrop/dev` installs dependencies and starts its services), so its databases start as the app makes them, not with Main's data. The agent doesn't start. The task's preview, files, shell and tools now show the pull request's code, so you can try it before you review it. Main isn't touched.

A pull request is checked out once. After that, its button says **Open task**.

The task's page shows the pull request where other tasks show **Apply to Main**:

| Control                              | What it does                                                                                                                              |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **#12**                              | Opens the pull request's page in Tools.                                                                                                   |
| **Files changed**                    | Opens the pull request's diff in Tools, beside the chat, while the preview runs its code.                                                 |
| **Pull**                             | Brings in commits pushed to the pull request since. They're merged in, and the task's agent resolves conflicts and installs what changed. |
| **Push**                             | Commits what changed in the task's copy and pushes it to the pull request's branch.                                                       |
| **Push after each turn**             | On by default: when the agent finishes a turn, its work is pushed to the pull request.                                                    |
| **Fix failing checks automatically** | Off by default. See below.                                                                                                                |

Ask the task's agent for changes the same way as in any chat. It works on the pull request's branch, and its work reaches GitHub through **Push**, since the agent can't push itself.

OneDrop never force-pushes. If someone pushed to the pull request in the meantime, the push fails and the task says to pull first.

<Note>
    A pull request from a fork runs in its task, but can't be pushed to: OneDrop
    can only write to your repository.
</Note>

Checking out needs tasks to get their own copy of the app. On an install where that's turned off, the button says why.

## Open a pull request from a task

Any task with its own copy of the app can become a pull request:

1. On the task's bar, click **Open pull request**. OneDrop commits the task's work and pushes it to a new branch, such as `onedrop/task-14-add-dark-mode`. It never force-pushes. The bar says **Pushing to GitHub…**.
2. When the push is done, click **Create on GitHub**. GitHub's new pull request page opens, from that branch into the repository's default branch, with a title and description your project's AI wrote from the changes. Change them, or the base branch, before you create it.
3. Within a minute or two of creating it, the task becomes the pull request's task: its bar shows the pull request, with **Push**, **Pull**, its checks and **Push after each turn**, and the task moves to Review on the [board](/guides/tasks). Its chat says "Opened #14".

To send newer work before you create the pull request, click **Push again**. It goes to the same branch.

OneDrop opens GitHub's page rather than creating the pull request itself, so the GitHub App only needs read access to pull requests.

## When a pull request is merged or closed

When a pull request is merged or closed on GitHub, its task moves to **Done** and its chat says "#12 was merged on GitHub" (or closed). Its card on the board shows **Merged** or **Closed**, and **Push** and **Pull** are turned off. OneDrop notices when you open the Pull requests list, and a moment after you open the board or the task.

The task is moved only once: if you drag it back out of Done, it stays where you put it.

## Previews for every pull request

Every pull request gets a running copy of the app with its changes, and a link anyone can click to try it. Reviewers don't need a OneDrop account: the link is on the pull request itself.

**Preview every pull request** is off until you turn it on, for each project. Tick it above the list on the Pull requests page or in **Tools → Pull requests**; the open pull requests are checked out right away. While it's on:

- Each pull request from your repository's own branches is checked out as a task within moments of being opened, as if you'd clicked **Check out as task**.
- When someone pushes to the pull request, the preview brings in the new commits. It waits while the task's agent is working.
- When the pull request is merged or closed, the preview stops, and its copy of the app is removed a day later unless the pull request is reopened.

Pull requests from forks aren't checked out on their own, because a preview runs its code next to your organization's secrets. Check them out by hand once you've read them.

If the project already runs as many task copies as it's allowed, new pull requests wait for a free copy, and their page says so.

### The preview link

Each preview has its own address that doesn't change while the pull request is open, such as `pr-12-shop-48.onedrop.dev`. The link to open it includes a key: anyone who has the link can open the app, without signing in, for 12 hours per visit.

<Warning>
    The link is posted on the pull request. On a public repository, that means
    anyone can open the preview. Previews run on a copy of the project's Main
    data, not production's, so think about what Main's database holds.
</Warning>

On the task's bar, **Preview** opens it, **Copy link** copies it, and **New link** makes a new one. The old link stops working at once, for everyone, and the pull request gets the new one.

### On GitHub

OneDrop shows each preview on its pull request in two places:

- **View deployment**, from a GitHub Deployment named "OneDrop preview #12". Its status shows when the preview is being updated, ready, or failed, and it's marked inactive once the pull request is closed.
- **One comment**, which OneDrop edits rather than posting again: the link, the commit it runs, and its state.

This needs the GitHub App's **Deployments** and **Pull requests** write permissions (see [GitHub App](/self-hosting/github-app)). If GitHub refuses, the preview still works, and the task's bar says why GitHub didn't show it.

## Fix failing checks

When a check fails, click **Fix failing checks** on the pull request's page. The names of the failed checks and the end of their logs go to the pull request's task (it's checked out first if it has none), asking its agent to find and fix the cause. When its turn ends, the fix is pushed and the checks run again.

To keep going without you, turn on **Fix failing checks automatically** on the task. After each push, OneDrop watches the checks. When they fail, it sends them to the agent the same way. If 3 tries in a row don't make them pass, it stops and says so in the task's chat; passing checks start the count again.

After each push, the task's chat says how the checks went, such as "Checks passed on 3f2a1c9" or "2 checks failed on 3f2a1c9", and the task's card on the [board](/guides/tasks) shows them too.

The agent is asked to fix the code, not the checks: it doesn't skip, delete or loosen tests, or add sleeps or longer timeouts. If a check fails for a reason outside the code, such as a missing secret, it says so instead of changing anything.

## What GitHub needs to allow

With the GitHub App, its admin gives it the **Pull requests**, **Checks**, **Commit statuses** and **Actions** read permissions (see [GitHub App](/self-hosting/github-app)); admins see in Source Control which are missing. With an access token, the token needs the same read access to the repository. When GitHub refuses, the section says which permission it needs.
