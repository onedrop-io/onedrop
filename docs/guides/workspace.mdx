The right side of a project holds tabs and a files panel.

To give the workspace the whole width, click the chat button at the far left of the tab bar to hide the chat; click it again to bring the chat back, with anything you'd typed still in the box. Your browser remembers whether the chat is hidden.

On a phone or small tablet, the chat and the workspace are tabs at the top of the page instead: tap **Chat** or **Workspace** to switch. A dot on the Chat tab shows the agent is still working while you look at the preview. To keep the tab bar on one line, a phone leaves out the preview's address, the size menu and splitting.

On a phone, a pane's tabs are one button showing the tab you're on and how many are open. Tap it to switch tabs, close one, or open another (Shell, Console, Tests…). The tab's own buttons, like the preview's Inspect and Annotate, stay in the bar, and **⋯** holds "Open in a new tab" and the files toggle. In the header, Commit and Share show only their icons.

Drag the divider between the chat and the workspace to make either one wider, or drag the files panel's left edge. The left sidebar's right edge can be dragged the same way on every page. You can also focus a divider and use the arrow keys. Double-click a divider to reset it. Your browser remembers the widths.

## Tabs

| Tab         | What it's for                                             | Can close |
| ----------- | --------------------------------------------------------- | --------- |
| **Tools**   | Project tools such as Publishing, Database, and Secrets   | No        |
| **Preview** | Your running app, with size, reload and open-in-new-tab buttons | No        |
| **Console** | The app's dev server output as it happens, in color and searchable ([Console](#console)) | Yes |
| **Services** | What runs in the sandbox: the preview server, Docker containers and open ports ([Services](#services)) | Yes |
| **Shell**   | An interactive terminal in the project's workspace        | Yes       |
| **Requirements** | What you've asked the app to do, and why ([Requirements](/guides/requirements)) | Yes |
| **Tests**   | The agent's browser tests, with a recording of each ([Tests](/guides/tests)) | Yes |
| File tabs   | An editor for a file you opened                           | Yes       |

A project opens with **Shell**, **Services** and **Console** tabs next to Tools and Preview. Add Requirements or Tests (or another Shell) from the **+** button. Each time you choose **Shell** you get another one (**Shell 2**, **Shell 3**…), each with its own session. Drag the tabs you can close to put them in a different order; Tools and Preview always stay first. A shell keeps its session while you switch tabs or [reload the page](#reloading-the-page), and the cursor lands in it whenever you open the tab, so you can start typing right away. It opens with a OneDrop banner showing the project's name and a few shortcuts.

### Services

The **Services** tab shows what's running in the project's sandbox, and checks again every few seconds while it's open:

- **Preview server**: the command the preview runs (from `.onedrop/dev`, or the placeholder page), whether it's running, and **Restart**.
- **Docker**: each container the sandbox's own Docker runs, grouped by compose project, with its state, how long it's been up (or why it's restarting, with its exit code), and the ports it publishes. Click a container to open its latest logs (in color: errors red, warnings amber, timestamps dimmed, slow durations amber or red, and any colors the program prints itself), search them, or **Expand** them into a large view with the latest 2,000 lines. You can also restart, stop or start a container. Projects that [run their own Docker Compose](/guides/docker-compose) show their whole stack here.
- **All logs**: with more than one container, every container's latest logs in one view, in time order, each line labelled with its service in its own color. It has the same search, **Live** and **Expand** as a single container's logs; search for a service's name to keep just its lines.
- **Ports**: everything listening in the sandbox and what it is (the preview, the host proxy, the Shell tab, SSH, or a Docker service). Only the preview port is reachable from outside.

#### Searching logs

The search box above a container's logs (or **All logs**) keeps only the lines that match, and marks the matches:

| Search | Finds lines |
| --- | --- |
| `timeout redis` | with both words, in any order |
| `"connection refused"` | with that exact phrase |
| `error -healthcheck` | with `error` but not `healthcheck` (`NOT healthcheck` works too) |
| `error OR panic` | with either word |
| `(error OR warn) -healthcheck` | grouped with parentheses |

Matching ignores case. Click a matching line to clear the search and see it highlighted among the lines around it. Turn on **Live** to load new lines every few seconds; the view stays on the newest line unless you scroll up.

### Console

The **Console** tab follows the app's dev server output while it's open. It shows the colors the dev server prints (Vite's, npm's, Laravel's, and each Docker Compose service's name). Lines without colors of their own are colored the same way as [container logs](#services): timestamps dimmed, errors red, warnings amber. Durations are colored too, so slow requests stand out: amber from 100ms, red from 500ms.

The search box above the output works like [searching logs](#searching-logs): it keeps only the matching lines, marks the matches and says how many there are. Click a matching line to clear the search and see it highlighted among the lines around it. New output keeps coming in while you search. The view stays on the newest line unless you scroll up. **Clear** (the circle-slash button in the tab bar) empties the view.

### Panes

Split the workspace to see two things at once, like the preview next to a Shell, or two Shells. Click the split button in a pane's tab bar and choose **Split right** (side by side) or **Split down** (one above the other). The new pane opens a new Shell. You can have up to four panes; choosing the other direction lays them all out that way.

- Each pane has its own tabs and **+** button. Tabs you add from a pane's **+** open in that pane; files, **Open shell here** and other tabs opened from elsewhere open in the pane you used last.
- Drag a tab onto another pane's tab bar to move it there. Tools and Preview can move too, but they can't be closed. A Shell keeps its session when you move it, and the preview doesn't reload.
- Drag the line between two panes to resize them, or double-click it to make them all the same size.
- Click **×** at the right of a pane's tab bar to close the pane; its tabs move into the pane next to it. A pane also closes when its last tab is closed or moved away.

### Reloading the page

Reloading a project's page brings the workspace back as you left it in that browser tab: the same panes, tabs and sizes, the open file and Tools section, the files panel's search and open folders, and the chat's half-typed message and scroll position. The preview comes back on the page of your app it was showing, and **Reload preview** keeps that page too.

Shells come back with the same session, so what was on screen and anything still running (a dev server, a long install, an editor) is still there. A Shell whose tab you close ends a few minutes later. A new browser tab on the same project starts with the usual layout and its own new Shells.

<Note>Sandboxes made before this pick it up once they update to the latest image; until then their Shells start fresh after a reload.</Note>

To see how the app looks on a smaller screen, click the size button in the bar above the preview and choose **Tablet** (768px wide) or **Mobile** (390px wide). The app shows at that width in the middle of the pane, so its own responsive styles kick in. **Desktop** fills the pane again. Your choice is remembered in this browser for every project.

To point at something in the app for the agent, click **Annotate** (the brush) in the bar above the preview and draw on it, or **Inspect** to pick and rearrange elements in the live app. See [Draw on the preview](/guides/build-a-project#draw-on-the-preview) and [Inspect and rearrange the preview](/guides/build-a-project#inspect-and-rearrange-the-preview).

| Command                  | What it does                                                             |
| ------------------------ | ------------------------------------------------------------------------ |
| `ls`, `ll`, `la`, `tree` | List files: folders first, with git status and how long ago each changed |
| `bat <file>`             | View a file with syntax highlighting                                     |
| `rg <text>`              | Search the code                                                          |
| `fd <name>`              | Find files by name                                                       |
| `z <dir>`                | Jump to a directory you've been to (`zi` to pick one)                    |
| `jq`                     | Read and filter JSON, e.g. `curl -s localhost:$PORT/api \| jq`           |
| `lazygit`                | Stage, commit and browse changes                                         |
| `btop`                   | See what's using CPU and memory                                          |
| `ncdu`                   | See what's using disk space, folder by folder                            |
| `micro <file>`           | Edit a file (**Ctrl-S** saves, **Ctrl-Q** quits)                         |
| `vim <file>`             | Edit a file in vim                                                       |
| **Ctrl-R**               | Search your command history                                              |
| `/opt/onedrop/restart`       | Restart the preview                                                      |

### Cloud and service CLIs

The Shell also has the command-line tools for the services apps use. Each one installs itself the first time you run it, which takes a few seconds (up to a minute for the biggest), then stays installed:

| Area                    | Commands                                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| Clouds                  | `aws`, `sam`, `gcloud` (with `gsutil`, `bq`), `az`, `doctl`                                           |
| Hosting                 | `wrangler`, `vercel`, `netlify`, `fly`, `railway`, `render`, `cloud` (Laravel Cloud), `cloudflared`   |
| Databases and backends  | `supabase`, `firebase`, `neonctl`, `turso`, `pscale`, `mongosh`                                       |
| Code and payments       | `gh`, `glab`, `stripe`, `eas` (Expo)                                                                  |
| Infrastructure          | `terraform`, `tofu`, `pulumi`, `kubectl`, `helm`, `k9s`                                               |
| Languages               | `bun`, `deno`, `go`                                                                                   |

Run `onedrop-tool list` to see each one's version and whether it's installed yet, or `onedrop-tool install gcloud az` to install some ahead of time. If your app has its own copy (say `wrangler` in its `node_modules`), that one is used.

These are always in the Shell: `psql` and `pg_dump`, `mysql`, `redis-cli`, `python3` with `pip` and `venv`, `uv`, `pnpm` and `yarn`, `yq` (YAML), `xh` (HTTP requests) and `shellcheck`.

OneDrop keeps all of them up to date. A new version of a tool installs the next time you run it.

<Note>To use a tool with your own account, sign in to it in your Shell (`gh auth login`, `aws configure`, `gcloud auth login`). The sign-in stays in the sandbox, where the agent could read it too. The agent won't sign in or deploy for you.</Note>

### Ask the AI and coding agents

Type `ask` and a question to get a short answer from your project's AI, right in the Shell. It uses the same AI as the chat, so there's nothing to set up:

```bash
ask how do I see what's using port 8000
cat storage/logs/laravel.log | ask why is this failing
git diff | ask write a commit message
```

`ask` can read your project's files to answer, but it doesn't change anything or run commands: it tells you what to run. Anything you pipe in goes with the question.

The Shell also has coding agents you can run yourself: `claude` (Claude Code), `codex`, `opencode`, and `pi`, `fx` and `gemini`, which install the first time you run them. Sign in to each with its own login (`claude`, `codex login`, `fx login`, `/login` in pi, `gemini`). A Gemini key you connected in **Settings → AI** works in `gemini` and `pi` straight away.

The Shell keeps your last 10,000 lines of output to scroll back through, also after you reload the page.

## When the app hits an error

The agent sees your app's errors, whatever it's built with. The sandbox records three kinds in `/workspace/.onedrop/errors.log`:

- **Server errors:** any 5xx response, with the error page's text and the end of the dev server's output.
- **Browser errors in the preview:** uncaught exceptions, unhandled promise rejections, `console.error` calls, and scripts or stylesheets that fail to load.
- **The app not answering:** it hasn't started, is restarting, or crashed.

When a page in the preview hits an error, a bar shows it over the preview. Click **Fix it** to send the error to the agent. The request shows up in the chat, and if the agent is busy, it runs next. Dismiss the bar with **×**.

After each agent turn, OneDrop loads the app's home page and checks for new errors from the preview. If it finds any, it sends them to the agent once, automatically. When OpenRouter is set up (your connection or the platform's key), [Jev](https://openrouter.ai/docs/guides/community/jev), a small decision model, first sorts out the noise: errors from a hot-reload rebuild or restart, a browser extension, a missing favicon, or a dev-only warning aren't sent, and when every error is noise, nothing is. Without Jev, every new error is sent. The run that request starts isn't checked again, so this can't loop. Errors from visitors to the published app are recorded for the agent too, but they never start a run on their own.

To turn this automatic fixing off for a project, click **Autofix** in the chat's controls, next to the model picker. Click it again to turn it back on. It's on for new projects. **Fix it** works either way, and always sends the error you clicked it for.

## Monitoring

**Tools → Monitoring** shows how your app is doing. It has two panels, each with its own time range (past hour, day, or week).

| Panel              | What it shows                                                                                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Application**    | Total requests, unique visitors, and the share of server errors (5xx); requests over time; HTTP status classes (2xx, 3xx, 4xx, 5xx) over time; a histogram of response times |
| **Infrastructure** | CPU use as a share of the sandbox's CPU limit, and memory use against its memory limit                                                                                       |

Choose **Published only** to leave out your own preview traffic. Hover a chart for exact values, or open **Show data table** under it.

Numbers are collected inside the sandbox: its proxy logs each request and samples CPU and memory once a minute, into `/workspace/.onedrop/access.log` and `metrics.log`. Requests for development-server internals (hot reload, module loading) aren't counted. The data survives sandbox recreation.

## Growth

**Tools → Growth** helps you get your app found and shows who visits it.

**SEO rating.** Click **Run scan with agent** and the agent checks what search engines and link previews see: page titles, descriptions, headings, Open Graph tags, `robots.txt`, the sitemap, image alt text, canonical URLs and more. It rates the app from 0 to 100 and lists each check as passed, needs work, or failed. To have it fix the problems too, open the arrow next to the button and choose **Scan and fix issues**. Either way, the request shows up in the chat; if the agent is busy, it runs next. The agent saves the result in `/workspace/.onedrop/seo.json`.

**Analytics.** Choose a time range (past day, week, or 30 days), and **Published only** to leave out your own preview traffic.

| Shows                                                  | What it counts                                                                                              |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Visitors**                                           | Unique IP addresses, and the change against the previous period of the same length                          |
| **Page views**                                         | Successful page loads (not scripts, styles, images, or form posts)                                          |
| **Signed-in users**                                    | Your app's users who signed in during the period. Needs sign-in from [Users & Auth](/guides/users-and-auth) |
| **Visitors over time**                                 | Visitors per hour (per day for 30 days)                                                                     |
| **Where visitors are**                                 | A world map: countries shaded by visitors, a bubble per city sized by visitors. Hover for details           |
| **Top pages, referrers, countries, cities, browsers, devices** | The ten biggest of each. Referrers are other sites that linked to yours                             |

<Note>
    Locations come from what sits in front of your app. On OneDrop's hosted
    service, the Cloudflare gateway adds each visitor's country, region, city
    and approximate coordinates (rounded to about 1 km). Self-hosted, a CDN that
    adds location headers (Cloudflare, CloudFront or Vercel) does the same.
    Without one (local Docker, Tailscale), the map and the Countries and Cities
    lists stay empty. Nothing is looked up from IP addresses.
</Note>

The numbers come from the same request log as Monitoring (`/workspace/.onedrop/access.log`), so there's nothing extra to install and nothing leaves the sandbox. Requests logged before Growth existed count as visitors, but they have no page, browser or referrer.

**Custom events.** Page views don't tell you whether people actually sign up, create things or finish a flow. Click **Set up with agent** and the agent finds your app's key moments and records an event for each, like `signed_up` or `project_created`. The request shows up in the chat as "Add custom analytics events to my project"; if the agent is busy, it runs next. The agent uses the model you picked for the project.

Once events are set up, Growth lists each one with its description, how many times it happened, and how many visitors triggered it, for the same time range and traffic filter as Analytics. Click an event to see it over time, the change against the previous period, and its most common property values (for example, which template people chose). To track something else, describe it in the box under the list and click **Add with agent**.

<Note>
    Events never carry personal data. The agent uses fixed event names and a few
    fixed-value properties. It never sends emails, names, anything a person
    typed, or IDs of people.
</Note>

How it works: the app sends each event to its own address (`POST /__onedrop/event`). The sandbox's proxy records it in `/workspace/.onedrop/events.log` and doesn't pass it on to the app. Invalid or oversized events are dropped, and a failed event never breaks the app. The agent describes the events in `/workspace/.onedrop/analytics.json`, following the platform's analytics guide, so every app tracks events the same way.

## Database

**Tools → Database** lets you browse and edit your app's data, similar to Drizzle Studio. It works with SQLite, PostgreSQL, MySQL/MariaDB and [MongoDB](#mongodb).

It finds your app's databases on its own:

- SQLite files anywhere in the project (`.sqlite`, `.sqlite3`, `.db`), except in folders like `node_modules` and `vendor`
- A PostgreSQL or MySQL URL in a `.env` or `.env.local` file, whatever the variable is called (`DATABASE_URL`, `SUPABASE_DB_URL`, `DIRECT_URL`, …)
- Separate settings in those files: Laravel's `DB_CONNECTION`, `DB_HOST`, `DB_DATABASE` and so on; `DB_HOST`, `DB_USER`, `DB_PASS` and `DB_NAME` (the kind of database comes from `DB_DIALECT` or `DB_TYPE`, or from the port); `PGHOST`, `PGUSER` and the rest; `POSTGRES_HOST` or `MYSQL_HOST` with their siblings
- PostgreSQL and MySQL/MariaDB containers your project runs with [Docker Compose](/guides/build-a-project), such as Supabase's `db` service. It knows them by their image (`postgres`, `supabase/postgres`, `postgis`, `mysql`, `mariadb`, …), including your own images built `FROM` one of those, and signs in with the user and password set in the container's environment (`POSTGRES_PASSWORD`, `MYSQL_ROOT_PASSWORD`, and so on) or in a Docker secret (`POSTGRES_PASSWORD_FILE`)

`.env` files are read from the project folder and its direct subfolders. A host in them that names a compose service (like `DB_HOST=db`) is reached at that container, on either its own port or one it publishes. If the app uses more than one database, pick one from the menu at the top left.

| Task         | How                                                                                                                                                                                                                                                             |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Open a table | Click it in the table list, or search for it by name                                                                                                                                                                                                            |
| Sort         | Click a column header. Click again to reverse the order, and a third time to clear it                                                                                                                                                                           |
| Filter       | **Filters**: choose a column, a condition (equals, contains, greater than, is NULL, …) and a value, then **Apply**                                                                                                                                              |
| Edit a cell  | Double-click it, or select it and press <kbd>Enter</kbd>. Press <kbd>Enter</kbd> to keep the edit or <kbd>Esc</kbd> to cancel it. **NULL** sets the cell to NULL                                                                                                |
| Add a row    | **Add row**, then fill in its cells. Cells you leave empty get the column's default value                                                                                                                                                                       |
| Delete rows  | Tick the rows, then **Delete**                                                                                                                                                                                                                                  |
| Run SQL      | **SQL runner**: write one statement and press **Run** (or <kbd>Cmd</kbd>/<kbd>Ctrl</kbd>+<kbd>Enter</kbd>). SQL is highlighted as you type, with suggestions for keywords, tables and the columns of tables in your query; press <kbd>Enter</kbd> to accept one |

Drag the edge between the table list and the grid to make the list wider, for long names. Double-click the edge to reset it. The width is remembered in your browser.

### Ask AI to write a query

Above the SQL runner (and the MongoDB query runner), describe what you're looking for in plain words, like `users who signed up this week without a team`, and press **Write query**. Your project's AI writes the query in your database's own language and puts it in the editor:

- A query that only reads runs right away, so finding records takes one step.
- A query that would change data waits for you to check it and press **Run**. On the [hosted database](#your-hosted-apps-database) it also asks first, as usual.

Ask again to refine it, like `only the ones from Canada`: the AI sees the query in the editor. It's given your tables' and columns' names, never your data. It uses the same AI as the project's chat, so it needs the project's sandbox to be running.

Edits, new rows and deletions are held until you press **Save changes**, and they're saved in a single transaction: all of them or none. You're asked before leaving a table with unsaved changes. Statements in the SQL runner take effect right away.

Views can't be edited. Nor can existing rows of a table without a primary key; change those with the SQL runner instead. Binary values and values over 10 KB show as a read-only preview.

**Download** (the arrow next to the database menu) saves a copy of a SQLite database, safe to take while the app is using it, that you can open in TablePlus, DB Browser for SQLite or DBeaver.

### MongoDB

MongoDB databases show up in the same panel. They're found in two places:

- A `mongodb://` or `mongodb+srv://` URL in a `.env` file, whatever the variable is called (`MONGODB_URI`, `MONGO_URL`, `DATABASE_URL`, …). If the URL names no database, `MONGODB_DATABASE` or `MONGO_DB` supplies one. Separate settings work too: `MONGO_HOST` with `MONGO_USER`, `MONGO_PASSWORD` and `MONGO_DB`, or Laravel MongoDB's `DB_CONNECTION=mongodb`.
- MongoDB containers your project runs with Docker Compose (the `mongo` image, or your own image built `FROM mongo`). It signs in as the root user set in the container's environment (`MONGO_INITDB_ROOT_USERNAME`, `MONGO_INITDB_ROOT_PASSWORD`, or `MONGO_INITDB_ROOT_PASSWORD_FILE` for a Docker secret).

A connection that names a database lists its collections. A container lists the collections of every database on the server, as `database.collection`, leaving out MongoDB's own `admin`, `config` and `local`.

Collections open in the same grid as tables, one document per row. `_id` comes first and is the key. After it come the top-level fields of the documents on the page, each labeled with its type (`objectId`, `string`, `int`, `date`, `object`, `array`, …). Nested objects and arrays show as JSON, and a field a document doesn't have shows as _missing_.

- **Filters** work as they do for tables. **equals** matches the value however it's stored: `42` finds the number 42 and the text "42", and a 24-character hex string finds that ObjectId. **is missing or null** matches documents without the field.
- **Edits keep each field's type.** An ObjectId stays an ObjectId, a date stays a date (type it as `2026-10-06` or `2026-10-06T09:30:00Z`), and a number stays a number. Objects and arrays are edited as JSON. A field the collection doesn't have yet takes the type of what you type: a number, `true` or `false`, a JSON object or array, or else text.
- **Add field** adds a column that none of the shown documents have, so you can fill it in. It's saved only on the documents you fill it in on.
- **Saving**: on a replica set, all of your changes are saved in one transaction, or none are. A standalone server has no transactions, so changes are saved in order. If one fails, the message says how many before it were saved.

The **Query runner** takes mongosh commands, one at a time. Put `use <database>` on a line before the command to pick a database. You can leave it out when the connection names a database, or when the server has only one.

```javascript
use shop
db.users.find({ age: { $gte: 18 } }, { name: 1 }).sort({ name: 1 }).limit(20)
```

It supports:

- **Reading:** `find` (with `.sort`, `.skip`, `.limit`, `.projection` and `.count`), `findOne`, `aggregate`, `countDocuments`, `estimatedDocumentCount` and `distinct`
- **Writing:** `insertOne`, `insertMany`, `updateOne`, `updateMany`, `replaceOne`, `deleteOne` and `deleteMany`
- **Anything else:** `db.getCollection('name')`, `db.getSiblingDB('name')`, `db.runCommand({ … })` (or a bare `{ … }` command), `db.adminCommand({ … })`, `show dbs` and `show collections`

It reads mongosh's literals: unquoted keys, single quotes, `ObjectId('…')`, `ISODate('…')`, `new Date(…)`, `NumberLong('…')`, `NumberDecimal('…')`, `UUID('…')` and `/regex/i`. It also reads Extended JSON, such as `{ "$oid": "…" }`. Commands are highlighted as JavaScript. After `db.` you get suggestions for collection names, after a collection for its methods, and elsewhere for the fields of the collection your command names. Nothing you type is run as JavaScript. Other shell commands (`drop`, `createIndex`, …) can go through `db.runCommand`, or through `mongosh` in the Shell (see [Cloud and service CLIs](#cloud-and-service-clis)).

### Your hosted app's database

When the project is published to [Hosting](/guides/hosting), a **Sandbox / Hosted (live)** switch appears above the browser. **Hosted** shows the hosted app's own data: its SQLite file on its volume, or the Postgres it was given. It works even while the sandbox sleeps, and wakes the hosted app if it's asleep. Everything above works there too, but on your visitors' real data, so saving changes and running SQL that could change it ask first. Download works there as well.

<Note>
    The database is reached from inside the sandbox, so connection details and
    passwords never leave it. Sandboxes created before this feature need a
    rebuilt image; they then [update
    themselves](/self-hosting/sandboxes#sandboxes-update-themselves).
</Note>

## Files

The files panel on the right shows the project's folder tree, with a colored icon for each file type. Click a file to open it next to the preview. Files added, removed or renamed show up in the tree right away, whether the agent, the Shell or your running app made them, and any open file refreshes as the agent works.

- Folders like `node_modules`, `vendor`, and `.git` are listed but not expanded
- Images (SVG too), video, audio and PDFs show as they are, and video and audio play and seek; other binary files and files over 200 KB show a notice instead of their contents
- Type in **Search files** at the top of the panel to show only files and folders whose names contain it; press Escape to clear it
- Press <kbd>⌘</kbd> <kbd>P</kbd> (<kbd>Ctrl</kbd> <kbd>P</kbd> on Windows and Linux) to [go to a file](#go-to-a-file) by name
- Type in **Search in files** below it to [search inside files](#search-inside-files)
- Hide or show the panel with the button in the tab bar; it opens by default on wide screens, and your browser remembers whether you last left it open or closed
- On a phone, open it from **⋯** in the tab bar: it covers the workspace, and closes when you open a file or tap **×**. It always starts closed there

### Go to a file

Press <kbd>⌘</kbd> <kbd>P</kbd> on a Mac or <kbd>Ctrl</kbd> <kbd>P</kbd> on Windows and Linux anywhere in the workspace, even while editing a file or typing in a Shell, or choose **Go to file…** from the files menu. Type a few letters of the file's name or path, in order: `usctl` finds `UserController.php`, and `comp/btn` finds `components/ui/button.tsx`. Letters that start words, and letters in the file's own name, rank highest. Use the arrow keys and press Enter to open the file, or press Escape to close the box. Before you type, the files you opened most recently come first. In a Shell on a Mac, <kbd>Ctrl</kbd> <kbd>P</kbd> stays the shell's "previous command".

It works with the files panel closed, and it includes hidden files like `.env`. Files inside `node_modules`, `vendor`, `.git` and `.cache` aren't listed.

<Tip>
### Search inside files

Type in **Search in files**, the second box at the top of the files panel, or press <kbd>⌘</kbd> <kbd>Shift</kbd> <kbd>F</kbd> (<kbd>Ctrl</kbd> <kbd>Shift</kbd> <kbd>F</kbd> on Windows and Linux) to jump there from anywhere in the workspace. Results show as you type, grouped by file, with each match highlighted. Click a line to open the file with the match selected. Press Escape to clear the box and get the tree back.

The three buttons in the box work like your code editor's:

| Button | What it does |
| ------ | ------------ |
| **Match case** | `User` no longer finds `user`. |
| **Match whole word** | `id` no longer finds `width`. |
| **Use regular expression** | Searches for a pattern, like `use[A-Z]\w+`. |

The search runs inside the sandbox with [ripgrep](https://github.com/BurntSushi/ripgrep), so it's fast even in big projects. It includes hidden files like `.env`, and skips `node_modules`, `vendor`, `.git`, `.cache`, files your `.gitignore` lists, binary files and files over 1 MB. It stops at 1,000 results; type more to narrow it down. Choosing **Search this folder** from a folder's menu limits this box to that folder too.

  Your browser keeps <kbd>⌘</kbd> <kbd>T</kbd> for a new tab, so the workspace
  uses <kbd>⌘</kbd> <kbd>P</kbd>, like VS Code.
</Tip>

| **Upload folder**     | Copies a folder from your computer into the project, keeping its structure. `node_modules`, `.git`, `vendor`, and `.cache` inside it are skipped, and each file can be up to 10 MB. Files with the same path are replaced. |

### File and folder actions

Hover over a file or folder and click its **⋮**, or right-click it:

| Action                                  | What it does                                                                                                                                                                                                |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Rename**                              | Renames it where it is. Type a name with slashes, like `pages/Home.tsx`, to move it into a folder (missing folders are created). If a file open in the editor is renamed, it stays open under its new name. |
| **Search this folder** | Limits the **Search files** and **Search in files** boxes to this folder. Click **×** on the folder's name in the box to search the whole project again. Folders only. |
| **Add file** / **Add folder**           | Creates an empty file (opened in the editor) or folder inside it. Folders only.                                                                                                                             |
| **Collapse child folders**              | Closes every folder inside it. Folders only.                                                                                                                                                                |

Renaming never overwrites anything either: if the new name is taken, you'll see an error.

## Editing files

Open files are editable, with syntax highlighting for most languages.

- Save with the **Save** button or <kbd>Cmd</kbd>/<kbd>Ctrl</kbd>+<kbd>S</kbd>. The file is written straight into the sandbox, so a running dev server picks it up.
- Your app only reads some files when it starts: `.env` files, `.onedrop/dev` and Docker Compose files. After you save one, the editor asks whether to restart the preview so the change takes effect. Choose **Restart**, or **Not now** to restart later from the Services tab.
- A dot on the file's tab means it has unsaved changes. You're asked before closing it or opening another file.
- If the agent changes a file you haven't edited, the editor shows the new version. Your unsaved edits are never overwritten.

### The open file goes with your message

The file open in the editor shows as a chip above the chat box. When you send a message, the agent is told which file you have open (and whether it has unsaved changes), so you can say "rename this component" or "add a test for this" without naming the file. The chat doesn't show this note.

Click the **×** on the chip to send without it. It stays off for that file until you open another one.
